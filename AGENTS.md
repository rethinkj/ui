# rethinkj UI

A native, GPU-rendered UI framework for Java, modelled on [rune](https://github.com/anomalyco/rune) (Rust, MIT). Rune is the reference for scope and concepts: its own renderer, text, layout and animation, plus a headless mode in which an agent can render to PNG, dump the element tree and drive an app with scripted input.

Status: early. `core` runs an app with and without a window: element tree, flexbox layout, text (shaped with HarfBuzz, rasterised with FreeType, with fallback fonts), springs and fading, shadows, clipping and scrolling with scrollbars, lists that build only the rows in view, overlays for menus and dialogs, pointer, wheel and keyboard input with focus, hover and pressed looks and drags, single-line text fields, work off the app's thread, a CPU reference renderer and a GPU renderer that is checked against it, images (PNG and JPEG, with filtered levels when shown smaller), scripts that drive an app, and SDL windows. `kit` has a theme, icons and components up to a data grid, a tree, tabs, split panes, menus and dialogs; `examples` has runnable apps, among them a schema browser. The native libraries (SDL3, wgpu-native, FreeType, HarfBuzz) are packaged per platform and loaded on demand.

- Repository: https://github.com/rethinkj/ui
- License: MIT

## Targets

- Desktop only: Windows 11 or later and Linux. macOS, web and mobile are not targets.
- Runs on an ordinary JRE. GraalVM native image is not a goal, but it has to stay possible. That means:
  - `core` and `kit` depend on `java.base` only. No `java.desktop`: no AWT, no ImageIO, no `java.awt.Font`.
  - No reflection, dynamic proxies or classes generated at run time, in this code or in anything it depends on at run time.
  - Native code is called through the Foreign Function & Memory API only, not JNI or JNA. Every native function's descriptor is a `static final` constant, so it can be registered for native image.

## Build

Requires JDK 25 and Maven 3.9+.

```sh
mvn verify                # build and test everything
mvn -pl kit -am verify    # one module plus the modules it depends on
mvn verify -Dwindows.tests=true   # also the tests that open real windows on the screen
```

Image tests compare what `Headless.render` produces with the PNG and tree files under `core/src/test/resources/golden`. After a deliberate change of the output, rewrite them with `mvn -pl core -am test -Dgolden.update=true` (`-am` builds the natives module that core tests with) and look at the images before committing. A failing image test leaves the expected image, the actual image and their difference in `core/target/golden`.

The layout is tested against Taffy's flexbox cases in `core/src/test/resources/taffy`; `scripts/import-taffy-fixtures.sh` refreshes them. Where Taffy and browsers differ, browsers win: `FlexBrowserMatrixTest` holds 756 cases of wrapping, gaps, `align-content` and auto margins to the rectangles headless Chrome gave (`core/src/test/resources/flex-browser-matrix.tsv`; its Javadoc says what the columns are), and `FlexTest` the aspect ratio with limits (a height that is set is never raised by the ratio, a limit goes through the ratio only to an axis whose size is not set, and a size that is not set comes through the ratio from the other one after that one's limits, also for an absolutely placed box) and the fallback of `space-between`, which is flex-start also where that overflows the start, as under `wrap-reverse`.

On Windows and Linux, the first build downloads the native libraries (see below) and needs network access; later builds, `mvn clean` included, do not. On Linux it also builds SDL, FreeType and HarfBuzz from source, which takes about a minute and needs cmake, make, a C and a C++ compiler, pkg-config, tar with xz, and the development packages listed in `natives-linux-x64/natives.properties`. On Windows it builds FreeType and HarfBuzz from source, which takes one to three minutes and needs Visual Studio's C++ tools (see "Native libraries"). `mvn verify -P '!natives-<platform>'` builds without them and skips the tests that load them.

## Driving an app with a script

`com.rethinkj.ui.Script` drives an app without a window: a script of steps goes in, images and trees come out. An app's `main` passes its arguments to `Script.handle(args, app)`; with `--script <file> --out <folder>` that runs the script, prints the files it wrote and returns true, and without them it returns false and `main` opens the window. `Script.run(text, app, folder)` does the same from Java. On a mistake it throws `Script.Failure`, which names the line and says what to write instead; uncaught, the program exits with status 1.

One step per line. A `#` at the start of a line or before a space starts a comment.

| Step | What it does |
| --- | --- |
| `size <width> <height> [scale <factor>] [at <x>,<y>]` | Sets the window size in logical pixels and the physical pixels per logical pixel (default 1), and with `at` where its top left corner lies on the script's screen, in physical pixels (default 0,0). Needed before the first `frame`; for another window (`window`), it changes that one. |
| `window <name>` | The steps after it go to this window: `main` for the first, else the title a handler opened a window with (`App.windows()`), quoted if it has spaces, as in `window "Note 2"`. See "Several windows". |
| `close` | Asks the chosen window to close, as its close button does: runs its close handler (`Windows.Handle.onCloseRequest`) as input of its app, else closes it. |
| `press <target> [clicks <n>] [shift] [control] [alt] [meta]` | Pointer down and up on the target. `clicks 2` is the second press of a double press, `clicks 3` of a triple one; the modifiers are held during the press, as in `press #name shift`. |
| `press <target> right` | The same with the secondary (right) button, without clicks or modifiers: it runs the handler of `El.onSecondaryPress` with the position, where a context menu opens. `down <target> right` and `up <target> right` are its halves. |
| `down <target> [clicks <n>] [shift] [control] [alt] [meta]`, `up <target>` | The two halves, for a press that ends elsewhere. A press counts only when both land on the same element; one that leaves the tree between them, or is leaving, ends it, also when an element with its identity comes back, and so does a row that its list no longer builds, while one that only scrolls among the rows that exist keeps it. Between them, `move` drags an element with a drag handler (`El.onDrag`) once the pointer is more than 4 pixels from where it went down, and then the press does not count. In a text field, `move` in between selects by dragging, from the first pixel, and drags no element around the field; on a scrollbar's thumb it drags the thumb, also from the first pixel. |
| `move <target>` | Moves the pointer onto the target, which hovers it and the elements around it. Presses do not move the pointer. |
| `leave` | The pointer leaves the window: nothing is hovered. |
| `wheel <target> <deltaX> <deltaY>` | Turns the wheel at the target's position, by these distances in logical pixels; positive scrolls down or right. It does not move the pointer, as `press` does not: hover stays where `move` left it. Along each axis the innermost scroll area under the pointer that can still move that way takes the whole distance, up to its end. |
| `scroll <target> row <index>` | Scrolls the list of rows (`El.rows`) at the target, or the one around it, so that the row `<index>`, counted from 0, is at its top, or as far as the end of the list allows. |
| `key <name> [shift] [control] [alt] [meta] [down \| up]` | Presses and releases a key with these modifiers held, as in `key Tab shift`; with `down` or `up` only that half, so that `key Space down`, `frame`, `snap` shows a key held. Keys have the web's key names (`Enter`, `Tab`, `Space`, `Escape`, `ArrowDown`, `F5`), and a key that types a character is named by it in upper case (`A`, `1`); the Javadoc of `com.rethinkj.ui.Key` lists them all. |
| `type "<text>"` | Text input for the focused element (`\"`, `\\`, `\n` for a line feed and `\t` for a tab inside). |
| `compose "<text>"` | The composition of an input method in the focused text field: shown underlined in place of the selection, not yet in the field's string. `compose ""` ends it; a `type` commits text. |
| `clipboard "<text>"` | Puts the text on the app's clipboard, where a paste takes it from. Needs no `frame`. |
| `dialog "<path>" ["<path>" …] [filter <n>]`, `dialog cancel`, `dialog button "<text>"`, `dialog error "<text>"` | Answers the next dialog of the system the app opens (`App.fileDialog`, `App.messageBox`), which a script never shows: with these paths and the filter chosen, counted from 0 (one path unless the dialog chooses several); cancelled, or a message box closed with its cancel button; a message box's button by its text; or a failure with this text. Write it before the step whose handler opens the dialog; answers are taken in order. The answer arrives as a posted task, so `await` and `frame` after the frame that opened the dialog show it. A dialog that finds no answer fails its `frame` step with a message naming its kind, title and filters, and so does an answer that does not fit it; an answer left over at the end fails the script. Needs no `frame`. |
| `drop <target> "<path>" ["<path>" …]`, `drop <target> text "<text>"`, `drop over <target>`, `drop leave` | What another application drags onto the window (see `El.onFileDrop` under "Windows"): files, or text, dropped at the target; a drag over the target, not yet released, which shows the look of a drop target; and one that leaves the window. |
| `focus <target>` | Gives the keyboard focus to the target, or the nearest focusable element around it, as Tab would. |
| `advance <seconds>` | Moves the app's clock; the actions the app asked for with `App.after` that are due then run at the next `frame`, and a look of `El.cycle` (a spinner, a running bar) shows the phase of that time. |
| `await [<seconds>]` | Waits until the work the app started on other threads (`App.background`) has delivered or was cancelled, at most 10 seconds unless it says otherwise, and queues what it and other threads posted for the next `frame`. Posted tasks reach a script only here (see "Work off the app's thread"). When work still runs after the timeout, it fails and names that work. |
| `frame` | Runs one frame: the handlers and scrolls that input queued, a rebuild of the view, the animations at the current time. |
| `snap <name>` | Writes `<name>.png` and `<name>.tree.txt` of the last frame into the output folder, and `<name>.clipboard.txt` with the text on the app's clipboard if there is any. `<name>` may contain `/` but must stay inside the folder. With several windows open, each other window's frame goes under its title in lower case with hyphens before the name: `groceries-<name>.png`. |

Only `frame` runs a frame, as in a window, where input arrives between frames: `press`, `move`, `leave`, `key`, `type`, `compose`, `focus`, `wheel` and `scroll` queue what they do, `await` queues what other threads delivered and `advance` moves the clock, but the screen changes at the next `frame`. The frame dispatches the queued input in order, each against a tree built from the state the input before it left: after an input that a handler took, it builds the view again before the next, so two `key ArrowDown` before one `frame` move a selection by two rows, a `key` after the `press` that opened a menu goes to the menu, and a `press` after one that dismissed a menu finds no menu there. `snap` refuses to write a frame that does not show the steps before it. Scripts use an in-memory clipboard, the app's default; only a window gives the app the system's.

A `.tree.txt` has one line per element, children indented, with its rectangle in window coordinates as shown, that is, moved by the scroll offsets above it. After the rectangle come the element's states, what the app's state is, with their names from WAI-ARIA, only those that are set and always in this order: `disabled`, `readonly`, `password` (a masked field; there is no WAI-ARIA name for it, so it is UI Automation's `IsPassword`), `invalid` (a value that is not accepted, WAI-ARIA's `aria-invalid`), `busy` (WAI-ARIA's `aria-busy`: a button whose action runs and takes no press meanwhile), `selected`, `current` (the cursor's cell or row among the selected ones, WAI-ARIA's `aria-current`), `grabbed` (what is being dragged, WAI-ARIA's `aria-grabbed`, as a tab on its way to another place), `checked` (or `checked=false`, `checked=mixed`), `expanded` (or `expanded=false`; absent where nothing opens), `level=<n>` (from 1), `pos=<n>/<size>` (the position in its set, from 1, and the set's size), `sort=ascending` or `sort=descending`, and `value="<text>"`, then `error="<text>"`, the message of a value that is not accepted (`El.errorMessage`, which `ValueField` sets; WAI-ARIA's `aria-errormessage`), as in `el #row-8 role=treeitem label="created_at" 8,184 264x22 selected level=5 pos=2/3`. The view sets them with `El.disabled(boolean)`, `invalid(boolean)`, `busy(boolean)`, `selected(boolean)`, `current(boolean)`, `grabbed(boolean)`, `checked(boolean)`, `checkedMixed()`, `expanded(boolean)`, `level(n)`, `position(n, size)`, `sortAscending()`, `sortDescending()` and `value(text)`; they change nothing about how the element looks or takes input. A text field's `disabled` (`editable(null)`), `readonly` (`readOnly()`) and `password` (`masked()`) come from the field, and each row of a list of rows (`El.rows`) has its index plus 1 among all rows as `pos` unless its row function sets another, as in `el #row-765436 role=row 8,119 964x22 selected pos=765437/1000000`. A scroll area that is scrolled adds its offset after the rectangle, as in `el #list role=list 16,16 208x168 scroll 0,90`. A list of rows (`El.rows`) adds before that the rows that exist, first and last, and how many rows it has, as in `el #rows role=grid 16,44 248x160 rows 765429-765440/1000000 scroll 0,21432096`, or `rows -/<count>` when none exist; its children are those rows in order. A line that ends in `exiting` is an element with a key and motion that a rebuild left out: it fades out where it was, takes no input, and is removed once invisible. Selectors do not match it, nor anything at opacity 0. The line of the element that a press under the pointer would go to ends in `hovered`, during a drag that of the dragged element, during a selection by dragging that of the text field and over a scrollbar or while its thumb is dragged that of the scroll area, and that of the element that has the keyboard focus in `focused`. A focused text field adds its caret as an index into its string, then the other end of a selection and an input method's composition: `text #name role=textbox label="Table name" "SELECT name FROM customers" 40,26 160x28 focused caret 17 anchor 26 composing "ni"`. A multi-line field adds, before its scroll offset, the lines that have a row in its content box, counted from 1, and how many lines it has, and after its caret the caret's line and column, both from 1, the column in UTF-16 units: `text #query role=textbox label="Query" "SELECT *\nFROM orders\nLIMIT 20;" 253,44 455x82 lines 1-3/3 focused caret 31 (3:9)`, or `lines 49998-50002/100000 scroll 0,899964` in a long text. A masked field shows its mask instead, one `•` per grapheme, with the caret, the anchor and the composition in it: `text #password role=textbox label="Password" "•••••••" 104,246 260x24 password focused caret 6 anchor 7`.

The overlays shown above the tree (see Overlays) follow it, in the order they are drawn, each under a line that starts with `overlay`, says where it is placed and ends with what it is anchored to, its key, role, label and rectangle as shown; the overlay's tree follows, indented by two spaces, in window coordinates:

```text
overlay at 120,85 bottom start on #list role=list label="Tables" 16,16 208x146
  el #menu role=menu 120,85 81x86
    el #open role=menuitem label="Open" 125,90 71x24 focused
overlay right start gap 6 on #export role=menuitem label="Export" 125,116 71x24
  el #formats role=menu 53,116 66x60
overlay center modal scrim on 0,0 240x200
  el #dialog role=dialog label="Delete" 34,55 172x91
```

An overlay placed against an edge of the window, as the kit's toast is, says so the same way: `overlay edge bottom center gap 16 on 0,0 360x240`.

Keys go to the focused element and then up through its ancestors until a key handler takes them; without focus only the root gets them. If none does, Tab and Shift+Tab move the focus through the focusable elements in tree order, around at the ends, and Enter and Space press the focused element, which shows its `El.whenPressed` look (and is `App.pressed()`) while the key is held and at least `App.KEY_PRESS` (0.1 s of the app's clock) after it went down when it comes up in a later frame; a key that goes down and up in one frame, as a script's `key`, shows none, so stored images do not change, and a window that goes inactive ends it (`KeyPressTest`). A press focuses the focusable element it lands in and clears the focus elsewhere, unless it lands in an element with `El.keepFocus()`, which leaves the focus where it is, with its ring (the button that shows a password leaves it in the field). `focusable().keepFocus()` is an element that only the keyboard focuses: Tab reaches it and Enter and Space press it, but a press leaves the focus where it was. The kit's buttons, toggles, checkboxes, selects, tab bar and split dividers are made so; text fields, the data grid, the tree and menus take the focus when pressed. Focus moved by the keyboard or by `focus` is drawn with a ring and scrolls into view; a press shows no ring. The ring lies 2 pixels outside the element's border box, or `El.focusRingGap(pixels)` beyond it, with what lies behind the element showing in the gap (the kit's primary button, whose fill is the accent its ring has), or just inside it, without a gap, where a clip around the element or the window's edge would cut it, as around a grid that fills a pane; it is clipped like the element, so an element scrolled half out shows half a ring. When a rebuild leaves out the focused element, or it can no longer take the focus, the focus goes to the nearest element along its old identity path, below the root, that takes the focus or holds one that does, then to that one, the first in tree order (`App.focused` says so): closing the active tab from its content puts the focus into the next tab's content, and an editor laid over a cell gives it back to the grid when it goes. With nothing focusable around it below the root, the focus is cleared and keys reach only the root. The ring stays as it was, so a focus that a key moved away shows it in its new place. `El.autofocus()` makes an element take the focus in the build that adds it, the first such in tree order that can take it once laid out (one clipped away passes it on to the next, also one that has the focus already) (the editor that Enter lays over a cell), with the ring if the focus had one, and in a row of a virtual list when the list builds the row, again when it comes back after leaving the rows that exist (the grid's own editor); `autofocus(key)` also takes it whenever a build gives it another key than the build before (the first field with an error, keyed by the count of Save presses). Among the elements a lost focus goes to, an `autofocus` one comes first. Besides `El.whenFocused`, `El.whenFocusWithin(look)` is a look for while the focus is on the element or inside it, as CSS's `:focus-within`, also in the rows of a list.

A target of `press`, `down`, `up`, `move` and `wheel` may also lie in another window, `in <window> <target>`, as in `move in Groceries #text`, or be a point of the script's screen, `screen <x>,<y>` in physical pixels, which goes to the window that lies there. Between `down` and `up`, `move` and `up` go to the window the press began in, wherever the target is, as the system's capture of the pointer has it.

A target is a position `x,y` in logical pixels, or a selector for exactly one element of the last frame: `#key` (anywhere in the tree and its overlays), `role=<role>`, `label="<text>"` (`\"` and `\\` inside), `text="<string>"` (see Text), a state as a `.tree.txt` writes it (`selected`, `current`, `grabbed`, `disabled`, `readonly`, `password`, `invalid`, `busy`, `checked`, `checked=false`, `checked=mixed`, `expanded`, `expanded=false`, `level=<n>`, `pos=<n>/<size>`, `sort=ascending`, `sort=descending`, `value="<text>"`; `checked=true` and `expanded=true` also do), or several of them, as in `role=switch label="Lights"` or `role=treeitem expanded label="public"`. A selector presses the centre of the element's rectangle. When it matches nothing, the error lists the keys, roles, labels and states there are, and the texts if there are any, and the lists of rows with the rows that exist, since a selector finds only those; when only its states match nothing, it lists the lines of the elements that match the rest, which show their states; when it matches several, it lists them with their rectangles.

The examples have text, so running one needs the fonts and the platform's native libraries on the class path besides core's classes. Build them, and keep the class path in `CP`, from the repository root. On Linux, in a POSIX shell, with `:` between the entries:

```sh
mvn -q -pl core -am test-compile
CP=core/target/classes:core/target/test-classes:fonts/target/classes:natives-linux-x64/target/classes
```

On Windows, in PowerShell, with `;` between the entries and the Windows natives instead, since `natives-linux-x64/target/classes` exists only where the Linux module is built:

```powershell
mvn -q -pl core -am test-compile
$CP = 'core/target/classes;core/target/test-classes;fonts/target/classes;natives-windows-x64/target/classes'
```

A scroll area scrolls as far as its content reaches: its children's border boxes with their margins, and what sticks out of the descendants inside them that do not clip, as CSS's scrollable overflow has it. A scroll area with `El.scrollbars(look)` has a bar along each axis whose content does not fit, and the line of the area in a `.tree.txt` ends in the rectangle of each thumb, `thumb-x` for the bar along the bottom and `thumb-y` for the one along the right edge, as in `el #rows role=grid 16,44 248x160 rows 0-8/1000000 thumb-y 256,46 6x24`. `down`, `move` and `up` at positions inside it drag the thumb, and a `press` on the track beside it scrolls a page. `core/src/test/resources/scripts/scrollbars.txt` drags the thumb of the million rows with bars, which `Examples` runs when `bars` comes first:

## Text fields

`El.text(value).editable(onEdit)` makes a single-line text field, and `.multiline()` after it one of several lines (see the points on multi-line fields below). The string belongs to the app: the view builds the field with the current value, and every edit hands the new string to `onEdit`, which stores it in the state. A handler may refuse an edit (store nothing), also an undo or a redo, which leaves the history as it was, or change it (keep only digits, say); the field then shows the app's string, with the caret where it was before a refused edit, and otherwise at the same distance from the text after it or before it, whichever the change left alone. A value the app changes on its own keeps the caret near its text and ends the undo history.

- `App` keeps per field, by the element's identity as for scroll offsets: caret and anchor (indexes into the string), horizontal scroll, undo history (100 steps; a run of typing, a run of deleting, a paste or cut each one step; moving the caret ends a run) and an input method's composition. A step holds the edit, where it replaced what by what with the caret and anchor before and after, never a copy of the string; undo comes back to the selection of the moment before, redo to the one before the undo. An edit the app changes becomes one step from before it to what the app made. The editing core is `Editor`, package-private; it works on strings and does not assume one line except where a single-line field turns line breaks into spaces and Home and End go to the ends.
- What `App` keeps by identity it forgets when the field leaves the tree, as the content of a tab that is not active does. `El.fieldState(FieldState)` keeps it in an object of the app's state instead, in the manner of `Menu.State`: the field's `Editor` lives in the `FieldState`, so caret, anchor, scroll of both axes (saved as the field leaves and set again in `Editor.placeLines` as it returns, also where another field had the same identity), undo history and Tab's mode (`tabIndents`, Control+M) come back with it, and with them the `Lines` and the highlighter's spans: going back to a tab with 100 000 lines (3.5 MB) costs about 0.25 ms (`FieldStateTest` prints it). A string the app changed meanwhile ends the history, as any change of the app's does; a composition ends as the field leaves. Two fields of one build with one `FieldState` throw when the view is built. `CodeEditor.State` holds one. A field that moves to the tree of another `App` of the same state, as a tab to another window, takes it with it, whichever app builds first. `FieldStateTest`.
- The caret stops only at grapheme boundaries (`BreakIterator.getCharacterInstance`): never inside a surrogate pair, between a letter and its combining mark, or inside an emoji sequence; Backspace removes a grapheme. Words (Ctrl+arrows, Ctrl+Backspace, Ctrl+Delete, double press) are segments of `BreakIterator.getWordInstance` with a letter or digit, which takes `shop.public.orders` for one word; with `El.codeWords()`, which `TextField.codeArea` and `CodeEditor` set, a word is a run of letters, digits and `_`, each with the marks, modifiers and joined characters of its grapheme (a mark goes with whatever stands before it but a line break, and a joiner joins only an emoji to an emoji before it, as `BreakIterator.getCharacterInstance` does), a run of spaces and tabs is one segment for a double press, and every other grapheme one of its own; every word key and double press ends between whole graphemes (`Editor.codeWord`, `codeWordLeft`, `codeWordRight`, scanned from the caret without a `BreakIterator`). Ctrl+Right and Ctrl+Delete go to the end of a word on Linux and to the start of the next one on Windows (`Editor.WORD_ENDS`), so scripts with stored images avoid them.
- Keys: arrows, Home, End, with Shift to select and Control by words; Backspace, Delete; Control+A, C, X, V, Z, Y and Control+Shift+Z; Control+Insert, Shift+Insert and Shift+Delete. Keys that type are the field's (their text comes with `textInput`); Enter, Escape, Tab and unknown shortcuts go on to the `onKey` handlers. The field's own `onKey` sees every key first. While an input method composes, it has the keys. Tab into a single-line field selects its text; into a multi-line one it leaves caret and selection as they are.
- Pointer: a press places the caret at the nearest boundary, a drag selects (beyond the edge it scrolls, one step per pointer move), a second press (`clicks 2`) selects a word and drags by words, a third everything (in a multi-line field the line with its line feed, dragging by lines, and a fourth everything), Shift extends. `App.pointerDown(x, y, clicks, modifiers)` takes what the window reports. A press in a field is the field's, even inside an element with `onPress` or `onDrag`: moving from it selects from the first pixel, without the drag threshold, and never becomes a drag of an element around the field, which can be grabbed outside the field instead. Until the release the field counts as hovered and pressed (`El.whenPressed`) and keeps its cursor, wherever the pointer is, as a dragged element does. A selection has nothing to cancel: if the field leaves the tree or the release gets lost, it stays as far as it got.
- Caret positions come from the shaped `GlyphRun`: at the pen position of the glyph that starts the next cluster, so kerning counts, and inside a ligature (Inter's `->` with `.fontFeatures("+calt")`) in proportion to the graphemes before it. JetBrains Mono draws its ligatures with one glyph per character, so its carets are plain.
- Drawing: `Text.selection()` behind the glyphs, `Text.composition()` (the underline) and `Text.caret()` after them, all ordinary rectangles with edges on whole physical pixels, clipped with the glyphs to the content box across and the padding box from top to bottom; the glyphs move left by `Text.scroll()`, which keeps the caret in view with `Editor.MARGIN` (4 logical pixels) to spare when the text is wider than the field. Without the focus a field shows its start, no caret and no selection, and forgets its scroll; a window that loses the focus leaves all that as it is and only hides the caret (next point). The line is centred vertically; layout measures a field as 0 wide, so its style gives the width.
- The caret blinks on the app's clock, on for `App.BLINK` (0.5 s), off as long, and restarts on after each change; `frame()` returns true only when it turns, and `App.nextChange()` says when that is, which `WindowLoop` waits for. `App.windowMaximized(boolean)`, which `WindowLoop` passes on from the window's state, builds the view again with `app.windowMaximized()` telling it (`WindowLoopTest`). While the window is inactive (`App.windowActive(false)`, which `WindowLoop` passes on from the window's focus at the start and from its focus events after, so that a window shown without the focus, as one opened under the pointer, starts inactive) there is no caret and nothing blinks; focus, selection and ring stay as they are, and activation turns the caret on.
- `.masked()` (or `masked(boolean)`, which the view sets on every build) shows one mask character per grapheme, `Text.MASK` (U+2022, which Inter and JetBrains Mono have) unless `.maskCharacter(c)` sets another; the string is still the app's. Caret and selection are indexes into the real string at its grapheme boundaries, and grapheme `n` stands at mask glyph `n`: `Text` shapes only the mask (with the composition masked in it) and maps positions between the two (`toGlyphs`, `fromGlyphs`), so `Editor` works on the real string as before. Copy, cut, Control+Insert and Shift+Delete do nothing and leave the clipboard as it was; paste works. Word keys and a double press take the whole string as one word. `Text.string()` returns the mask, so the dump, selectors (`text="…"` matches the mask, never the value), `Script`'s errors and every message built from a `.tree.txt` line see only it; the dump shows the state `password` and caret, anchor and composition in the mask. The real string stays in the app's state, the element's `Text` (`value()`, package-private), the `Editor` and its undo history, as it would in any field. `App.inputArea().password()` makes `WindowLoop` start text input for a hidden password (`SDL_TEXTINPUT_TYPE_TEXT_PASSWORD_HIDDEN`, starting text input again when it changes), which SDL 3.4 passes on only on Wayland, as text-input-v3's purpose `password` with `hidden_text` and `sensitive_data`; on Windows and X11 the input method composes as in any field, and the composition is masked. Building the field without `masked` shows the string, and caret, selection, scroll and history stay, as they belong to the identity; it is then an ordinary field that copies. `MaskedFieldTest` checks all this, also that `Font.shape` never sees the string (`FontProbe`).
- `.readOnly()`: focus, selection and copy, no edits; it shows a caret and takes no text input. `editable(null)` disables the field: no focus, presses go to its ancestors. A `.tree.txt` says `readonly` or `disabled` after the field's rectangle without a call of `El.disabled`. `.maxLength(n)` limits typed and pasted text to `n` code points, cut at a whole grapheme. `.placeholder(text, argb)`, `.caretColor(argb)` (the text colour unless set), `.selectionColor(argb)`.
- The clipboard is `App.clipboard()`, a `Clipboard`: `Clipboard.inMemory()` at first, which scripts and tests use, and the system's (SDL) once a `WindowLoop` runs the app.
- `App.inputArea()` is the focused field's box and caret for the system's input method, or null when the focused element takes no text; from a primary press that lands in an editable field until the frame that dispatches it, it is that field's, since SDL makes text events only while text input is on, and a character typed before that frame would otherwise come as a key alone and be lost (`WindowLoop` asks again right after the press), which is too late for keys that come in the same batch as the press: their characters reach the field through `App.keyText` (see Windows: on Windows the window makes them from `WM_CHAR`, on X11 and Wayland it turns text input on as SDL queues the press); `WindowLoop` turns the window's text input on with it (`Window.textInputArea`) and off without (`Window.stopTextInput`), so an on-screen keyboard shows only for a field. Compositions arrive as `WindowEvent.TextEditing` and go to `App.textComposition`; the window asks SDL to leave drawing them to the app (`SDL_IME_IMPLEMENTED_UI=composition`).
- A field in a row of a virtual list (`El.rows`) gets its editor when the list builds the row, by the row's index. The editor goes when the row leaves the rows that exist, as everything else the app keeps of a row, except the focused field's: it stays with the focus and comes back with the row, without its composition. Text typed meanwhile, and Backspace, Delete, Control+V, X, Z, Y and Shift+Insert, bring the row of an editable field back into view first and go into it, as an editor brings its caret back on typing (`App.wakeField`, as Tab's `wake`); other keys go to the list and its ancestors, as before (`FieldRowsTest`).
- Multi-line fields (`.multiline()`): the string has a line feed per line break. Carriage returns, with or without a line feed after them, and U+2028 and U+2029 become line feeds in typed, pasted and composed text (the composition's cursor moving with them) and in the app's value, which the field shows and edits so (`Text.string()` and the dump see line feeds); the app's string keeps them until the first edit, which hands it the string with line feeds only. `.masked()` and `.multiline()` refuse each other with a message.
- Keys of a multi-line field, besides those above, which work across lines (Ctrl+Left goes over a line feed, Backspace at a line's start joins it to the one before): Enter and Shift+Enter break the line, and the field takes them, so an ancestor's Enter does not run, read-only or not; Control+Enter (and Alt, Meta) go on to the `onKey` handlers, so an app runs a query with it. Up and Down move by a row on screen, Page Up and Page Down by the rows the content box holds and scroll as far, all keeping a goal x in pixels that a horizontal move or an edit resets; above the first row Up goes to the start of the text, below the last Down to its end. Home goes to the start of the row, and on the first row of a line a second Home to the first character that is not a space or a tab, a third back; End to the end of the row, which for a wrapped row is before the space it wraps at (there is no caret affinity, so a caret at a wrap stands at the start of the next row). Control+Home and Control+End go to the ends of the text. All with Shift to select.
- Tab in a multi-line field moves the focus, unless `.tabIndents(spaces)`: then Tab puts a tab, or with `spaces` spaces up to the next stop, in place of a selection inside a line, and with a selection across lines indents each but empty lines by a tab or `tabSize` spaces; Shift+Tab takes up to one of those from the start of the caret's line or each selected line. A selection that ends at the start of a line leaves that line out, and a position at the start of a line stays there; each indent is one step of the history, and one that would make the text longer than `maxLength` does nothing, while an outdent works also on a text that is longer already. Escape and then Tab (or Shift+Tab; the key presses of modifiers alone between them do not count) move the focus, and Control+M switches Tab between moving the focus and indenting until it is pressed again; a read-only field leaves Tab to the focus. `.tabSize(n)` (4) sets the tab stops: a tab advances to the next multiple of n spaces of the font, from the start of its line, which `Text` does by shaping a space in its place and widening that glyph (`GlyphRun.tabbed`), so carets and selection on both sides follow.
- Layout and scrolling of a multi-line field: it is a scroll area of its own (`overflow-y: scroll`, and `overflow-x: scroll` unless it wraps), so the wheel scrolls it while it can and its ancestors beyond, `.scrollbars(look)` gives it bars that drag and page as any area's, `App.scrollTo` and the dump's `scroll x,y` work, and the offsets stay with its identity. Its rows start at the top of the content box and are clipped to the content box both ways, so they scroll by under the padding. Layout measures it 0 wide and `.lines(n)` (1) lines high, so a field without a height in its style is exactly n lines high at every scale. `.wrapText()` breaks lines at the content box's width (no horizontal scrolling); `wrapText(false)` lets them be as long as they are and the field scroll sideways, the width being the widest line shaped so far plus room for the caret, which grows as longer lines come into view, as in editors, and is measured anew at another font, size, scale, tab size or features. An edit or a move of the caret scrolls just far enough to show the caret's row whole and the caret with `Editor.MARGIN` to spare sideways; the wheel and the bars may scroll it out of view, and the next key or edit brings it back. Without the focus it keeps its scroll, and shows neither caret nor selection.
- Selection of a multi-line field: one rectangle per row in view; on a row whose end is selected, its line feed or the end of a wrapped row, it reaches the right edge of the content box, as editors show a selected line break; an empty line in the selection is a full-width rectangle. There is no current-line highlight: it would need a background per row before the selection, which `Scene` draws from `Text.selection()` alone. `App.inputArea()` gives the caret's row (the field's x and width, the row's top and height, clamped into the field), with the caret's x as the cursor.
- Large texts: `Text` of a multi-line field shapes and lays out only the rows in the content box and three more above and below (`Text.lines()` holds those, their baselines moved up by the vertical scroll), however long the text. The field's `Editor` keeps `Lines`: the line starts as a sorted array, found by binary search and changed by each edit in place (the starts after it move by the difference, an `arraycopy` and an addition per later line: about 0.1 ms for 100 000 lines, less than the copy of the string the edit makes), and, while wrapping, the rows each line takes in a Fenwick tree: measured once shaped at the width, estimated from the length and the font's average advance until then, so that the row at a height, a line's height and the text's height cost a logarithm. An edit that changes the number of lines rebuilds the tree in one pass; another width, font or size forgets what was measured. When layout measures rows above the view for the first time, the view moves by as much, so what is in view does not jump; the thumb moves a little instead. The grapheme iterator of the JDK reads its whole text when set (about 110 ms for 5 MB), so the editor asks it about the line of a position alone. `TextAreaLargeTest` counts the lines shaped per frame (at most 28, from a counter in `Lines`) and prints timings, here alone on a desktop with 12 threads (under the load of a full build up to five times as long): with 100 000 lines of about 40 characters (4 MB) a typed key with its frame takes 2 to 7 ms, Enter with a key 3 to 12 (two edits, and one more line to put into the starts), Page Down under 1, a wheel step 0.1; single runs of Control+End and Control+Home took 0.1 to 8, of Control+A and Delete 0.1 to 11, and the undo of that 4 to 8, the larger ones with a garbage collection in them. Each edit still replaces the app's string: with 5.3 MB the copy with one more character takes 1.5 to 4 ms and allocates about two copies of the string (10 MB), and a key with its frame 2 to 3 ms. The next step, if that ever is too slow, is a document the app holds instead of a string (a piece table or rope behind a `CharSequence`), which `Lines` and the editor's edit steps already fit: they speak of offsets and replaced ranges, not of strings.
- Highlighting: `El.highlight(key, highlighter)` colours ranges of a text and sets them in other fonts of its size. A `Highlighter` gets a line, the state the line before ended in (null for the first) and a `Spans`, on which it calls `color(from, to, argb)`, `font(from, to, font)` (the font as given: give it the fallbacks the text needs), `background(from, to, argb)`, `underline(from, to, argb)`, `strike(from, to, argb)` (a line through the middle of the lower-case letters, as thick as an underline, behind the glyphs) and `lineBackground(argb)`, and returns the line's end state, compared with `equals` (null for none). A multi-line field asks only about the lines it shapes; `Lines` keeps per line the spans and the state they were given for, and the state each line starts in up to a high-water mark. An edit moves both arrays along with the starts, forgets the spans of the lines it touched and lowers the mark to the first of them, asking nothing; shaping a line at or below the mark first asks about the lines from the mark to it, with spans that keep nothing, and a line whose start state comes out equal keeps its spans. So `/*` typed at the top of 100 000 lines asks about the lines from the top to the view (about 20), and the first view of the end after it asks about every line once: about 30 ms with `Sql` once the JIT is warm, 60 ms cold (`CodeEditorLargeTest`, 4 MB); a jump back and forth then costs nothing. No slicing across frames: at this size a pass is shorter than a frame of a wheel that scrolls far; slicing would be the next step for texts ten times larger. The same key on every rebuild keeps everything; another key asks again. Other text, a single-line field among them, is one line, asked on every build; a masked field and a placeholder are not highlighted. Colours need no shaping: `Text.Line.colors()` holds a colour per glyph, from the colour of the character that starts its cluster, and `Scene` gives each glyph its colour and the correction for that colour. A range in another font is shaped on its own (`GlyphRun.concat` joins the parts, clusters moved to their place in the line), so carets, selection, wrapping and hit testing follow its glyphs; kerning across a font change is lost. Tabs, wrapping, fallback fonts and ellipses keep the colours (an ellipsis has the text's). `HighlightTest` checks all of it.
- Decorations: `El.decorate(decorator)` on a multi-line field: a `Decorator` gets each line in view and a few around it (index, start in the string, text, `Spans`) whenever the rows are laid out, keeps nothing, and gives backgrounds, underlines and the line's background, such as the caret's line, matches of a find, a bracket pair or an error. `Text.marks()` holds them for the rows laid out: line backgrounds across the content box (each row of a wrapped line), then range backgrounds, a line high, then underlines where a composition's underline lies, as thick, the highlighter's and the decorator's alike; `Scene` draws them after the field's fill and before its selection, with the selection's clip. Not in single-line fields. A wavy underline would need a drawing primitive of its own.
- Gutter: `El.gutter((line, caret) -> cell)` on a multi-line field builds a cell per line for the lines laid out, at each line's first row, a line high, in a column `#gutter` that `Editor.placeLines` makes the field's only child once the rows are laid out and scrolled: inside the field's border and padding, clipped to the content box's height, staying in place sideways and moving up and down with the text (the column is placed where the scroll that shifts the field's children brings it back). Layout treats a text element as a leaf whatever children it has. The column is as wide as the cell of the last line laid out at its natural width when `El.scaleText` runs (or as the cells set), and the field's left padding grows by as much, so text, carets, hit testing and the input area start after it. Cells are built again only when the lines laid out, their places, the scroll or the caret's line change (not for a blink); without a key they are `line-<index>`. Presses reach a cell's handlers; elsewhere in the column they focus the field. No hover or pressed looks on cells (they are built after the looks are applied), and `Headless.render` without an `App` draws no gutter. `GutterTest`.
- Documents: `.fitLines()` makes a multi-line field exactly as high as all its rows at its width, so it never scrolls up and down (every row is shaped), and `El.skipTab()` lets Tab pass a focusable element by while a press and `App.focus` still focus it: a read-only paragraph that selects and copies between the links Tab reaches. `El.range(from, to)` on a child of a multi-line field lays the child over those characters of the field's string instead of where layout would put it: its rectangle in the dump is the bounding box of the rows the range takes, but it is hit, filled (behind the glyphs) and ringed only on those rows, one rectangle per row (`El.rangeBoxes()`), placed after layout and again after the field's editor scrolls. It takes presses, cursor, hover looks and the focus like any element, and a press on it is its own, not the field's; Enter presses it when focused. A script's selector presses the middle of its first row. That is how a link is made: a range child with `role=link`, a label, `focusable()`, `cursor(POINTER)` and `onPress`, so that `press role=link label="…"` and Tab reach it. Ranges are a child rather than part of `Spans`, because a link needs an identity for the focus, a handler and a line in the dump, also for lines no highlighter has been asked about. `RangeTest`.
- Caret and selection for the app: `El.onSelect((caret, anchor) -> …)` is told the caret and the anchor, always between graphemes, whenever they changed: `App` asks each editor after every input and after the rebuild at the end of a frame (which it builds once more when a handler was told), so a refused edit and the app's own change of the string are told too, and a new field tells where its caret starts. `App.edit(field, from, to, text, caret)` replaces a range and puts the caret there (a caret in or after `text` moves as the field's line breaks and `maxLength` change `text`) as one step of the history, through `onEdit` as typed text, with the field's limits; `App.undo(field)` and `App.redo(field)` step through the field's history as Control+Z and Control+Y do, for an Edit menu; `App.select(field, caret, anchor)` selects and scrolls into view, a multi-line field also while it does not have the focus, as a find bar's matches. Both take a field of the last frame's tree and run right after the handler that calls them, as `App.scrollTo` does, in the field of the same identity. An overlay with `.atCaret()` is placed beside its anchor field's caret, a line high, instead of the anchor's rectangle (`Editor.caretBox`), again after the editors are placed, so it follows the caret without a rebuild. A component that adds its own handlers to a field the view made calls the field's too: `El.onSelect()`, `El.onKey()` and `El.decorator()` return what the view gave. `CaretTest`.
- `FieldTest` and `FieldGeometryTest` drive fields through `App`, `FieldRowsTest` drives them in the rows of a list and in a scroll area; `EditorTest` checks boundaries and needs no native libraries. `TextAreaTest` drives the keys of multi-line fields, `TextAreaPointerTest` presses, drags beyond all four edges, the wheel and the bars, `TextAreaLargeTest` 100 000 lines and 5 MB; `LinesTest` checks the line starts and rows against a fresh count after random edits, without native libraries.

## Overlays

A menu, a tooltip, a dropdown list or a dialog lies above everything else and is not clipped by the scroll area its anchor is in. The view declares it next to the element it belongs to, `anchor.overlay(menu)`, so that a component returns its anchor with what it opens attached; whether it is open is the app's state, as all state: `button.overlay(s.menuOpen ? menu : null)`. An overlay is an ordinary tree with layout, text, scrolling, motion and presence: its identity is the anchor's plus its key or index among the anchor's overlays, counted apart from the children, so one with a key and `motion` fades in as it opens and out as it closes. `El.overlays()` lists an element's overlays; after a frame, the root's `El.shownOverlays()` lists those shown, in drawing order, in window coordinates.

- Placement, after layout (`Overlays`, package-private): each overlay is laid out as a root of its own, at most as large as the window (its max size is limited to it; one with `scroll()` then scrolls), and placed beside its anchor's rectangle as shown, moved by the scroll offsets above it. `.side(Side, Style.Align, gap)` (default `BOTTOM`, `START`, 0) puts it on a side, aligned `START`, `CENTER` or `END` along it, or `STRETCH` for at least as wide as the anchor (a select's list); `.atPoint(x, y)` takes a point of the window instead of the rectangle (a context menu at the pointer); `.atCaret()` the caret of the anchor, a text field (completions; see Text fields); `.centerInWindow()` a dialog; `.atWindowEdge(side, align, gap)` lies against an edge of the window, `gap` away from it (a toast at the bottom). Where it does not fit, it goes to the other side, then to the other end along the side, then moves into the window as far as it needs; a tooltip (below) keeps its gap from the window's edges too where there is room, so that it does not sit flush with them. An overlay inside one that went to the other side than it asked tries that other side first when it asks the same side, so submenus go on to the left once one flipped at the window's right edge. An overlay that a delayed look attached (`whenHoveredFor`, `whenFocusVisibleFor`: a tooltip) and that would cover its anchor goes to a side across where one has room: under the pointer it would take the hover from its anchor and hide again. Positions are whole logical pixels. It is placed again in every frame that scrolls, moves or builds rows, so it follows its anchor.
- An overlay shows while its anchor shows. When the anchor is clipped away entirely (scrolled out of its area), lies wholly outside the window (an anchor of no width or height counts on the window's edge), made invisible by the view or leaving, the overlay is neither drawn nor hit, and stays open; one the view itself makes invisible (opacity 0) is not shown either, so a modal one blocks nothing, and one that fades in counts from its first frame; an anchor that fades in counts from its first frame, as for the focus, so a submenu that a key opens in the frame its menu appeared in shows and takes the focus: the state is the app's, and the core never closes anything. In practice the wheel closes menus first (below); a programmatic scroll leaves them hidden until the anchor is back.
- Drawing (`Scene`): after the whole tree, in the order the overlays opened (the animator counts when an identity first appeared; a submenu opens after its menu, and ties keep tree order), each as a tree of its own from clip entry 0, so free of the anchor's clips and opacity, with its own (rounded) clips. `.scrim(argb)` draws a rectangle as large as clip entry 0 in that colour before the overlay, at its opacity. No new instance kind: order and clip indices only. An overlay's shadows (`El.shadow`, see GPU renderer) come with it, under it and free of the anchor's clips like the rest of it; the kit lifts its overlays with them and keeps a border from its tokens.
- Hit testing: overlays first, the topmost first; within a tree it descends from the root to the last child whose box holds the point, so a child is hit only inside its parent's box, also where the parent does not clip (`App`'s Javadoc says why); a hit inside an overlay goes no further than its root: press and drag targets, hover looks, the cursor and the scroll areas the wheel moves are those of the overlay, never its anchor's. Hover belongs to the topmost thing under the pointer.
- A press outside: the overlays above the first one the press lands in get their `.onDismiss` handler called, the topmost first. If the press lands in an overlay below them, it goes on there (a press on a menu item closes the item's sibling's submenu and chooses the item). If it lands outside all overlays and one was dismissed, that is all it does: the menu button pressed again closes its menu and does not open it again, and a press beside a menu does no second, accidental action. Overlays without a dismiss handler (a tooltip) let presses through. `El.dismissGroup(group)` on an overlay and on elements outside it (equal by `equals`; the kit uses the component's state object) makes a press on such an element, or inside it, count as landing in the overlays of the group: they are not dismissed and the press goes on to the element, whose handler decides. A menu bar puts its titles and their menus in one group, so that a press on another title switches menus with one click and a press on the open menu's title closes it; dropdowns, context menus, selects and dialogs set no group and dismiss as before. After the overlays, a press outside an element that holds the focus (`El.holdFocus`, below) calls its `onDismiss` handler and goes no further. The secondary button dismisses the same way. The handlers run when the frame reaches the press, in the order of input, and the input after it finds the tree they left.
- The wheel outside a non-modal overlay calls its dismiss handler and scrolls what is under the pointer, as Swing's popups and browsers' select lists close on scrolling: a menu that rode along with scrolled content would cover other content and lose its anchor.
- `.modal()`: input outside it reaches nothing below it. A press there calls its dismiss handler and nothing else (the scrim of a dialog), the wheel does nothing, hover finds nothing, `App.focus` refuses elements outside it, Tab and Shift+Tab go around inside it, and keys go up from the focused element only as far as its root, which gets them while nothing has the focus. Overlays that open above it, such as its select's list, work as usual. An overlay that is leaving no longer blocks. The parts of a frameless window's own frame (`El.windowPart`) stay usable under it: `App.windowPart` looks through it, so the window can still be moved, minimized, maximized and closed, and a press on such a part neither dismisses it nor reaches anything else. Closing the window closes it without the dialog's dismiss handler: dismissing means cancelling the dialog, which the user did not ask for, and the window's close request is where an app would ask whether to close.
- Focus: an overlay that opens moves the focus to its first `El.autofocus` element, else its first focusable element in tree order, without a ring (while it does, elements outside it that ask with `autofocus` get nothing); a modal one without such an element takes the focus away. When it closes, the focus goes back to where it was before it opened, with the ring it had, if the focus is still inside the overlay or nowhere and that element still exists; overlays that close in the same frame give it back the newest first, so that a submenu returns it to its menu and the menu to its button. This happens before the looks are applied, so the focus look shows in the same frame, and in every build of the view, also between two inputs of one frame, so that a key right after the press that opened a menu goes to the menu. Tab walks a non-modal overlay right after its anchor and everything inside the anchor. Overlays attached inside the rows of a virtual list are placed and drawn but do not take or give back the focus; attach a row's menu to the list. Overlays under an anchor or ancestor the view makes invisible take no focus. An overlay that keeps the focus remembers the last place outside it at every move of the focus, also between two rebuilds. `El.keepFocus()` on an overlay opens it without moving the focus (a toast with Undo while the user types); when the keyboard has moved the focus into it and it closes, the focus goes back to where it last was outside it, and on any element makes a press inside it leave the focus where it is, also on focusable elements inside it, except in a text field (a menu bar's titles, so that the menu gives the focus back to the editor). `El.holdFocus()` makes an element hold the focus while the view marks it, as an overlay that opens and closes: the build that marks it moves the focus to it or its first focusable element, the one that unmarks it gives it back, and overlays inside it take it from it and give it back first (a menu bar from Alt or F10 until Escape).
- Keys: from the focused element up to the overlay's root, then on to its anchor and the anchor's ancestors, so that a handler of the menu's owner sees Escape. Escape closes nothing by itself: the overlay's own `onKey` calls the app. The root's handler sees what nobody before it took, which is where the kit's menu shortcuts are: a focused text field's editor takes its own keys (Control+C, Control+V, Control+Z, Control+Shift+Z, Control+A, Control+X, Control+Y, the arrows and the keys that type) before any ancestor sees them.
- The secondary button: `El.onSecondaryPress((x, y) -> ...)` runs when the right button goes down and up on the element or a descendant without such a handler, with the release's position in the window; it focuses as a press does and never drags or selects. `App.secondaryDown/secondaryUp` take it, `WindowLoop` passes the right button there, and the Menu key or Shift+F10 that no key handler takes run the nearest handler at the bottom left of the focused element's cursor: the first element inside it that is `current` (a grid's cursor cell), else the first that is `selected` (a tree's selected row), else the focused element, kept inside its box. That is how an element says where its cursor is: a component with a cursor marks it `current`, or `selected` where only one thing can be selected, as the grid, the tree and the menu do. Scripts write `press <target> right`.
- Delays on the app's clock: `.whenHoveredFor(seconds, look)` is a look that applies once the pointer has rested on the element (or inside it) that long, until it leaves or presses; it may attach an overlay, which is how a tooltip appears. `.onHoverFor(seconds, handler)` runs a handler once per stay (0: in the frame that finds the pointer there), which a menu uses to follow the pointer and to open a submenu after a delay. `.whenFocusVisibleFor(seconds, look)` is the keyboard's counterpart: a look once the element has had the focus with its ring that long, until the focus leaves or a key goes down that does not move it; a tooltip has both. `.onShownFor(seconds, handler)` runs a handler once an overlay has been open that long, once per opening (a toast closes itself), also one a delayed look attached and one in a row of a list, while its row exists; one the view makes invisible is not open, and one that an input closes and a later input of the same frame opens again opens anew. `App.nextChange()` reports when the next one is due, so an idle window wakes for it, and `frame()` returns false while it waits: no frames are presented. A press keeps the pointer's away until the pointer leaves and comes back, also when the pointer came in the frame of the press. `.cycle(seconds, (el, phase) -> …)` is a look without an end: in every frame while the element is shown it gets the phase, 0 towards 1, of a period of that length on the app's clock, counted from the frame in which the element got the cycle with its identity, so rebuilds and scrolling go on where it was; it runs after layout and motion, on the element as they left it, and may only `place` it (a piece laid out over its whole track draws a part of it), `fill` it and set its `opacity`, so no layout runs for it. While one is shown (not clipped away, outside the window, under an ancestor at opacity 0 or in a row that is not built), `isMoving()` and `frame()` are true and `nextChange()` is now, so a window draws one frame per refresh, also while inactive, and nothing while minimized, as for any motion; a window without one stays idle. A frame with cycles costs one more walk of the tree, without allocations, and their looks. An element with `motion` whose cycle a rebuild takes away springs from what the look showed last, so a bar that learns its value does not jump; `Headless.render` shows phase 0. `CycleTest`.
- `OverlayTest` checks placement (submenus going on the way the first flipped, tooltips beside an anchor they would cover, the window's edge), following and hiding, drawing order and clips, dismissing and dismiss groups, modality, focus and keys with `keepFocus` and `holdFocus`, the secondary button, the delays of the pointer, the keyboard and an overlay's time, presence and the dump without text; `WindowPartTest` the frame's parts under a modal overlay; `ScriptTest` runs `overlay.txt` against the stored images `overlay-*`; `GpuRendererTest` compares those and a menu with its submenu across the rounded clip of a scrolled list and a dialog over a scrim at scales 1, 1.5 and 2.

## What a table needs from core

The kit's data grid is built from these; any view may use them. `TableTest` checks each without text.

- Presses: `El.onPress((clicks, modifiers) -> …)` is told the modifiers held when the pointer went down (Shift adds a sort key); Enter and Space give `1, 0`. `El.onPress((clicks, modifiers, x, y) -> …)` is also told where the pointer was released, in the element's content as `Drag.x` and `y` are (the left and top of its border box as shown, plus its own scroll offset), so that a slider's track can put its knob there; Enter and Space give the middle of the border box. `onPointerDown` has the same form, with where the pointer went down. `El.onPointerDown((clicks, modifiers) -> …)` runs as the primary button goes down on the element or inside it, before anything moves, without making the element the target of the press or drag that follows, which may belong to an ancestor; a press on a scrollbar, in a text field or outside an open overlay runs none. `El.onAnyPointerDown(handler)` runs whenever a button of the pointer goes down anywhere in the window, while the element is in the tree or a shown overlay, before the press does anything else and taking nothing from it, also in a text field or on a scrollbar: the menu bar tells Alt alone from Alt held during a press by it. `El.onAnyKeyDown(key -> …)` is the same for keys: it gets every key that goes down, before any `onKey` handler or field, also one the focused element takes, and takes nothing from it (`AppTest`). `El.onPressOutside(handler)` runs, at the same moment and taking nothing from the press either, when a button goes down outside the element and everything inside it (an overlay attached inside it counts as outside): the grid's editor hands its value on there, and a press on another cell then selects that cell. These three hooks run also in the rows of a list, for every input of a frame, and not for an element that is leaving: a key that follows a rebuild between two inputs of a frame, which left the rows out, asks the lists' row functions whether a row has an `onAnyKeyDown` handler, without laying the rows out, and builds the rows only where one has (a burst of ten keys on a grid of 20 columns took about 0.1 to 0.3 ms more per key for it).
- `Drag` has `x` and `y`: where the pointer is in the dragged element's content, its border box as the last frame shows it plus its own scroll offset, doubles, so that a drag on a list of rows reads the row under the pointer also while the list scrolls. The wheel's scrolling of the frame that runs a step comes after it.
- `El.fixedX()` keeps an element in place sideways while the nearest scroll area around it that scrolls sideways (`scrollBoth`) scrolls, for drawing and input: frozen columns. It is drawn in tree order, so it comes after what it covers and needs a fill. `El.fix(root)` links such elements after each build, and a list links the rows it builds; inside a fixed element the area's offset counts once, so a fixed element in a fixed one stays with it.
- `El.rows(count, rowHeight, (index, from, to) -> row)` builds each row for the part in view sideways, from `from` to `to` in the content box, which is the visible part (clipped by the window and the ancestors that clip) widened by half its width on each side; scrolling sideways beyond that part builds the rows anew, without the view. The `IntFunction` form builds whole rows as before.
- `El.reveal(key, x, y, width, height)` keeps a rectangle of a scroll area's content in view whenever a rebuild gives it another `key` than the tree before, as `revealRow` does for a row's index: the grid keeps its cursor's column, or a dragged edge, in view without jumping back when nothing moved.
- `El.rows(count, heights, row)` is a virtual list whose rows are each as high as their content at the list's inner width (or their own height), the blocks of a long document: a `RowHeights` the app keeps in its state holds each row's height, estimated by a function of the index until the row is built, then measured by its layout, in a Fenwick tree, so that where a row starts, the row at an offset and the total cost a logarithm. When rows above the one at the top turn out higher or lower, the offset moves by as much, so that what is in view stays; a frame builds the rows again (at most three passes) when the measured heights show other rows than the estimate did, and what they still show after that the next frames build, for which `App.nextChange()` is the current time. The heights are kept by index: rows inserted or removed before others leave the measured heights where they were, until those rows are built again; an app that moves rows makes a new `RowHeights`. `App.scrollToRow` goes to where a row starts as far as the heights are known, and the list follows that row while rows built later turn out higher or lower, until the user's next press, key or wheel, or a `scrollTo`: a jump to a heading far down a document arrives there once the rows on the way are measured. `RowHeightsTest`.
- `El.scrollState(ScrollState)` keeps a scroll area's offsets (`scroll`, `scrollBoth`, `rows`, with `RowHeights` too) in an object of the app's state instead of by the area's identity, as `FieldState` does for a field: the area takes them from there in each build (`Animator.visit`, in place of the offsets of the tree before) and writes them there whenever they change (`El.scrollTo`), but only the element that took it last, so neither an older tree that still fades out nor the tree of the app the area left writes over them, whichever of two apps builds first. A `revealRow` or `reveal` the area had when it left counts as seen, so it comes back exactly where it was and not at its cursor. `ScrollState.scrollTo(x, y)` sets the offsets for the next build (the start, for a new result). Two areas of one build with one `ScrollState` throw when the view is built. `DataGrid.Selection` holds two (rows, and header with rows sideways), and `Tree.tree` and `NavList.navList` return their list, so `.scrollState(s)` chains onto them. `ScrollStateTest`.
- `El.onRowsBuilt((first, last) -> …)` tells the app which rows a list built, when they change, not on every rebuild; the handler runs after the input of the frame that built the rows, or in the next frame when the rebuild at its end built them, and `App.nextChange()` returns the current time while a handler waits. There is no thread-safe way yet to hand state from another thread to an `App` and wake its window.
- `El.onResize((width, height) -> …)` tells the app the size layout gave an element, in the first build that has it and when a rebuild changes it (`App.toldSizes`, by identity, before `animator.update` in `rebuild`, so never the sizes its motion passes through; an element that leaves is forgotten and told again when it comes back), as a `ResizeObserver` does, so that a view shows what fits: the kit's toolbar and breadcrumb move what has no room into a menu. It runs as `onRowsBuilt` does, and the view built from what it changed is laid out and may tell again, so a script needs a frame more before the view has settled. `App.handlersWaiting()` says that the next frame has such handlers to run; a `WindowLoop` that draws for the system's redraw during a live resize draws again while it holds (three times at most), since no other frame comes until the next step of the resize, and the toolbar showed each width a step late, its parts overlapping and coming back (`WindowLoopTest`). Not inside the rows of a list. `ResizeTest`.

## Work off the app's thread

An app, its state and its elements belong to the thread that runs it; `App` is not thread-safe, and only handlers change the state, in the order of the input. A query or a file that takes long runs on another thread, and its result comes back through `App.post(Runnable)`, the one method of `App` that any thread may call. It never blocks. The task joins the queue of input after the input that came before it, the tasks of one thread in their order, and runs on the app's thread as the handler of an input: against the tree the input before it left, and the view is built again before the next input, so a key, a task and a key each see what the one before left, and the frame draws. A task posted while a frame runs, by a handler too, waits for the next frame.

- `App.background(name, compute, onResult, onFailure)` runs `compute`, a `Callable`, on a virtual thread of its own (`Thread.ofVirtual()`, no pool) and posts `onResult` with its result or `onFailure` with its exception. It returns a `Work`: `work.cancel()`, called on the app's thread, keeps both handlers from running, also when the answer already waits in the queue, and interrupts the thread, so the answer of a request the user closed or asked again never arrives. The computation gets only what the handler put in its closure (names, an SQL string, a connection), never the state or elements: the app's thread reads them while it builds the view, and nothing guards them. An `Error` it throws is thrown on the app's thread. Virtual threads do not keep the JVM alive, so work that runs when `main` returns is dropped. The Javadoc of `post` shows the same with a thread of the app's own, in three lines.
- A `WindowLoop` wakes for tasks. It gives the app `Window::wake` with `App.onPost`, which the first post after the app took the ones before it calls: it pushes an SDL event of a type from `SDL_RegisterEvents` (`SDL_PushEvent` may be called on any thread), which ends `Window.waitEvents`. The tasks that arrived until the frame takes them run in that one frame, and a thread that posts nothing costs nothing. On Linux under X11, `WindowLoopTest` measured about 1 ms from a post to its frame; a burst of 1000 tasks that arrives while the loop draws is one frame, and one that arrives while it waits is one or two, as the first task wakes it before the last is there. A task that arrives less than a refresh after the last frame began waits for that refresh, as input does (see GPU renderer), also when it ends the wait for input early, and goes into that refresh's frame.
- Without a window (`Headless`, tests that call `frame()`) a task runs at the next `frame()`. A task that throws ends the frame as a handler that throws does: the exception comes out of `frame()` and the input after it waits for the next frame, which builds the view again before it, since the handler may have changed the state; a `WindowLoop` ends with it, and a script fails at its `frame` step. After the window has closed, tasks still queue; they run if the app runs frames again.
- Scripts and tests do not wait for the clock on the wall. `App.await(Duration)` waits until the work that `background` started has delivered or was cancelled, then queues what it and other threads posted for the next `frame()`; when work still runs after the timeout, it throws and names it. A script holds every posted task until its step `await`, so a snap shows "Loading…" and, after `await` and `frame`, the answer, however fast the work was. An app whose made-up work sleeps makes it immediate under a script: `Workbench.main` sets its latency to 0 before `Script.handle`.
- What happens later without another thread, a delay or a timeout on the app's clock, is `App.after(seconds, action)`. The action runs as a task does, in the first frame that begins at or after its time, after the input and tasks that came before that frame; `nextChange()` reports it, so an idle window wakes for it, a script runs it with `advance` and `frame`, and `await` does not wait for it. Its Javadoc has the rest; `Workbench` clears a message of its status line with it.
- `PostTest` checks the order of ten threads' tasks, the dispatch rule, cancellation, failures, idle frames and scripts, and `AppTest` the actions of `after` beside tasks and input and under a script; `WindowLoopTest` the wake-up, the frames of a burst and a task posted while input waits for the refresh in a real window; `TreeTest` the kit's tree with a catalog whose staging server answers on another thread.

## Several windows

One `WindowLoop` runs any number of windows on the windows' thread, each with an `App` of its own (view, focus, hover, scroll offsets, animations, clock) and a presenter of its own. `new WindowLoop(window, app, presenter)` and `WindowLoop.run(...)` run one window as before; more open with `loop.open(title, width, height, options, app)` or from a handler through `app.windows()`, a `Windows`, which the loop and a `Script` set on every app they run; an app that no runner runs gets one that refuses to open. `examples/.../Notes.java` shows all of it.

- `Windows.open(title, width, height, Window.options()..., app)` opens and shows a window that runs `app` and returns a `Windows.Handle`: `app()`, `title()`, `isOpen()`, `close()`, `raise()`, `moveTo(x, y)`, `x()`, `y()`, `width()`, `height()`, `screenScale()`, `onCloseRequest(handler)`, `dropTarget(on)` and `window()`, the `Window` for its taskbar button (null in a script). `Window.Options.position(x, y)` places a window where it opens. The loop makes the window's presenter with `loop.presenters(window -> ...)`, a `GpuPresenter` unless set, and gives the app its clipboard, fonts and itself, as to its first app. `Windows.all()` lists the open windows, `of(app)` finds an app's. The state holds the main `App` (as `Workbench` and `DataBrowser` do) and reaches the windows with `s.app.windows()`.
- Shared state: apps that show one state are made with the same state object, as `new App<>(notes, Notes::view)` and `new App<>(notes, s -> s.noteView(note))`. When a handler, a posted task, an action of `App.after` or an `onHoverFor` handler of one app ran (`App.ranHandlers()`), the runner calls `App.invalidate()` on the other apps whose `state()` is the same object, and they build their views again in the same pass: a press in one window shows in the others in the same frames. So does a task that the frame of a redraw runs (the system asks a window for one when it is exposed and while it is resized), outside a pass: the other windows of the state draw right after it. A pass builds a frame in each window whose input does not wait, then again in those another app invalidated, for up to three rounds; windows of other states are not touched, and an idle loop presents nothing in any window.
- Waiting and pacing: the loop waits once for all windows, for the earliest of the refreshes that a window's input waits for, the next frame of each window that moves (by its own display's refresh rate, which the loop reads at the start and again at `ScaleChanged` and `DisplayChanged`: SDL's `SDL_EVENT_WINDOW_DISPLAY_CHANGED` when the window moves to another display, and `SDL_EVENT_DISPLAY_CURRENT_MODE_CHANGED`, which every window gets; `WindowLoopTest` injects both), and the earliest `nextChange()` of all apps; for events alone when there is none. The hold-back is per window: input or a task that arrives less than a refresh after the last frame of its window began waits for that window's refresh, while another window draws at once. A post to any app wakes the loop once (`Window.wake`), and each app's tasks go into its next frame.
- Closing: `handle.close()` takes effect after the pass that runs: the loop presents nothing more there, closes the presenter (when it is `AutoCloseable`) and then the window. A window that a handler or its owner closed past the loop (`handle.window().close()`) has its presenter closed all the same, once, when the loop finds it closed. The loop ends when its last window closes, or with `stop()`; then it closes the windows it opened and leaves those given to it open for their owners. What a presenter's `close()` throws does not stop that: the loop closes every window and presenter it holds, and the rest of the windows whose close waited for the pass, and then throws the first failure with the others suppressed (or adds them to what ended the loop). A close request (the close button, Alt+F4, a script's `close`) runs the window's `onCloseRequest` handler as a task of its app; the handler closes the window, now or after a dialog, or vetoes by not closing it. Without a handler the request closes the window, or, when it is the loop's last, ends the loop and leaves the window open, as a loop of one window always did.
- The cursor: SDL has one for all windows. Each `Window` keeps the shape its app asked for last (`window.cursor(c)`, after each frame), and only the window the pointer is in, by its last move and leave, gives it to SDL, now or when the pointer enters it; while the pointer is in none, any may. Before, every frame set it, and the window drawn last won, whatever the pointer was over.
- Drags that know the screen: each `Drag` step also has `screenX`, `screenY` (the window's position plus the pointer's place in it, in the units of `Window.moveTo`), `outside` (the pointer is outside the window the drag began in), `window` (the `Windows.Handle` under the pointer, the drag's own included, or null) and `windowX`, `windowY` in that window. The window under the pointer is the topmost one whose content holds the point among those that are drop targets; since the system does not say which window lies on top, the loop keeps them in the order they last opened, were raised or took the keyboard focus. `Window.pointer()` reads the system's pointer (`SDL_GetGlobalMouseState`) where no event says where it is; drag steps take the event's place instead, which keeps them in the order of the input and lets tests inject events.
- Drop targets: `El.dragPayload(object)` on an element with `onDrag` makes its drags carry the object, and `El.onDrop(drop -> ...)` lets an element take it: `Drop.Phase.OVER` on each step while the pointer is over it or inside it (no element inside with a drop handler of its own), `LEAVE` when the pointer leaves, the drag ends elsewhere or is cancelled, and `DROP` at a release over it, with the payload and the point in its content. The element is hit tested, overlays first, in the tree its own window shows, in the drag's window or in another window of the runner, and its handler runs in the drag's frame before the drag's own step; its app builds its view again. The same handlers reorder within a window. A drag that carries a payload goes on when its element leaves the tree, with `x` and `y` NaN, since what moves is the payload: a card or tab torn out of its row.
- A window that follows the pointer: the drag's handler opens the window when `d.outside()` first holds, at `d.screenX()` less where the pointer holds the element times `screenScale()`, sets `dropTarget(false)` on it so that the windows under it stay findable, and moves it there on each step; at `END` it stays, or a drop handler of the row took the payload and closed it. SDL hands the pointer to a window that maps under it, also during a press, and on X11 its moves then come only while the pointer is over that window, and a release outside it is lost; the loop therefore gives what another window reports between a press and its release to the window the press began in, at the same point of the screen, and captures the pointer again (`SDL_CaptureMouse`). The keys that another window reports during a press go to the window the press began in too, so that Escape, which gives up a drag (`Drag.Phase.CANCEL`, and the release presses nothing), reaches the drag although the new window took the keyboard focus. A window the app moves during a press (`moved`) reports the pointer from where it has just moved to, while its position comes from the window manager a step late, and SDL drops each move that leaves the pointer where it was in that window, which is every move once it caught up: while such a window reports the pointer or is the pressed one, the loop takes the system's pointer (`Window.pointer()`) for the drag's place on the screen and reads it once per refresh until the release, also for the release itself, whose drop the next frame places (until the next press the window counts as moved), where positions are known (not on Wayland). Injected events into the pressed window alone, as tests send them, never start that. This was tried on X11 with a real pointer: the new window took the keyboard focus, the drag's moves and its release kept arriving, the window stayed exactly under the pointer, and Escape gave the drag up. On Windows, SDL captures the pointer for the window under it with `SetCapture` (SDL's source), so the same routing applies; it is not tried there.
- Platforms: on Windows and X11 a client places its windows anywhere and moves them; screen units are physical pixels and `screenScale()` is the window's scale. Wayland lets no client position a top-level window: `SDL_SetWindowPosition` moves only popups in SDL 3.4, `x()` and `y()` stay 0, and SDL 3.4 has no toplevel-drag protocol (`xdg-toplevel-drag-v1`, which would let the compositor move a window with the pointer). There a torn-off window opens where the compositor puts it and does not follow the pointer, and `Windows.place` finds no window but the drag's own, so a drop into another window cannot be detected; dropping back needs another gesture there, such as closing the window. The global pointer on Wayland is the pointer's place in the focused window. The session this was built on runs X11.
- Scripts: a `Script` is a runner too. The app it runs is the window `main`; a handler's `open` adds a window named by its title, at the position the options give or 32 pixels further than the last, at the first window's scale, with the first app's text rendering and clipboard, and posts held until `await` as for the first. `frame` runs a frame in every open window with the rounds of the loop, `advance` and `await` act on all apps, `snap` writes every open window, and `window`, `close`, `size … at x,y`, `screen x,y` and `in <window>` steer them (see the table above). A script that runs after another on the same app finds its windows.
- Tests: `SeveralWindowsTest` runs real windows through one loop: a press in one window shown in another in the same pass and nothing presented while idle, a handler that opens a window and one that closes all, which ends the loop, a vetoed close request, a drag from one window that is over and drops in another, a press whose pointer another window reports, pacing per window, posts to two apps and a post that a redraw runs, which the other window shows, a window closed past the loop, presenters that fail to close, the cursor of the window the pointer is in and a window shown without the focus, which starts inactive. `DropTest` checks drop handlers in one app without a runner, `WindowsScriptTest` tearing off, following, dropping back, shared state and close requests by scripts, and `NotesTest` the example's windows against stored images.
- Keeping windows reachable: a window the app moves during a press, as a torn-off tab's that follows the pointer, can be let go with its title bar above the top of the screen or beyond another edge, where nothing grabs it again. `Window.keepReachable()` moves a window so that its title bar (from `SDL_GetWindowBordersSize`), or for a frameless window the rows at its top that the view marks `WindowPart.DRAG` (`App.windowPart`, sampled every 8 pixels across and 2 down; the top 32 pixels where none is marked yet), lies in the work area (`SDL_GetDisplayUsableBounds`) of the display it is mostly on (`SDL_GetDisplayForRect`): wholly from top to bottom, the top first where the bar is higher than the area, and across for `Window.REACHABLE` (120) logical pixels or its whole width (`Window.reachable`, `EdgesTest`); not while maximized, minimized or fullscreen, nor on Wayland. It belongs to `Window`, which knows its frame, its drag area and the displays, and is public for an app that moves a window by itself; the `WindowLoop` calls it after the frame that handles a release for every window the app moved during that press or in that frame (`moved`, which a move in the frame of the release, as a drag's `END` step makes, now keeps), since only the loop knows both, so `TabGroups`, Notes and any app's own drags get it, and `Window.open` calls it for a window opened at a position (`Options.position`) outside every work area, as one remembered on a display that is gone. By hand on Windows: a torn-off Workbench tab let go at the top edge (its window at y -48) came back to y 0, one at the right edge (55 pixels on the screen) to 120 pixels on it. `WindowLoopTest` opens a window at -20000,-20000 and drags one above the screen with SDL events.
- Remembering where windows were: `window.placement()` is a `Window.Placement` (position of the content in screen units, size in logical pixels, whether it is maximized, the display's name from `SDL_GetDisplayName`): while maximized or minimized, the bounds it is restored to, which the window keeps from its moves and resizes while it is neither (`rememberNormal`, which on Windows also asks `IsZoomed` and `IsIconic`, since Windows moves and sizes a window it maximizes before SDL has the flag). It prints itself as one line, `120,80 1200x720 maximized display "DELL U2720Q"`, and `Placement.parse` reads it back and refuses anything else with what one looks like (`PlacementTest`); the library writes no file. `Window.Options.placement(p)` opens a window there: its size in place of the one given to `open`, maximized (before it shows) if it was, at most as large as the work area of the display it then lies on, wholly inside the nearest work area where it lies on no display (its display gone), and otherwise reachable (above). `WindowTest` opens from placements, maximizes and restores, and opens one 20000 pixels wide on a display that is gone. Workbench keeps the first window's in `%APPDATA%\rethinkj-ui-examples\Workbench\window.txt` (under `$XDG_CONFIG_HOME` or `~/.config` elsewhere), a choice of the example, written only by its `main` with a window, when the app ends (`quit` and after the loop), never under a script or a test.
- Tear-off tabs are built on this in the kit (`TabGroups`, see Kit). A window that opens under the pointer during a drag takes `Window.options().underPointer()`, which `TabGroups` and the Notes example set: it shows without the system's opening animation (on Windows `DWMWA_TRANSITIONS_FORCEDISABLED`, set in `Win32Shell.transitions` before it shows; before, with a device and a pipeline made per window, an empty dark frame zoomed in for about 220 ms and stayed empty about 360 ms in all) and without taking the keyboard focus (`SDL_HINT_WINDOW_ACTIVATE_WHEN_SHOWN` set to 0 while SDL shows it), so the window the drag began in keeps the keys and Escape gives the drag up as before (a window manager may focus it all the same, as GNOME's does on X11, where the loop's routing of a press's keys to the window it began in does that); the loop raises it, which gives it the focus, after the frame that handles the release, if it is still open (a drop that docks it closes it in that frame). With a real pointer on Windows 11 the window showed its first frame within one screenshot of about 17 ms after it appeared, the first window stayed in the foreground until the release, Escape closed the torn-off window and put the tab back, and after a release outside every bar the new window was in the foreground. `SeveralWindowsTest` checks the focus with a press that SDL events make. What core does not offer: the stacking order from the system, and on Wayland any of the screen.

## Kit

`kit` (`com.rethinkj.ui.kit`) holds components built on `core`: `Label.label`, `Icon.icon`, `Button.button`, `Toggle.toggle`, `Checkbox.checkbox`, `TextField.textField` (and `passwordField`, `revealable`, `textArea`, `codeArea`), `DataGrid.dataGrid`, `Split.split`, `Tabs.tabs` (with `TabGroups` for tabs in several windows), `Menu`, `MenuBar.menuBar`, `Tooltip.tooltip`, `Dialog.dialog`, `Select.select`, `ComboBox.comboBox` (and `free`) and `CommandPalette.palette` on the shared `FilterList` with its scoring `Fuzzy`, `Toast.toast`, `Card.card`, `Group.group` with its rows, `Section.section` and `page`, `Form.form`, `Divider.divider`, `NavList.navList`, `Radio.radioGroup`, `Segmented.segmented`, `NumberField.numberField`, `Slider.slider`, `Progress.bar` (and `indeterminate`, `line`, `labeled`, `spinner`), `Callout.callout`, `EmptyState.emptyState`, `CodeEditor.codeEditor` with the highlighter `Sql`, `Find.find`, `Completion.complete` and `Markdown.markdown` with its reader `MarkdownDocument`, `StatusBar.statusBar`, `Badge.badge`, `Popover.popover`, `Breadcrumb.breadcrumb`, `Toolbar.toolbar`, `Properties.properties`, `Avatar.avatar`, one file each. A component is a static function that returns an `El`, which the caller may chain further, as in `.key("save")`; there is no base class. `El.child` and `El.children` leave out a null, so `open ? part : null` composes anywhere.

- The look is layered: the window's background (`surface().window()`, also the title bar's) is a page on which each region lies as a card (`surface().panel()`, lifted by `elevation().card()`); a tab bar, a grid's header and a card's footer are quiet bands inside a card (`surface().band()`); controls and popups are `surface().raised()`. Hairlines of low contrast (`border().subtle()`) separate surfaces and rows; buttons and popups have the slightly stronger `border().control()`, fields and boxes the 3:1 `border().strong()`. Radii go by rank: cards `radius().large()` (10), controls `medium()` (6), small parts `small()` (4). The full accent fills primary buttons and what is on; its lighter `accent().edge()` draws lines and outlines: the focus ring, the active tab's line, the grid's cursor, a selected card's edge and a navigation list's mark. Selections in lists, the grid and menus are the calm tint `grid().selected()` with primary text. Headings are Inter SemiBold, strong text, column titles and buttons Inter Medium.
- The theme is `Theme`, a record of token groups: surfaces (with the band and the scrim under a modal dialog), text colours, borders, accent (with its edge), status colours, spacing, radii, type (with the headings `title` over a page, `heading` over a section or a card's toolbar and `strong` over a card; `Label.Variant` has all three), sizes, motion (with the delays of submenus and tooltips, the fade of popups and dialogs, and how long a toast stays), the data grid's, elevation, the shadows under cards, popups and dialogs, and code, the colours of an editor of code (keyword, string, number, comment, operator, and translucent backgrounds of the caret's line, of a bracket pair, of a find's matches and its current match, and of the occurrences of the word at the caret; `ThemeTest` holds the token colours to 4.5:1 on the field's raised surface, hovered, on the caret's line and on each of those backgrounds, and to 3:1 under the selection). A theme made with the constructor without code gets `Code.DARK` or `Code.LIGHT` by the lightness of its raised surface. The group caption is the red fill and white cross of a frameless window's own close button under the pointer, and its lighter red while pressed, as Windows 11 draws its own (`TitleBar`); a badge's colours are the group `badge`, and `danger` (`Theme.Danger`: fill, hover, pressed, the text on it, the red text of a quiet button, its edge and the focus ring of a button that destroys) the last, `Hue.RED`'s accent of the theme's lightness with the status colour as text; a constructor without a group gives the default of its lightness. `ThemeTest` holds its text 4.5:1 on each fill and its red text on the surfaces with hover and pressed, edge and ring 3:1 on the surfaces, and hover and pressed darker by 2 L* each. The comment above `Theme.DARK` states the rules the default themes follow, which `ThemeTest` checks. `Theme.DARK` and `Theme.LIGHT` are the neutral default; an app copies one and changes a group with `withAccent(...)` and the other `with` methods. They are written with the colours of `Palette`, named by hue and CIELAB L* times ten (`BLUE_496`, `GREY_083`: 37 greys and 59 colours of ten hues, opaque, the only colour literals of the kit), or one of them at an alpha (`alpha(GREY_298, 0.25f)`, the dark hover), so the source shows which tokens share a colour; a value that no rule makes from another is an entry of its own, also where it is close to another. `ThemeValuesTest` holds every value of both themes, and of the defaults the shorter constructors fill in, to `kit/src/test/resources/theme/values.txt`. `Theme.Hue` names accents: `theme.withAccent(Theme.Hue.VIOLET)` takes the hue's `dark()` or `light()` accent by the theme's lightness; `BLUE` is the default's, and `VIOLET`, `PURPLE`, `PINK`, `RED`, `ORANGE`, `AMBER`, `GREEN`, `TEAL` and `GREY` are made by one rule (in a dark theme the hue's avatar fill at L* 49, hover and pressed with 12 and 24 % less light by `Colors.mix` with black, which keeps the hue, the edge the hue's tone at L* 70; in a light theme the dark accent with 25 % less light, its own edge). `ThemeTest` runs its contrast rules for each hue in both themes and checks that hover and pressed each darken by 2 L* or more. Only the accent changes: the grid's selection, links, the tint of a changed cell and a badge's accent stay blue. Fonts are `Supplier<Font>`, so that making or reading a theme loads no native library; the defaults need `rethinkj-ui-fonts`.
- A component takes the theme as its first parameter, `button(theme, PRIMARY, "Run", onRun)`. The view gets it from the app's state or a constant. There is no global or per-thread theme: a view says what it draws with, and two themes can be on screen at once, as in the gallery. Every focusable component draws its focus ring in `theme.accent().edge()` (`El.focusRing`), a primary button, whose fill is the accent, `size().ringGap()` (2) away from it (`El.focusRingGap`), so that the surface behind it shows between fill and ring; a view that switches its theme switches the ring with it. `Theme.over` mixes an overlay into a surface in linear light, as the renderer blends a translucent fill, so the hover and pressed overlays give one colour whether a component fills with the mixed colour or draws them translucent.
- Components read only tokens: no colour, size or spring of their own. `TokenTest` fails on a colour literal (eight hex digits, `rgb(0x…)` or `hex("…")`) in any file of the package but `Palette.java`, and on a `Spring` constant or a `new Shadow(` in any but `Theme.java`. A component that needs a new value gets a new token, with a value in both themes; `ThemeTest` checks the default themes: contrast (WCAG AA, 4.5:1 for text on every background it is used on, 3:1 for the strong border, the accent's edge and the focus ring, disabled text between 2.5:1 and 3.5:1), hover 4 L* and pressed 3 L* more from each surface, an inactive selection apart from a hovered row, and shadows stronger and tighter in the dark theme.
- A null handler disables a component: it takes no focus, shows no pointer cursor and draws in the disabled colours, a press on it goes to its ancestors, and its line in a `.tree.txt` says `disabled`.

The detail (`detail(node)`, asked only for the rows built) is muted text `space().s()` after the label, such as a column's type or a schema's number of tables, and the row's `value` in a dump; where the row is narrow it gives way first, as a grid header's type does: label and detail lie in a box that wraps and clips at the row's height (a zero-width strut as high as the row first, so both sit in the middle of the first line), the label `shrink(0)` and at most the box's width, the detail growing from a basis of its first character and an ellipsis, so it ends in an ellipsis, then wraps to the second line, which the box clips away, before the label is cut at all. The tooltip that then names both is a `whenHoveredFor` look of the row that reads the layout (rows' looks run after it), since `Tooltip.whenShortened` sees cut text but not a detail wrapped away. Rows without a detail are built as before. It owns which nodes are open and which is selected; the tree reports a selection (only a change), a node to open or close (`Tree.Toggle`), and an activation. A press selects, a press on the mark (the icons `Tree.CLOSED` and `Tree.OPEN`, chevrons, which need `rethinkj-ui-icons`) selects and opens or closes, a double press opens or closes and activates (it reads the count from `El.onPress(IntConsumer)`); with the focus, Up, Down, Home, End, Page Up and Page Down move, Right opens and then goes to the first child, Left closes and then goes to the parent, Enter activates. The rows follow the selection (`revealRow`), and whenever nodes open or close the tree also scrolls the selected node's children into view below it, as far as its height allows with the node in view (`El.reveal` keyed by the number of rows), so a node opened at the bottom shows what it holds. A secondary press on a row selects it and then runs the tree's own `onSecondaryPress` handler, so that a `Menu.contextMenu` on the tree acts on the row it opened on. Each rebuild of the view walks the open nodes from the roots to number the rows, in proportion to the nodes shown (`TreeTest` prints it: about 1.3 ms for 100 000), and the rows are an `El.rows` list, so scrolling builds rows, never the view. An open node whose children are null shows one muted loading row; the app starts the load in `onToggle` and changes its state when the data is there. Rows are rounded (`radius().medium()`), so a tree in `Card.inset` shows its selection and hover as a tinted row inside the card's padding. Rows are `role=treeitem` with the node's label and the key `row-<index>`, marks have the key `mark-<index>`; each row says its level, whether it is open and its position among its siblings as states (`expanded level=2 pos=1/3`), which costs two more ints per node shown in the walk. Its tokens are the grid's row height and selection colours, `space().xl()` per level and `surface().hover()` over the rows. `TreeTest` runs `kit/src/test/resources/scripts/tree.txt` against `Catalog`, three servers with a schema of 300 tables, in both themes, and compares the snaps with `golden/tree-<dark|light>-<snap>.png`.

- `Find.find(theme, app, field, state)` gives a multi-line field a find bar, as `Completion.complete` gives completions: the app keeps a `Find.State` (in a `CodeEditor.State` already), and the component wraps the field's key, selection and decorator handlers. The bar is an overlay over the top right corner of the field (`side(TOP, END, -height)`), clear of its scrollbar, on the raised surface with the control border and `elevation().popup()`: a floating bar rather than a row above the text, since a row pushes the text, and in the Workbench the grid under it, down by its height whenever it opens, while the corner it covers is mostly empty in code, whose lines are short. It holds the field to find (`label="Find"`, with the switches Match case, Whole word and Regular expression inside its frame), the count (`#count`: `3 of 17`, `17 results` while the selection is no match, `No results`, `10000+` beyond `Find.LIMIT`, `Searching…` while another thread counts, `Too slow`), Find in selection, Previous match, Next match and Close; with Control+H a second row with the replacement (`label="Replace"`), Replace and Replace all, never in a read-only field; with Control+G the field of the line to go to (`label="Go to line"`, `42` or `42:7`, `1 to <lines>` beside it). `role=search`, the switches `role=button` with `checked` (core has no `pressed`), each with a tooltip that names its key. The bar's buttons keep the focus in its fields; Tab in the field to find goes to the replacement while that shows, and Shift+Tab there back, and otherwise Tab goes through the bar; as an overlay it comes after the field in the order of Tab. Every match in view has `code().match()` behind it, the current one `code().current()` and a line in `accent().edge()` under it, which tells it apart where the contrast of the text allows little difference of background; Find in selection has `code().line()` behind the lines it keeps to. `Search` (package-private, no native libraries) makes the query a `Pattern` (Unicode's simple case folding: `ä` finds `Ä`, `ß` finds `ẞ` but not `SS`), never matches empty, never begins or ends inside a grapheme (asking `BreakIterator` only where the characters are not below U+0300, from the last boundary it knows, as regional indicators pair up from the start of their run), and reads the text through a `CharSequence` that throws past a deadline, so a regular expression that backtracks without end stops, and one that recurses too deep for the stack (`(a|b)+` on 20 000 `a`) stops as too slow. Replacing checks a match, and expands its groups, within the same bounds as the search. A text of up to `Find.SYNC_CHARS` (200 000) characters is searched whole on the app's thread (a few milliseconds); a longer one searches the lines in view at once and the whole on another thread (`App.background`), which a new query or text cancels, and a jump that takes more than 10 ms goes there too, which a change of the text cancels. Links hold no links: after a link or an autolink the brackets around it are text. Reference labels compare by case folding (`ẞ` finds `SS`). - `FilterList` is what `ComboBox` and `CommandPalette` share: a list of `FilterList.Entry`s (text, optional `Symbol` before it, muted detail and shortcut at the right, a group, and the handler, null for a disabled entry; `FilterList.entry(text, onChoose).symbol(...).detail(...)`) filtered by a typed text. `FilterList.Entries.of(list)` lets the kit filter with `Fuzzy` (all entries in their order while nothing is typed, else the matches best first within their groups, the groups in the order of their first entries; of matches alike the shorter text first, or with `Entries.inOrder(list)` the earlier one, as the palette's commands have it, where `fi` would otherwise put `File: Exit` first; the app passes the same list while it does not change, as the filter keeps by its identity what it lowered and matched), `Entries.by(text -> entries)` is the app's own finding on its thread, shown in order, and `Entries.background(app, name, text -> entries)` the same on another thread (`App.background`): the entries found for the text before stay with a row "Loading…" until the answer, a new text cancels the work before, and closing the list cancels it too. - `Fuzzy` scores a query against a text, as editors' quick open does, without native libraries: the query's characters in order; 16 per matched character, a bonus at the start of a word (10 at the start or after a space, 9 after `. _ - / \ : , ;`, 7 for camelCase's capital or a digit after a letter, twice that for the query's first character), 6 for a character right after the one before, and a gap costs 3 and 1 per further character; the best alignment counts (a dynamic programme over query and text), `Fuzzy.positions` gives its characters. - `Format<T>` (no native libraries, `FormatTest`) writes a value as text (`text`) and reads a text into a value or a message that says what a valid text looks like (`parse`, a `Format.Parsed`), and says whether typing may lead from a text to a valid one (`allows`: false for `12a`, true for `12.` and `-`). `TEXT`, `INTEGER`, `LONG`, `BIG_INTEGER`, `DECIMAL` (`BigDecimal`, the text's scale, written plain, so an exponent that would write more than `Format.MAX_ZEROS` (4096) zeros is refused by `parse` and `allows`), `DATE`, `TIME`, `DATE_TIME` (a space or `T`; refuses an offset, which `LocalDateTime` would drop), `OFFSET_DATE_TIME`, `BOOLEAN`, `BYTES` (a `Long` size in SI's decimal units, `817 B`, `1.2 MB`, `12 MB`: one decimal below 10 of a unit, none from 10 on, half up, never 1000 of a unit; reads its own texts back to the bytes they say, so not exactly the value written, also plain bytes, `KiB` to `EiB` and the unit's letters in any case; negative sizes and sizes beyond `long` are refused; `type()` is `INTEGER`, so a typed column aligns right, sorts by the bytes and its editor parses as the format does, `GridTableTest`), `choice(list, label)` (exact labels, unique: two values that differ with one label throw an `IllegalArgumentException` naming the label and both; `choices()` lists them; enums as `List.of(E.values())`, as the typed choices take them) and `of(text, parse, message)` (a parser that throws or returns null fails with the message); `.optional()` reads the empty text as null, else it is `Format.REQUIRED` ("A value is required"), but `TEXT`'s is the empty string; `.where(test, message)` narrows. ## Native libraries

The window (SDL3), the GPU renderer (wgpu-native) and text (HarfBuzz shapes, FreeType rasterises) will call native libraries. They reach users in one JAR per platform, `rethinkj-ui-natives-<platform>`, where the platform is `windows-x64` or `linux-x64`. Both hold SDL 3.4.20, wgpu-native 29.0.1.1, FreeType 2.15.0 and HarfBuzz 15.1.0. FreeType and HarfBuzz are built from the same source archives with the same options on both platforms, without dependencies beyond the C runtime: on Linux HarfBuzz needs no libstdc++, and on Windows both link the C runtime statically and need only `KERNEL32.dll`.

- The JAR has no Java code. Under `META-INF/rethinkj-ui/natives/<platform>/` it holds the libraries, `manifest.txt` and the licence texts in `licenses/`. `manifest.txt` lists the libraries in load order, one line each: `library <name> <version> <file> <sha256>`, after the lines `rethinkj-ui-natives 1` (the format) and `platform <platform>`. A library built from source is followed by `built <name> <sha256 of the source archive>`, because its own hash differs between machines. `com.rethinkj.ui.natives.Manifest` reads it, ignores `built` and documents the format.
- No binaries are committed. `natives-<platform>/natives.properties` pins each library: version, archive URL, the archive's SHA-256 and the file inside it. `scripts/FetchNatives.java` (run with `java scripts/FetchNatives.java natives-windows-x64`; it needs only the JDK) downloads the archives into `natives-<platform>/fetched/archives/`, checks their hashes, and unpacks the libraries and writes `manifest.txt` into `natives-<platform>/fetched/resources/`, which the module packages. The module's build runs it in `generate-resources`; it does nothing while `fetched/` matches `natives.properties`. `fetched/` is ignored by git and survives `mvn clean`; delete it to fetch again. Offline, put the archive at the path the error message names.
- A library with a `<name>.cmake` line (on Linux every library but wgpu-native, on Windows FreeType and HarfBuzz) comes from a source archive, a `.zip` or a `.tar.xz`: the tool builds it with cmake in `fetched/builds/<name>/`, on Linux with make, and reuses that build while archive, options and entry stay the same. It fails if cmake turns off an option the line sets `ON`, such as `SDL_X11` or `SDL_WAYLAND` when their development files are missing.
- On Windows the tool builds with Visual Studio 2022 or later, or its Build Tools, and needs nothing on the PATH. It takes the installation of the developer prompt it runs in (`VSINSTALLDIR`), else the newest one with the C++ x64 tools that `vswhere.exe` finds (one that also has Visual Studio's CMake first), and runs every command in the environment that its `VsDevCmd.bat -arch=amd64` sets up. cmake is the file the environment variable `CMAKE` names, else the first `cmake.exe` on that environment's PATH, where Visual Studio's own (the component "C++ CMake tools for Windows") comes before the user's PATH. The generator is the Ninja that the same component brings, else NMake: FreeType and HarfBuzz take about 70 s with Ninja and about three minutes with NMake. Windows' `tar.exe` reads `.tar.xz` but cannot make a symbolic link without a privilege, so the tool has it rewrite the archive as a zip and unpacks that; a link becomes a file holding its target, as Git makes links where it cannot. The libraries link the C runtime statically (`CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded`), because `VCRUNTIME140.dll` comes with the Visual C++ Redistributable, not with Windows.
- A fresh Windows machine needs Visual Studio or its Build Tools with the workload "Desktop development with C++", whose defaults include the x64 tools, a Windows SDK and "C++ CMake tools for Windows"; nothing else needs installing or setting. Where cmake is missing, the build stops with a message that says what to do; it does not download CMake itself. The fix is needed once, as later builds reuse `fetched/builds/`, and the build cannot get Visual Studio by itself either. Without installing anything, unpack the Windows x64 ZIP from cmake.org anywhere and build once with `$env:CMAKE = '<folder>\bin\cmake.exe'`. An agent working unattended does that, or builds with `-P '!natives-windows-x64'` when it needs no native libraries.
- A Linux library is packaged under its SONAME (`libSDL3.so.0`), so that a library that needs it finds the loaded copy; the tool checks that. HarfBuzz's CMake build gives it the SONAME `libharfbuzz.so`, without the `.0` of its Meson build.
- To change a version, edit `natives.properties`, build, and update the licence texts under `natives-<platform>/src/main/resources` if the release changed them.
- A natives module is built only on its own platform: the root `pom.xml` lists it in a profile of the same name, activated by the operating system and architecture, and `core` has a profile with that id that adds it as a test dependency.
- `com.rethinkj.ui.natives.Natives.lookup("sdl3")` returns a `SymbolLookup`, loading the library and every library listed before it on first use. The package is internal to `core`. It finds the manifest of the current platform on the class path and unpacks the libraries into a per-user cache, `%LOCALAPPDATA%\rethinkj-ui\natives\` on Windows and `$XDG_CACHE_HOME/rethinkj-ui/natives/` (default `~/.cache`) on Linux, in a subfolder named after their hashes. Two system properties change that:
  - `rethinkj.ui.natives.dir`: load from this folder, which holds the libraries and their `manifest.txt` as the JAR has them. Nothing is unpacked or hash-checked, and the class path is not read. For packaged apps and GraalVM native image.
  - `rethinkj.ui.natives.cache`: unpack into this folder instead. Core's tests set it to `core/target/natives-cache`.
- Native access must be enabled for core: `--enable-native-access=com.rethinkj.ui` (core's tests pass it). On the module path, the natives JAR is resolved only with `--add-modules com.rethinkj.ui.natives.<os>.x64`.
- Loading happens only on first use. Never call `Natives` from a static initialiser that the headless path can reach: rendering without a window must not need the libraries.
- Linux cannot load a library from a file system mounted `noexec`; then the cache has to move. On Linux, a failed load reports the dynamic linker's reason, which the JDK leaves out.
- On Windows a library is loaded with `LoadLibraryExW` and its symbols found with `GetProcAddress` (`Natives.Kernel32`): `SymbolLookup.libraryLookup(Path, …)` hands the path to Windows in the ANSI code page and failed, on JDK 25.0.5 under code page 1252, for a cache in a folder named in Japanese, as a user profile may be. A failed load reports Windows' error code and its text, such as 193 for a damaged file. `NativesLoadTest` loads from folders named in Japanese, in Cyrillic and with spaces.
- The libraries built for Linux need the glibc of the machine that built them (2.38 on Ubuntu 24.04, for SDL and FreeType), and SDL lacks what that machine had no headers for (IBus, libdecor). A build on an older distribution does not exist yet.

## GPU bindings

`com.rethinkj.ui.gpu` (internal to `core`) binds wgpu-native in two layers. `Wgpu` and `Structs` are the raw layer: constants, function and callback descriptors, struct layouts written by hand and the header's `*_INIT` defaults (zero is not always the default). Everything else is the safe layer, which the renderer uses; renderer code never sees a handle or a `MemorySegment` of wgpu.

wgpu-native ends the process where WebGPU would report an error, so the safe layer has to keep these from happening:

- Every call that can fail runs inside a validation and an out-of-memory error scope and throws `GpuException` with wgpu's text and the label. A command encoder keeps its scopes open until `finish`, which throws instead of handing out a command buffer that recorded an error. Push and pop scopes only through `Device`: popping one too many ends the process, and so does the `Internal` filter.
- Every device gets the uncaptured-error and device-lost callbacks. Upcalls catch everything and hand it to the calling code. The stubs live in `Callbacks` for the process and find their target by an id in `userdata1`.
- Check arguments that wgpu-native panics on before calling: sizes of 0, a second surface texture while one is held, a buffer still mapped when commands using it are submitted, a command buffer submitted twice, NULL handles, a bind group entry with neither buffer nor view, a texture entry of a bind group layout without a view dimension (WebGPU would take 2D, wgpu-native panics), a texel copy with 0 bytes per row or rows per image, an offset and a size that overflow a long when added (checked as `size > limit - offset`).
- Do not bind any of the 35 functions wgpu-native leaves unimplemented (`WgpuTest` lists them), and do not rely on `wgpuInstanceWaitAny`: callbacks run inside the call or inside `wgpuDevicePoll`.
- Textures for shaders to read: `Device.createTexture` makes a 2D texture, `createTextureArray` an array of layers whose views are always 2D arrays, even of one layer. `BindGroupLayout.Entry.texture` and `textureArray` (`texture_2d<f32>`, `texture_2d_array<f32>`) bind a view that the shader reads with `textureLoad`, without a sampler: the sample type is unfilterable float, which takes every float format, `R8_UNORM` among them. `BindGroup.Entry.texture` binds the view. `Queue.writeTexture` writes a rectangle of texels into one layer from memory, rows `bytesPerRow` apart from an offset, so a region of a larger image goes without copying it out first; unlike a copy between buffer and texture, the rows need no alignment of 256. `Device.createTexture(label, width, height, levels, format, usages...)` makes a 2D texture with mip levels (level `k` is `max(1, size >> k)`, checked against the most the size allows before wgpu sees it), its views hold all levels for `textureLoad(texture, texel, level)`, and `Queue.writeTexture(texture, level, ...)` writes into one. They set the fields `mipLevelCount` of `WGPUTextureDescriptor` and `mipLevel` of `WGPUTexelCopyTextureInfo`, which the layouts already had; no struct, function or callback is new.

Objects belong to the thread that created their `Instance`; closing one closes what it created, newest first. `Device.created()` and `RenderPipeline.created()` count the devices and pipelines the process made, for tests that check what windows share (see GPU renderer). A lost device cannot be produced for a test: `wgpuDeviceDestroy` ends the process on Direct3D 12 with an uncaught exception of the driver, before any callback, so it is not bound, and the package-private `Device.lose(text)` (through `DeviceLoss` in the tests) marks a device lost as the device-lost callback does. After adding or changing a struct, function or callback, run `scripts/LayoutCheck.java` (its header has the commands; it needs jextract, which stays out of the repository).

## Colours

A colour is an `int`, 0xAARRGGBB in 8-bit sRGB with straight alpha, everywhere (`El.fill`, `color`, `border`, `Shadow`, the kit's theme). `Colors` (`com.rethinkj.ui`, no native libraries) writes, reads and mixes them, in one place for the whole project: `rgb(0x3D6FE6)`, `rgb(r, g, b)`, `argb(a, r, g, b)`, `alpha(argb, share)` (`round(share * 255)`, halves up: 0.4 is 0x66, 0.35 is 0x59), `hex("#3D6FE6")` and `hex("#663D6FE6")` with a message that says what a colour looks like, `toHex`, `BLACK`, `WHITE`, `TRANSPARENT`; `alpha(argb)`, `red`, `green`, `blue`; `over(base, overlay)` (in linear light as the renderers blend; `Theme.over` calls it), `mix(a, b, t)`, `luminance` and `contrast` (WCAG's), `lightness` (CIELAB's L*), and `linear` and `srgb` for one channel, with `StrictMath`. `Scene`'s table of linear values, `Image`'s levels and `CpuRenderer`'s encoding use `linear` and `srgb`; `Scene` keeps its own float luminance and the L* it biases text by, whose bits the renderers' text depends on. `ColorsTest` checks that each calculation that stood in several places gives the same bits as before (the kit's tests and the examples used `Math.pow` and `Math.cbrt`, which differ from `StrictMath` in the last bits for about a fifth of colours, by less than 1e-12). `ReferenceCpuRenderer` and the WGSL keep their own, as references.

## Text

Text is shaped with HarfBuzz, rasterised with FreeType into greyscale bitmaps and drawn by `CpuRenderer` and `GpuRenderer`.

- `El.text("…")` makes a text element, a leaf that layout sizes to its shaped text. Chained calls: `.font(Font)`, `.fontSize(<logical pixels>)`, `.color(0xAARRGGBB)`, `.wrapText()`, `.ellipsis()`, `.fontFeatures("+calt")`, `.textAlign(Style.Align.CENTER)` (or `END`: each line in its box, on the grid of glyph positions, also a line shortened with an ellipsis; not in fields, which scroll; `Text.Line.x()` says where a line starts; `TextRenderTest` stores `text-align-<1|2>x`), `.highlight(key, highlighter)` (see Text fields), and `.editable(onEdit)` for a text field, with `.multiline()` one of several lines (see Text fields). With `.ellipsis()` a line wider than its box ends in `…` (`Text.ELLIPSIS`): as many graphemes as fit, without the spaces before it, shaped anew with the ellipsis; layout sizes the text as before, so the element needs a width or `minSize(0, 0)` to shrink below its text, as a table's cells have. `Text.shortened()` says whether a line was shortened; the tree dump keeps the whole string, and a right-to-left run is cut before it, not inside it. `TextRenderTest` stores `text-ellipsis-<1|2>x`, and `GpuRendererTest` compares them. The defaults are `Font.sans()`, 14, opaque black and no wrapping. Each line feed starts a line; with `wrapText` it also breaks where `java.text.BreakIterator` allows, and a word wider than the box stays whole. Characters the font lacks come from fallback fonts (below); a character no font has shows as the first font's glyph 0.
- `Font.sans()`, `sansMedium()`, `sansSemibold()`, `sansBold()`, `sansItalic()`, `sansBoldItalic()`, `mono()` and `monoBold()` are Inter 4.1 (regular, medium, semibold, bold, italic and bold italic) and JetBrains Mono 2.304 (regular and bold), the static hinted TrueType files of their releases. They come in `fonts/` (`rethinkj-ui-fonts`, under `META-INF/rethinkj-ui/fonts/` with their SIL Open Font License 1.1 texts in `licenses/`); `core` uses that module only in tests, and without it these methods throw a message that names it. Other fonts: `Font.of(bytes)` or `Font.resource(owner, name)`, freed by `close()`.
- `Font.icons()` is Fluent UI System Icons Regular (MIT), the TrueType file the project publishes at its tag 1.1.345, unchanged: 2.9 MB, in `icons/` (`rethinkj-ui-icons`, under `META-INF/rethinkj-ui/icons/` with its licence in `licenses/`), loaded like the default fonts. An icon is a glyph at a private-use code point, drawn anew for some of 12, 16, 20, 24, 28, 32 and 48 pixels, each drawing at its own code point and sharp at its size. Two things set this font apart (`Font.wholePixels()`): its line is the em square, which the drawings fill, so an icon is as high as its font size (the font asks for a line gap of 0.09, which would put it a pixel low in a box a pixel too high), and its glyphs sit on whole physical pixels at every scale, also where text would use quarter pixels, so a 16-pixel drawing at scale 2 keeps strokes of two whole pixels in a box scrolled by a fraction. Icons are hinted alike under every `TextRendering`, with FreeType's auto-hinter in both directions (`Font.ICON_HINTING`), which puts the straight strokes it finds on whole pixels: the light auto-hinter that `LINUX` uses for text moves outlines vertically only and left an arrow's shaft at 16 pixels and scale 1 across two rows of pixels, 29 and 72 % covered, where the auto-hinter fills one row. A drawing whose strokes lie between two pixels in its design, such as `ADD` at 16, stays half covered under any hinting. At scale 1.5 the 16-pixel drawings have strokes of 1.5 pixels, which no position makes sharp.
- `Font.shape(text, size, scale, features...)` shapes with HarfBuzz into a `GlyphRun` in physical pixels: at `size * scale`, advances and offsets rounded to whole pixels below scale 1.5 and to quarter pixels from 1.5 on. Kerning is on and `calt` off (JetBrains Mono's ligatures); features use HarfBuzz's syntax, such as `"+calt"` or `"-kern"`. Each font keeps the last 1024 runs.
- Fallback fonts: `font.withFallback(Font...)` is a font that falls back to those fonts in order, `font.withSystemFonts()` one that then falls back to the fonts installed on the system; both are the same object for the same arguments, own no native objects, and keep the first font's metrics, so the line height stays its own. `Runs` splits the text into runs of one font and one script, without native libraries: each grapheme cluster (`BreakIterator.getCharacterInstance`: a letter with its marks, an emoji sequence, a flag, a variation selector with its base) goes to the first font that has all its characters but joiners, variation selectors, format and control characters (or all of its NFC form), else to the first font; neutrals (scripts Common and Inherited: spaces, punctuation, digits) the first font has stay with the font of the clusters on both sides when that is one font that has them. Each run is shaped on its own with HarfBuzz, in its script (`hb_buffer_guess_segment_properties` on the run alone) and direction, with the whole string as context, at the element's size, and the runs follow each other on one baseline in the order of the string. A glyph's font is `GlyphRun.font(i)`, which the scene passes to the atlas; the renderers did not change.
- Right to left: a run of Arabic, Hebrew and other right-to-left scripts is shaped right to left, so its letters join and stand in their order, and a neutral is right to left only between two right-to-left letters, not next to a number, whose digits stay left to right. Lines are not reordered by the bidirectional algorithm: runs follow each other from left to right. A right-to-left run is one cluster (every glyph at its first character), so a line does not break inside it (lines break only where a cluster starts, also in ligatures), and in a field the caret moves through it from its left edge in proportion to its graphemes.
- The system's fonts (`text.SystemFonts`, through FreeType, without fontconfig or DirectWrite): the first cluster that no font of a chain has walks `/usr/share/fonts`, `/usr/local/share/fonts`, `$XDG_DATA_HOME/fonts` (or `~/.local/share/fonts`) and `~/.fonts` on Linux, `%WINDIR%\Fonts` and `%LOCALAPPDATA%\Microsoft\Windows\Fonts` on Windows, maps each `.ttf`, `.otf`, `.ttc` and `.otc` in turn and keeps each face's family, style and characters as ranges; it runs once per process, and the lookups are kept. Faces without outlines are left out (CBDT, COLR version 1). A cluster gets the first face with all its characters by the platform's preferred families for its script (Linux: Noto Sans, Noto Sans Symbols and Symbols 2, the Noto Sans family of the script, such as Noto Sans Arabic, DejaVu Sans, Noto Emoji, Symbola; Windows: Segoe UI, Segoe UI Symbol, Segoe UI Emoji, Leelawadee UI, Nirmala UI, Segoe UI Historic; emoji first to the emoji families), then the style nearest the text's font. The CJK families (Noto Sans CJK, or Yu Gothic UI, Microsoft YaHei UI, Microsoft JhengHei UI and Malgun Gothic) come first for Han, kana and Hangul, ordered by `Locale.getDefault()` (Japanese for other languages), with Korean first for Hangul and Japanese for kana. Private-use and unassigned characters are never looked up. A chosen face is mapped and opened as a `Font` for the process; the others are unmapped after the scan. On a Linux desktop with 408 font files in the file cache, the scan takes 0.15 to 0.25 s in a fresh process (up to 0.45 s while tests run beside it), and the index holds about 0.75 MB; on Windows 11 with 145 files it takes 0.2 s with the files in the cache and 1.1 s without, and holds 0.66 MB. So that no frame waits for it, `App.systemFonts(true)`, which a `WindowLoop` calls when it starts, begins the scan on a virtual thread (`Font.prepareSystemFonts`); a lookup before it ends waits for the rest. In a window on Windows that took the first Japanese character typed from 139 ms to 12 ms between the key and its frame.
- `App.systemFonts(boolean)` switches system fallback for the app's text; it is off, so scripts, `Headless` and tests draw the same everywhere and never scan, and a `WindowLoop` turns it on when it starts unless `loop.systemFonts(false)`. Stored images use only explicit chains: `Examples.fallbackChain()` is Inter with JetBrains Mono (its box drawing and maths), Noto Sans Hebrew and Noto Sans Thai, small OFL fonts in `core/src/test/resources/fonts`.
- Colour: glyphs are coverage in one colour, so a colour font draws only where its glyphs have outlines, in the text colour (the base glyphs of COLR version 0, as in Segoe UI Emoji, whose COLR table on Windows 11 is version 1 with version 0's records and outlines for its base glyphs; monochrome fonts such as Noto Emoji or DejaVu Sans). This FreeType has COLR layers but no PNG, so CBDT bitmaps (Noto Color Emoji) fail to load (error 7) and are left out; COLR version 1 needs a painter of its own and SVG glyphs a renderer. Colour emoji would need an RGBA atlas and a third kind of instance besides that.
- `App` and `Headless` pass the window's scale, and `App` whether to use the system's fonts, to every text element before layout (`El.scaleText`); `Flex.layout` alone shapes at scale 1. After layout, `el.text().lines()` holds what a renderer draws: per line a `GlyphRun`, its width and its baseline, in physical pixels from the top left of the content box. Layout hands the final content size to `Measure.placed`, and the lines are broken for that width.
- In a `.tree.txt`, a text element's line starts with `text` instead of `el` and has its string in quotes after the key, role and label: `text #save "Save\nall" 0,0 32x36`. Strings and labels are quoted with `\"`, `\\`, `\n` for a line feed, `\t` for a tab and `\u{E0EB}` for a character of a private use area, such as an icon, which would otherwise show as nothing or a box. A string longer than 200 UTF-16 units shows its first 100 and its last 40, each quoted, with `…` between them and its length after them: `text #query "SELECT …" … "… 1;" length 104857`. The selector `text="<string>"` matches the exact string, written the same way, so it finds a short multi-line field but not a long one, which a key or a role finds.
- `Scene` turns the glyphs of each line into glyph instances, `KIND` 1, in the same list as the rectangles (`KIND` 0), so text and boxes overlap in tree order. Their 64 bytes (of an instance's 96), the WGSL struct and the coverage formula are in `Scene`'s Javadoc; `CpuRenderer` is the reference. A glyph's bitmap is drawn one texel to one physical pixel, never resampled: the content box of a text element is snapped to the grid of the glyph positions, whole pixels vertically and, horizontally, whole pixels below scale 1.5 and quarter pixels from there, so text in a moving or scrolled box keeps its bitmaps.
- Bitmaps live in a `text.Atlas`: pages of 8-bit coverage (`scene.pages()`), keyed by font, physical size, hinting, glyph and quarter-pixel offset, bounded in entries and bytes, least recently used out first but never what the current scene uses. `Page.takeChanged()` gives the region written since the last call, for uploads; the GPU renderer takes it, so it must be the only one that does for an atlas. An `App` keeps one atlas; `Headless.render` and `Scene.of(root)` make their own.
- `TextRendering` holds the hinting and the two exponents of the coverage correction: `LINUX` (FreeType's light auto-hinter, 1.8 and 1.8) and `WINDOWS` (the font's own hints in FreeType's v40 interpreter, 1.8 and 1.4); `TextRendering.platform()` is the default. Set it with `app.textRendering(...)` or `Headless.render(root, width, height, scale, rendering)`. Tests that compare images pin `TextRendering.LINUX`, and so does `Examples.main`, so that the stored images do not depend on the machine.
- The correction thickens text darker than its background, `1 - (1 - a)^darkGamma`, and thins lighter text, `a^lightGamma`. The scene finds the background in the fills of the text element and its ancestors; it misses earlier siblings, absolutely placed boxes, borders and what lies outside rounded corners, and then decides by the text colour, biased towards thickening (thicken up to L* 60, thin from 80). When the answer is wrong, state the background: `El.text("…").textBackground(0xFFFFFFFF)`.
- The switch and list examples have text, so the tests that render them call `TextLibraries.assumeLoaded()`; tests about input, focus and motion use `Examples.switchAlone`, which has none and runs without the natives module. The views behind the stored text images are in `Examples` (`textSizes`, `greyOnLight`, `textOpacity`, `scrolledText`), so that the image tests and `GpuRendererTest` draw the same; `Examples.laidOut` lays out a view with its text shaped for a scale, as `Headless.render` does.
- The bindings are in `com.rethinkj.ui.text.ffi`, not exported, in the style of `com.rethinkj.ui.gpu`. FreeType's C `long` (64 bits on Linux, 32 on Windows) is handled only in `FreeType`: `C_LONG`, its method handles, which take a Java `long` for it, and `getLong`/`setLong`. Tests that need the libraries skip themselves where there is no natives module.

## Images

`Image` (`com.rethinkj.ui`) is a picture for `El.image(image)`: `Image.of(pixels)` or `Image.of(pixels, scale)` from `Pixels` (sRGB, straight alpha), `Image.decode(bytes)` or `decode(bytes, scale)` from a PNG or JPEG file, told apart by their first bytes. The scale is the physical pixels per logical pixel the image is made for: 200 by 100 pixels at scale 2 are 100 by 50 logical pixels, drawn one pixel to one pixel in a window at scale 2. An image computes its levels when it is made (88 ms for 1920 by 1080), so an app decodes it off its thread (`App.background`) and keeps it in its state; renderers know an image by its identity, and the GPU uploads it once.

- Levels: level 0 is the image, each further level half as large on each side, rounded down and at least 1, down to 1 by 1, as GPUs count mip levels. A texel is red, green and blue premultiplied by alpha in linear light and encoded to 8-bit sRGB, and alpha, linear: how an sRGB render target stores colour, so 8 bits keep dark colours apart and an opaque pixel keeps its bytes. Each level averages the area each of its texels covers in the level before (two texels, or up to three where a side was odd), in linear light with premultiplied alpha, so translucent edges do not darken. An image larger than `Image.MAX_SIZE` (16384) on a side is halved until it fits, and its scale with it.
- The element: a leaf of role `img`, sized by layout to the image in logical pixels but no wider than the width there is for it, keeping its aspect ratio, as CSS's `max-width: 100%` for images (its measure takes the available width); a width or a height from the style scales it and the other follows the aspect ratio (`Style.aspectRatio`), and with both `fit(Image.Fit)` says how it fills the content box, as CSS's `object-fit`: `FILL` (the default), `CONTAIN` or `COVER`. It is clipped to the element's rounded corners, each its own; fill, border, shadows, opacity and motion apply as to any element. Its `.tree.txt` line starts with `image` and has the label, the text that stands for the image: `image #photo role=img label="A photo" 0,0 40x20`.
- In the scene an image is a fourth kind of instance, `Scene.IMAGE` (3): the rectangle its texels map onto, level 0's size and the number of levels where a glyph has its atlas slots, the opacity as its colour and its index into `Scene.images()`. A rounded element, and one whose image covers it and reaches beyond its content box, gets a clip entry of its own. The renderers draw it with the coverage of the square rectangle and of its clip, and sample it as `Scene`'s Javadoc writes out: one texel to one physical pixel, read as it is, where the rectangle is the image's size in physical pixels at whole positions; otherwise trilinear: `lod` is the log2 of texels per physical pixel along the axis with more, bilinear on level 0 when magnified, else the two levels around `lod` mixed, bilinear each, and the last level beyond it. That is continuous in the point and in `lod`, so the CPU's doubles and the GPU's floats differ by little, and a photo shown at a fraction of its size neither flickers as it moves nor frays.
- `App.imageMemory(bytes)`, 256 MB (`Scene.DEFAULT_IMAGE_MEMORY`) unless set, goes into each scene: the GPU renderer gives up the images drawn least recently beyond it, never one of the frame it draws. The windows of a thread share their images on the GPU (see GPU renderer), so the limit is one for the device: each window's scene sets it when that window draws, and an image that another window's last frame shows is not given up either.
- Costs on the CPU, on a desktop with 12 threads: a frame of 1920 by 1080 with a fill and its encoding takes 23 ms, 37 ms with a full HD image one to one in it and 31 ms with that image at a quarter of its width (`ImageTest` prints them).
- `ImageTest` checks the levels, the premultiplying and averaging in linear light, the element's size, aspect and line in a dump, the rectangles of the three fits and that one to one draws the pixels as they are; `GpuRendererTest` and `CpuRendererEquivalenceTest` the drawing (see GPU renderer).

## Pixel grid

The scene that `App` and `Headless` draw (`Scene.of(root, …, scale)`) puts the boxes at rest on the physical pixel grid, as browsers do; `Scene.of(root)` without a scale draws them where layout put them. Layout stays in whole logical pixels, which at scales 1 and 2 are whole physical pixels, so there the scene is the same as before and so is every stored image; at 1.25, 1.5 and 1.75 the scene snaps. It does so in its own numbers only: `CpuRenderer`, `ReferenceCpuRenderer` and the WGSL did not change.

- Edges: each edge of a border box at logical `x` is drawn at `round(x * scale)` physical pixels, halves up, so that neighbours that share an edge in layout share it on screen, with no seam, and a box may be a pixel wider than its neighbour of the same logical width. An edge that lies on the content box of a parent with a border snaps to the inner edge of the border as drawn, so what fills a bordered box meets its border.
- Widths: borders, each side's on its own, the focus ring (`Scene.RING`) and its gap, and a side of a box of at most `Scene.HAIRLINE` (2) logical pixels, such as a separator, are `max(1, floor(width * scale))` physical pixels, as browsers round border widths. A hairline of 1 is 1 pixel at 1.25, 1.5 and 1.75, 2 at 2 and 2.5, and 3 at 3. Radii are not rounded: with whole edges and widths the straight parts of a rounded rectangle are whole rows and columns, and its border is as wide all round.
- Clips are the snapped boxes intersected; a text field's text clip is its content box widened to whole pixels, so that it cuts no glyph. Shadows are drawn from the snapped box. A text element's content box starts from its snapped box and is then put on its glyph grid as before (see Text), so text and icons move with their box by whole pixels and are drawn from the same bitmaps wherever it is; a label may sit a pixel nearer one edge of its button at one position than at another.
- Motion: while a spring moves an element's position or size (`El.isMoving`, which `Animator` sets), it and everything inside it are drawn where they are, between pixels, so that it glides instead of stepping a pixel at a time, which shows at the slow end of a spring; once it rests it snaps, by at most half a physical pixel. A scrollbar's thumb is snapped across its bar, not along it: its place and length measure the offset and move with it.
- Pointer: a window reports the pointer, which the system gives as a whole physical pixel, at the centre of that pixel, a 256th of a pixel towards its top left (`Window.position`). A pixel is drawn as part of a box exactly when that point lies in the box's layout rectangle, edges included, so a press reaches the box that drew the pixel under it at every scale, and not the box that ends where the pixel begins; `PointerPixelTest` checks every pixel of a row of boxes at 1, 1.25, 1.5, 1.75, 2 and 2.5.
- Scroll offsets stay in logical pixels, as the wheel (also in fractions from a touchpad), `revealRow` and the thumbs give them. At 1.25 a step of one logical pixel moves the content by 1 or 2 physical pixels; its edges and text land on whole pixels anyway, as above.
- Rows of a virtual list are laid out one by one, each rounded where it lies in the list (`Flex.layout` with an origin), so that rows of a fractional height, such as 10.5, and what fills them share their edges with their neighbours.
- `PixelGridTest` in core measures borders and hairlines at every position, neighbours, a child filling a rounded clip, scrolled content, text and an icon in a moved box, a moving knob and the scene's numbers; kit's `PixelGridTest` measures the kit's field, buttons, checkbox, tabs, a card with rows and hairlines, the data grid, a menu with its shadow and the focus ring at 1.25, 1.5, 1.75, 2.5 and 3, and stores the sheet at 1.5 on whole and on half pixels (`pixel-grid-1.5x-whole`, `-half`).
- Icons stay in the drawing for their logical size (`Symbol.codePoint`). At 1.5 the 24-pixel drawing of a 16-pixel icon has crisper straight strokes than the 16-pixel drawing scaled, but strokes of 1 pixel instead of 1.5 and other proportions; at 1.25 and 1.75 the drawings for 20 and 28 pixels had more half-covered pixels than the 16-pixel drawing (15 and 40 % of the inked pixels against 11 and 19 % for icons of straight strokes).

## GPU renderer

- `render.GpuRenderer` draws a `Scene` with wgpu. Its WGSL is the constant `GpuRenderer.WGSL`, and every line of the fragment shader has a counterpart in `CpuRenderer` and in `ReferenceCpuRenderer` (see below): change them together. The instance block and the clip table go unchanged into two read-only storage buffers, and one instanced draw call, four vertices per instance as a triangle strip, draws all instances in order, rectangles, glyphs and shadows alike; images split it (below). The buffers double when a scene needs more and are kept for the next frame. A quad reaches at most a pixel beyond the target, which leaves its fragments as they are: a scrim's, a billion pixels out, was dropped whole by Direct3D's software rasteriser (WARP) at scale 2.5. The shader declares the slots in which the kinds differ as `u32` and bitcasts them to `f32` where they hold floats: a glyph's small integers read as floats would be subnormals, which a GPU may flush to zero.
- Corners and sides: `El.radius(topLeft, topRight, bottomRight, bottomLeft)` gives each corner its radius, which fill, border, clip, shadows, the focus ring and hit testing follow, and `El.border(top, right, bottom, left, argb)` each side its width in one colour; a side of 0 has none, so `border(0, 0, 1, 0, c)` is a line along the bottom of a box with no element for it. An instance is 96 bytes since then (`Scene`'s Javadoc says why it grew, and keeps the first 64 bytes as they were): a rectangle's and a shadow's other three radii at 64, a rectangle's other three borders at 80; the clip table's entry holds the four radii in its first 32 bytes. A pixel takes the radius of the corner on its side of the centre; with every corner alike the formulas and the bits are those of a single radius. The fill shows inside the rectangle moved in by each side's border and out by a physical pixel on a side without one, so that no border colour shows in its smoothed edge; its corners have the radius less the border on either side, as in CSS, and where the two differ a quarter of an ellipse, whose first-order distance (`(k - 1) k / |q / r|`) the renderers take. A shadow whose corners differ is the box less each rounded corner's square plus its quarter disc, the crossed boxes' blur where all four are alike (`ShadowTest` holds it within 0.006 of a brute-force sum too). `CpuRenderer` keeps its runs: along a row that the fill does not reach, as the bottom border of a grid's row, they are runs of the border colour; a fill with elliptic corners is measured at every pixel. `Examples.shapes` (`shapes.txt`, stored as `shapes-1x` and `shapes-2x`) shows them all with a ring with a gap; `GpuRendererTest` compares it and a scene of fractional borders and radii (`sides`) at scales 1, 1.5 and 2, and `aWrongShapeShaderIsNoticed` swaps the right corners, makes the inner corners circles, leaves the fill's edge on a side without a border, and gives a shadow's or a clip's corners all the top left radius, each failing hundreds to thousands of pixels.
- Nested clips: a clip table entry is 48 bytes, its rectangle and radii and then its parent, a u32 index of an earlier entry or 0 (WGSL pads `struct Clip { rect, radii, parent }` to 48; the 32 bytes had no slot free). A clip covers a pixel as its own rounded rectangle does, then as the least of that and each parent's own coverage along the chain: the coverage of the intersection, whose signed distance is the larger. An entry's rectangle is still the intersection of the boxes, which culls and bounds the quad. `Scene` gives it a parent only where the rounded corners of a clip around it reach into that rectangle (within a physical pixel), as a card's do around the square list that fills it; elsewhere, nearly always, it is one entry as before, with the same bits. A corner that the clip around cuts off gets no radius, and where the element's own rounded corner still shows in what is left, an entry of its whole box comes first as the parent. Hit testing needed nothing: a press reaches a child only inside every ancestor's rounded rectangle. `GpuRendererTest` compares `Examples.nestedClips` (a square list scrolled in a card with a radius per corner, three rounded boxes each sticking out of the one around it, text and images) at 1, 1.5 and 2, and `aWrongShapeShaderIsNoticed` leaves the parents out. Before, an entry kept the inner radii alone, so a square scroll area brought back the corners of the card around it.
- Shadows (`El.shadow(Shadow...)`, CSS's `box-shadow` without `inset`: offset, blur, spread and colour, the first on top) are a third kind of instance, `Scene.SHADOW`, drawn right before their element with its clip and opacity, over the shape grown by three deviations. A shadow shows also under a translucent fill, and it does not spring with `motion`. Its coverage is an analytic Gaussian blur of the rounded rectangle, evaluated per pixel with no offscreen pass or texture: two crossed boxes, whose blur is a product of `erf` differences and exact, and four quarter discs at the corners, each in eight slices of exact Gaussian mass across within three deviations; the deviation is half the blur radius with a pixel's share added (variance 1/12), so a shadow without blur gets an antialiased edge. `erf` is Abramowitz and Stegun's 7.1.28, arithmetic only and within 3e-7, written the same in WGSL and `CpuRenderer`, where the only other function is `sqrt`. `ShadowTest` compares the formula with a brute-force sum over a grid of cells: square corners within 1e-5, rounded ones within 0.006 (radius 0, small, half the height, blur below and above the radius, a spread, a menu's tight layer). A dialog of 400 by 240 with the dark theme's two shadows adds 8 ms at scale 1 and 33 ms at scale 2 to a CPU frame, most of it near the rounded corners, where each pixel takes the eight slices. Within three deviations at most 0.14 % of the colour is cut off, below a step for a dark shadow; a light glow on black can show that edge faintly. Gradients of a dark shadow on a dark surface step by single 8-bit levels, a few physical pixels apart, as in browsers; dithering in both renderers would hide them.
- A glyph's quad covers exactly its texels, from the physical pixel `floor(x * scale + 0.5)` on, as the CPU's `Math.round`; the fragment reads its texel with `textureLoad`, never a sampler. The atlas pages are the layers of one `r8unorm` texture array, page `i` in layer `i`: one array keeps the single draw call, since WGSL cannot choose among bound textures by a per-instance index. Before each draw the renderer writes into each layer the region `Page.takeChanged()` reports, nothing for an unchanged page, and a page it has not seen in that layer whole, once. More pages than layers, or pages of another size, replace the array by one with the next power of two of layers (at most `maxTextureArrayLayers`, 256 or more), and every page is written whole again. `GpuPresenter.atlasUploads()` counts the writes; a frame without new glyphs, and an idle window, upload nothing.
- Images (see Images): each is a texture of its own with the image's levels as its mip levels, uploaded when it is first drawn and kept by the image's identity while the images on the GPU fit into the scene's `imageMemory`; beyond it the ones drawn least recently are given up, never one of the scene, and come back when drawn again. `GpuPresenter.imageUploads()` counts the uploads: a frame without new images uploads nothing. The texture is bound as group 1, which only image instances read, so the instances are drawn in order in one draw call per run that one image texture is bound for: a scene without images is one draw call, a list of 200 rows of the same icon too, 200 different icons 201 (a bind group each, made once per image, and a few microseconds of recording each), and a document of 30 photos at most 31. A texture per image rather than an atlas of images: the GPU's mip levels hold the levels with no packing, padding or bleeding between neighbours, an image's memory goes whole when it is given up, and an image larger than the device's largest texture (`maxTextureDimension2D`, 8192 or more) leaves out its largest levels, which the shader then takes from the first it has. The format is `rgba8unorm` with the bytes of `Image`'s levels, which the shader decodes from sRGB with sRGB's formula and filters itself with `textureLoad`, as the CPU does, without a sampler: on an NVIDIA GTX 1070 with Vulkan, the GPU's own decoding of `rgba8unorm-srgb` put 33 of 256 values a step off after halving them, against 9 for the shader's, which is what the target's encoding does, and bilinear filtering of translucent edges showed that as 2 steps. `GpuRendererTest` compares `Examples.images` at scales 1, 1.5 and 2 (one to one, magnified, made smaller and 4000 pixels made 60 and 100, alpha over and under text, rounded clips with a radius per corner, half opacity, covering and contained, on light and dark), `aWrongImageShaderIsNoticed` moves the sampled point a quarter texel, takes the nearest texel instead of four, the finer level alone, one to one a texel off and leaves out the clip, each failing thousands of pixels, and `anImageGoesToTheGpuOnceAndIsGivenUpBeyondTheMemory` counts the uploads.
- It draws only into sRGB targets, with premultiplied blending (`one, one-minus-src-alpha`), so that the GPU blends in linear light and the target encodes: `RGBA8_UNORM_SRGB` for images, `BGRA8_UNORM_SRGB` (or `RGBA8_UNORM_SRGB`) for windows. `GpuRenderer.create()` and `render(scene, width, height, scale)` draw into `Pixels` without a window, like `CpuRenderer.render`.
- `render.GpuPresenter` is the `WindowLoop.Presenter` that owns a window's surface (Direct3D 12 on Windows, Vulkan on Linux, FIFO, opaque) and configures it with the window's size in physical pixels. FIFO paces nothing where the display holds no frame back: on a machine whose display is virtual, FIFO, MAILBOX and IMMEDIATE all returned from presenting at once, more than a thousand times a second in a tight loop, on Direct3D 12 and Vulkan alike. So `WindowLoop` itself draws input and posted tasks that arrive less than a refresh after the building of the last frame began only once that refresh has passed, with whatever else arrived meanwhile, and input after a pause at once. It draws nothing while the window is minimized. When the surface is out of date, lost or times out, it reports `pending()`, and the loop offers the newest frame again a refresh later; the presenter then reads the window's size again. Close it before the window.
- The `GpuPresenter`s of one thread share a `GpuContext` (package-private): the instance, the adapter and device (made with the first presenter, on an adapter that can present to its window), the shader module, the bind group layouts, a render pipeline per surface format (compiled when a window of that format first draws, so a second format gets its own) and the images on the GPU; the context counts its presenters and closes the instance after the last, and the next presenter makes a new one. Per window stay the surface and its configuration, the globals, instance and clip buffers with their bind group, and the glyph atlas texture: each `App` has its own `Atlas`, whose pages only one renderer may take the changes of (`Page.takeChanged`), so sharing the texture would need one atlas per device. Images are shared because a renderer knows an image by its identity: an image that several windows show goes up once (`imageUploads()` counts per window). The device is worth sharing because making one took 60 to 240 ms and compiling the pipeline 324 to 379 ms on Direct3D 12 here, so a window torn off during a drag showed nothing for half a second while every window stood still. `GpuRenderer.create()` keeps a device of its own. A window whose surface the shared adapter cannot present to is refused with a message. A lost device is not made anew: on Direct3D 12 a window's surface cannot be configured for another device while the lost one holds its swapchain (DXGI says "window is in use", then "access denied" for a new surface on the same window, and wgpu-native ends the process when configuring fails), and releasing a lost device may end the process too; so every present throws `GpuException` of kind `DEVICE_LOST`, which ends the loop, and the presenters close as usual, in any order. `SharedGpuTest` opens three real windows on one loop and closes them in all six orders, counting one device and one pipeline (`Device.created()`, `RenderPipeline.created()`), and a window after all others closed gets a new device; `SharedDeviceTest` gives a second window `RGBA8_UNORM_SRGB` and finds a second pipeline and one upload of an image both windows show, and loses the device under three windows and under a loop.
- `GpuRendererTest` compares the GPU's images with the CPU's: the views behind every stored image of core, which it builds as their tests and scripts do and checks against the stored PNG first (`theCasesIncludeTheViewBehindEveryStoredImageOfCore` fails when a stored image has no case), and scenes that stress one formula each, at scales 1, 1.5 and 2; text in both fonts at 1.25 and 1.75, 5000 instances at 1.75, a scrim at 2.5 and 500 random shapes at 1, 1.25, 1.75, 2.5 and 3 besides. The text scenes have 11 to 14 pixels in both fonts on light, dark and grey with both `TextRendering`s, opacity, rounded clips, translucent boxes over and under text, an atlas of 64-texel pages that a frame fills several of, and empties for the next, text fields with a selection, a caret and a composition, scrolled and in the rows of a list, and fallback fonts in lines and a field (`Examples.fallbackText`, `fallbackField`). Overlays are there too: a menu with its submenu across the rounded clip of a scrolled list, and a dialog over a scrim, all with shadows. So are shadows of their own (`shadows`): on light and dark, under text and translucent boxes, cut by a rounded clip, at half opacity, overlapping, wide, sharp, coloured and three on one element; `aWrongShadowShaderIsNoticed` makes the blur a tenth wider, leaves out the pixel's share or the corners, takes the slices at their top and leaves out the clip, and each fails hundreds to thousands of pixels. The kit's data grid is there too: core's tests cannot see the kit, so `Examples.grid` builds the grid of `Orders` as `DataGrid` does, from core's elements in `Theme.DARK`'s values; the test first checks that it draws the kit's stored images `grid-dark-*` from kit's `grid.txt`, then compares at scales 1.5 and 2. A change of the grid's look shows there, and `Examples.grid` follows it. A channel may differ by 1 step of 8 bits, and by half a step more for each further instance that draws into the pixel, because the GPU rounds into the 8-bit target after every draw (`tolerance` says why). On top of that comes what the GPU's blending can add: it takes the source's alpha at the 8 bits of the target, so a layer lets up to 1/255 more or less of the light under it through (`ALPHA_STEP`); under nearly opaque dark text on white that measured up to 4 steps near black, and the test adds what it can be at each pixel, from the CPU's blends (`CpuRenderer.Blends`). `aWrongGlyphShaderIsNoticed` breaks the texel mapping, the reading of texels, the correction and the clip one at a time; each fails thousands of pixels. A failing scene leaves `.cpu.png`, `.gpu.png` and `.diff.png` in `core/target/gpu-vs-cpu`. The test is skipped without the natives module or an adapter.
- `Png.decode` reads PNG files without `java.desktop`: grey, grey with alpha, RGB, RGBA and palette images of 1, 2, 4, 8 and 16 bits per sample as the format allows them (sixteen keep their high byte), the transparency of `tRNS` by palette and by colour key, the five row filters and every chunk's CRC, into straight RGBA `Pixels`; interlaced images are refused with a message that says so. `PngTest` reads images that Pillow wrote (`core/src/test/resources/png`) against the pixels Pillow reads, and rows of all five filters. `El.image` draws them (see Images).
- `Jpeg.decode` reads JPEG files without `java.desktop`: baseline, extended sequential and progressive files with Huffman coding, 8 bits per sample, one component (grey) or three (YCbCr, or RGB by Adobe's transform 0 or the component ids R, G, B), whole sampling factors from 1 to 4 (4:4:4, 4:2:2, 4:2:0, 4:4:0 and others), restart markers, and the orientation of an EXIF block, which it applies. It decodes as libjpeg does with its defaults: libjpeg's integer inverse DCT (`jidctint.c`), its smooth upsampling of chroma halved across, down or both (`h2v1`, `h1v2`, `h2v2_fancy_upsample`; across only where the chroma is more than 2 samples wide, as `jinit_upsampler` decides; other factors repeated) and its fixed-point YCbCr to RGB, so `JpegTest` finds every pixel of its ten files (`core/src/test/resources/jpeg`, crops of the kit's gallery that ImageMagick 6.9 with libjpeg-turbo 2.1 and Pillow wrote at quality 90: baseline in all four samplings, grey, progressive, restart intervals in a baseline and a progressive file) equal to what ImageMagick decodes them to, `<name>.expected.png`. A file that ends early or breaks off at a marker decodes as far as it goes, the blocks after left as they were, as libjpeg does; corrupt data is refused with an `IllegalArgumentException`, as are four components (CMYK, YCCK), arithmetic coding, lossless and hierarchical files, 12 bits, fractional sampling, a height only a DNL marker gives and more than `Jpeg.MAX_PIXELS` (40 million), which bounds the memory a file can make it take: coefficients of 2 bytes per sample and 4 bytes a pixel for the result. `JpegTest` cuts four files at every length and changes up to eight bytes of each file 300 times: each decodes or is refused, nothing else, within a time limit. Reading a photo of 1920 by 1080 (265 KB, 4:2:0) took 36 ms, progressive 43 ms, on a desktop with 12 threads; it decodes bit by bit, without a lookup table for Huffman codes.
- `CpuRenderer` draws the same bits as a loop that evaluates every formula at every pixel of every instance, and is fast by leaving out only what it knows, never by computing it another way: in each row, the pixels that a rounded rectangle, its fill and its clip, or an image's rectangle and its clip, cover whole (coverage exactly 1) are one run, whose ends it finds by evaluating from both sides, and a clip that covers the four corner pixels of an instance's box covers all of it, because every step of the coverage is monotonic also in doubles (`CpuRenderer.Box` says why), and a clip with parents covers a pixel whole only where each of them does; a glyph's corrected coverage is computed once per texel value and frame, a shadow's blur across x once per column and across y, with the slices of its corners, once per row; the encoding to sRGB is kept per pixel value and per channel value. `CpuRendererEquivalenceTest` compares it with `ReferenceCpuRenderer` in the test sources, the plain loop as it was, byte for byte, the floats before encoding and every blend `Blends` sees included: on `GpuRendererTest`'s scenes, the shapes of `ShadowTest`, images at every size from one to one to beyond their last level at five scales, 3000 random scenes with fractional and non-finite values, image instances among them, and frames that make the encoder's slots collide. Against the plain loop, on a desktop with 12 threads under a load of 4 to 6: an 800 by 600 rectangle 5 ms (was 137), the data grid at scale 2 14 ms (216), text at scale 2 8 ms (112), the rows of a million at scale 2 3 ms (85), each with 3 to 13 ms of `Png.encode` on top when a script snaps it.

## Windows

- `com.rethinkj.ui.window` opens windows through SDL 3 (`Window`), turns SDL's events into `WindowEvent`s and runs an `App` in a window (`WindowLoop`), which hands each new frame to a `Presenter`. `Sdl` and `Win32` hold the handwritten bindings: a new function gets its descriptor as a constant there and its handle in the class's lazy holder.
- Windows are used on the thread that opened the first one, until all are closed. Every event is translated in an SDL event watch as SDL queues it (a wheel that turns only up and down with Shift held as one that turns sideways, as in the system's own apps) and delivered in that order by `Window.pollEvents` or `waitEvents`; SDL's own queue only ends the wait. On Windows the listener is also called from inside the system's move and resize loop, with `Redraw(live = true)`.
- The hit test, the event watch and the Windows subclass are upcalls: each catches every `Throwable` and hands it to `Window.fail`, and the next `pollEvents` or `waitEvents` throws it. One that escapes ends the JVM.
- Text input is off until `Window.textInputArea` turns it on, which `WindowLoop` does while the focused element takes text (`App.inputArea`), and `stopTextInput` turns it off. On Windows the character that the system makes of a key pressed with Control and without Alt (Control+Space types a space there) is dropped, as Linux makes none; Control with Alt is AltGr, whose characters stay. SDL reports a key held with AltGr as held with Alt alone (it hides the left Control that Windows adds for AltGr), so an Alt shortcut took it: in Workbench AltGr+Q, @ on a German keyboard, opened the Query menu; a key held with Alt alone whose character Windows makes as `WM_CHAR` (Alt with a letter makes `WM_SYSCHAR`) was AltGr, and `Window.systemChar` gives its `KeyDown`, still queued, Control with Alt. SDL turns a key into text only while text input is on, and handles a whole batch of input (a click into a field and the keys after it, from a fast typist or a tool that types; Tab and the keys after it; a key that opens a dialog whose field takes the focus, and the keys after it) before the loop sees the click or key and turns text input on for the field: those characters were lost. On Windows the system still makes them (`WM_CHAR` from `TranslateMessage`, through the keyboard layout with its dead keys and AltGr), so `Win32Shell`'s subclass hands each one that SDL dropped to `Window.systemChar`, which applies SDL's rules (no control characters, nothing of Control without Alt) and queues it as `WindowEvent.KeyText` when it follows the key that made it, or as `TextInput` when it came without a key (`VK_PACKET`, as `KEYEVENTF_UNICODE` sends it); `WindowLoop` gives a `KeyText` to `App.keyText`, which types it if that key went to an element that takes text and drops it otherwise, as Space's space when Space pressed a button that opened a dialog. Text input still turns on only for a field, so input methods compose and an on-screen keyboard shows only there; keeping it on whenever the window has the focus would have let an input method take the keys of a grid or a button (Space, Enter, letters) in its native mode. The characters typed before text input comes on bypass the input method: with one in its native mode they arrive as the layout's letters, uncomposed (not tried: no input method is installed here). On X11 and Wayland SDL makes the text of a key only while text input is on as it handles the key (X11: `XFilterEvent` for the input method and `Xutf8LookupString`; Wayland: xkbcommon's compose state and keysym), so there `Window` turns text input on itself, as SDL queues a primary press or a key other than a modifier while it is off, from the event watch (`Window.textSoon`), and the text SDL then makes of a key goes on as `KeyText`, typed only where the key went: the keys after the click, Tab or key arrive with their text, through the input method, its dead keys and Compose, and AltGr; the click's or key's own text was made before and is none, as Space's when it presses a button. The loop turns text input off after the frame unless a field has the focus, so it is on for a non-field only from such an input to its frame: an input method in its native mode (IBus with Anthy, Mozc or Pinyin, fcitx) composes the keys of a batch that follows a key on a button or a menu, which were keys without text before, and Wayland's text-input-v3 is enabled and disabled once for each such key (GNOME shows its on-screen keyboard on enabling only after touch input). Not tried on Wayland; on X11 with GNOME and IBus (XIM, its plain engine for the German layout) `xdotool` with 1 ms between keys typed the keys after Enter and after Space on a menu item that opens Workbench's Drop table dialog into its field, where they had been lost, and Space's space not; a click into a field, Tab into one and a click on a grid's cell with keys after them worked before and after, as such a press reaches the loop alone when the app is idle. With 1 ms between keys IBus sometimes lost a dead key's or an AltGr key's character, also in a field that had text input on long before. With real input (`SendInput`, one call per batch) on a German layout, a click with keys or with characters sent as `KEYEVENTF_UNICODE`, Shift+Tab with keys, a dead key with its letter (`ê`, `â`), Shift+1, a click on Drop table… and Enter or Space on it with the keys after reached Workbench's query, ConnectionDialog's fields and the dialog's field, and Space's space did not; `TextInBatchTest` posts `WM_KEYDOWN`s after a press in real windows, and `KeyTextTest` checks the rule. `WindowLoop` also gives the app the system clipboard (`SystemClipboard`, through SDL) and the system's fonts (`App.systemFonts`), passes the click count and modifiers of a press (a second press counts as a double one within the system's distance, half of `SM_CXDOUBLECLK` on Windows and 5 pixels elsewhere, which `Window` sets as SDL's `SDL_MOUSE_DOUBLE_CLICK_RADIUS` in place of its 32 for touch screens), and wakes an idle window for the caret's blink, hover delays and the actions an app asks for with `App.after` (`App.nextChange`).
- A frameless window draws its own title bar: the view marks elements with `El.windowPart`, and `App.windowPart` answers SDL's hit test. Where a press would go to a control (`WindowPart.CONTROL`: an element with a press or drag handler, a text field, a scrollbar's strip) or to a minimize, maximize or close part, the resize margin narrows to `Window.CONTROL_MARGIN`, 2 pixels, so that a scrollbar along the window's edge can be grabbed at its outer pixels; the corners keep their reach. The Windows 11 parts (rounded corners, snap layouts on the maximize part, system menu on a right click) are in `Win32Frame`; Alt+Space that no key handler takes opens the system menu below the drag area at the left edge (`Window.showSystemMenu`, which `WindowLoop` calls through `App.keyDown(key, untaken)`), on a framed window too, since SDL keeps the key from the system, whose Javadoc also says why the resize margin lies inside the window. The press that `Win32Frame` reports itself, on the maximize part or the secondary one on a drag area, captures the pointer (`SetCapture`) until its release, which it reports wherever it happens: released over the content, SDL, which saw no press, reported none, and the app stayed pressed, or the next secondary release in the content was taken for the menu's; when another window takes the pointer, the press ends at -1,-1, where it presses nothing (`WindowTest`). `Win32Frame` also gives a minimized frameless window no client area, as Windows does for a framed one; otherwise SDL reports the 160 by 28 pixels of a minimized window when the system restores it.
- Icons: `WindowIcon.of(Pixels...)` (square, straight alpha, as `Pixels` is) or `WindowIcon.of(size -> view)`, a view laid out in a square of `size` logical pixels at scale 1 and drawn by `Headless.render` (without natives unless it has text); `AppIcon.appIcon(theme, size, colour, symbol)` in the kit is a rounded square in the app's colour with a symbol of the icon font. `Window.options().icon(icon)` sets it before the window shows, `window.icon(icon)` later. It goes to `SDL_SetWindowIcon` as a surface with alternate images (Linux: 64 with 128 and 256, which only Wayland's `xdg_toplevel_icon_v1` uses; X11 gets the base). SDL's Windows driver makes one `HICON` of the base image for both sizes, so `Win32Shell`, a second window subclass beside `Win32Frame`'s, also sets the small (16 × scale) and big (32 × scale) icon with `WM_SETICON`, again when the scale changes, and again with new handles when `TaskbarButtonCreated` arrives: the taskbar asks for the icon when it makes the button, and while the app's thread is busy (setting up the GPU right after the window opens) it times out and keeps java.exe's class icon.
- Identity: `Window.identity(id, name)`, before the first window (again with the same values later, as the examples do for a torn-off window, does nothing; another identity throws), goes to `SDL_SetAppMetadata` (Wayland app id, X11 class) and on Windows to `SetCurrentProcessExplicitAppUserModelID`: the app's windows group under a taskbar button of their own with the window's icon, instead of under java.exe. Its jump list then offers no "Pin to taskbar", since Windows cannot tell how to start the app; with a Start menu shortcut that carries the same `System.AppUserModel.ID` and an `.ico`, the list names the shortcut, pinning works and the pinned button starts what the shortcut says and shows its icon. That shortcut is a packaging matter (an installer, jpackage). The examples each have an id `com.rethinkj.ui.examples.<class>` and an icon (`Identity`).
- Appearance: `Window.systemAppearance()` is a `SystemAppearance`: the scheme from `SDL_GetSystemTheme` (on Windows `AppsUseLightTheme`), the accent as 0xFFRRGGBB from `HKCU\Software\Microsoft\Windows\DWM\AccentColor` (the colour chosen in Settings, stored as ABGR; `DwmGetColorizationColor` is the frame's colorization colour, the same RGB with alpha C4, and only the fallback) and high contrast from `SPI_GETHIGHCONTRAST`. Every window gets `WindowEvent.AppearanceChanged`: from SDL's `SDL_EVENT_SYSTEM_THEME_CHANGED`, and on Windows when `Win32Shell` sees `WM_SETTINGCHANGE`, `WM_SYSCOLORCHANGE` or `WM_DWMCOLORIZATIONCOLORCHANGED` after SDL has handled it and the value differs. `WindowLoop.appearance(handler)` hands it to the app as a posted task at the start and on each change; the kit's themes stay values, and Showcase's look "System" and Settings' theme "System" pick dark or light from it. Linux reports no accent (0) and no high contrast. What high contrast should mean for an app is in `SystemAppearance`'s Javadoc. Drive the Settings switch with `AppsUseLightTheme` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` and a `WM_SETTINGCHANGE` broadcast with `"ImmersiveColorSet"`, and restore it.
- Taskbar: `window.attention(Attention.BRIEFLY | UNTIL_FOCUSED | NONE)` is `SDL_FlashWindow`. `window.badge(icon, description)` is `ITaskbarList3::SetOverlayIcon` with an icon of 16 × scale pixels (`AppIcon.count`, `AppIcon.dot`), through a taskbar list that `Win32Shell` creates with `CoCreateInstance` on the windows' thread (SDL initialised COM there) and releases before `SDL_Quit`; it waits for `TaskbarButtonCreated` and is set again when Explorer restarts. COM methods are called through the vtable by hand (`Win32.method`, address-less downcall handles). Linux has no badge. `window.progress(Window.Progress, fraction)` shows progress on the button through the same list, `SetProgressState` and `SetProgressValue` (slots 10 and 9; the fraction as a share of 10 000): `NONE`, `INDETERMINATE` (a bar that runs), `NORMAL`, `PAUSED` (yellow) and `ERROR` (red); set before the button exists it waits for `TaskbarButtonCreated` and is set again when that comes back after Explorer restarted, as the badge (`SystemIntegrationTest` sends the message itself and counts what reaches the list, `Win32Shell.progressApplied`). It replaced SDL 3.4's `SDL_SetWindowProgressState`, which kept a taskbar list of its own and on Linux stored the state and returned true with nothing shown; on Linux it now returns false and does nothing. A `Windows.Handle` reaches both through `window()`. Workbench counts its questions on the badge with a running bar beside it, and flashes when an answer arrives in the background; Showcase shows its made-up download as a bar, red where it failed, and none once done.
- `window.frameDark(boolean)` sets `DWMWA_USE_IMMERSIVE_DARK_MODE`: a framed window's caption and border follow the app's theme instead of the system's. SDL already makes every window follow the system's setting (`WCA_USEDARKMODECOLORS`, `SetPreferredAppMode`), and a frameless window's border and every system menu stay with it; the attribute does not change a frameless window's border (`DWMWA_BORDER_COLOR` would). Mica and acrylic (`DWMWA_SYSTEMBACKDROP_TYPE`) need the content to be transparent where they show, and wgpu offers only an opaque surface for an HWND (D3D12 and Vulkan both report `OPAQUE` alone); wgpu-native's other Windows source is a WinUI `SwapChainPanel`.
- File dialogs: `App.fileDialog(FileDialog, onChoice, onError)` shows `FileDialog.open(title)` (`.many()` for several files), `save(title)` (`.fileName("orders.csv")`) or `chooseFolder(title)`, with `.filter("SQL", "sql")` (extensions without the dot, `*` for all; the first filter chosen at first) and `.in(folder)`, and posts a `FileDialog.Choice` (the paths, empty when cancelled, and the index of the filter chosen, -1 where the system does not say, as Linux's portal never does) or SDL's text of what went wrong. It returns at once; the window draws on while the dialog is open. What shows it is `App.dialogs()`, a `Dialogs`: `Dialogs.NONE` at first, which fails every dialog saying so, the window's `SystemDialogs` in a `WindowLoop`, the script's in a `Script`, or one a test sets. `SystemDialogs` calls `SDL_ShowFileDialogWithProperties` with the window as parent: on Windows SDL shows `IFileOpenDialog` owned by the window on a thread of its own, which calls back; on Linux it asks the XDG desktop portal (`org.freedesktop.portal.FileChooser` over D-Bus, modal to the window through its X11 or exported Wayland handle) and reads the answer when it pumps events, so the callback runs on the windows' thread, and the loop therefore waits at most `SystemDialogs.PUMP` (50) ms while a dialog is open, since SDL pumps D-Bus only every 3 s while it waits; without a portal SDL runs zenity on a thread of its own (whose cancel comes as one empty line, which counts as none), and without either the app gets a message that names what to install. The callback (an upcall, `SystemDialogs.answer`) catches everything, copies the UTF-8 paths at once and hands on only Java values; on Windows the dialog answers with the 8.3 short form of a path longer than `MAX_PATH` (`…\EINSEH~1\LANGED~1.TXT`), so a path with a `~` goes through `GetLongPathNameW` (`SystemDialogs.longName`; a file not there yet, a save dialog's, keeps its name after its folder's long form); the filters live in a shared arena until it has answered. The location SDL gets is the folder with a separator after it (Windows takes the last part of a path without one for a file's name), or the folder and the suggested name. The SDL build has dialogs and D-Bus on (`SDL_DIALOG` is on by default; `SDL_DBUS=ON` in `natives.properties`). A window has one file dialog at a time: another fails at once while one is open, since the system enables the window again as each closes, also under a second still open. A window that closes while its dialog is open leaves the answer to its app, which runs it if it runs frames again; on Windows it first closes the dialogs it owns (`Win32Shell.closeDialogs`, `WM_CLOSE` to each `#32770` it owns), which answer as cancelled, since a dialog on SDL's thread outlives its owner, stays on the screen without one and never answers. A dialog may still be on its way then, as when the window closes right after asking for it: while one of its dialogs has not answered, the window only hides, `pollEvents` and `waitEvents` (which then wait at most `PUMP` ms) close each of its dialogs as it appears, and destroy the window once all have answered; SDL quits only after that. Until the windows' thread handles messages, SDL's dialog thread waits for it and shows nothing; once that thread handles them in any other way, as for a message box, the dialog appears, owned by the hidden window, and stays. So when no other window is open, as when the last window of a `WindowLoop` closes and the loop ends, `close` itself pumps until the dialogs have answered (or, when a listener closed the window, the `pollEvents` or `waitEvents` that delivered the event does), at most `Window.LINGER_MILLIS` (5 s; about half a second here), and returns with the window, the dialog and SDL gone; after that time it leaves them to the next pump. `SystemDialogsTest` closes a window right after asking, with another window open, as the only one, and as the last of a loop. `SystemDialogsTest` calls the callback through its stub with UTF-8, spaces and paths of 1400 characters, on another thread too, with the short form of a path longer than 260 characters on Windows, and a handler that throws; only its tests that close a window under its dialog open real ones (with `-Dwindows.tests=true`), and each closes what it opened.
- Message boxes: `App.messageBox(MessageBox, onButton, onError)` shows `MessageBox.information`, `warning` or `error` with up to three `.buttons(...)` (Enter presses the first, Escape the last, unless `defaultButton` and `cancelButton` say otherwise) through `SDL_ShowMessageBox`, modal to the window, and posts the index of the button (the cancel button's when it was closed without one). SDL wants it on the thread of the parent window and blocks there, so all windows stand still while it is open: it is for what cannot be shown in the window, and the kit's `Dialog` asks inside one. On Linux SDL uses zenity where it can and else, on X11, draws the box itself. `SystemDialogs.show(box)` shows one with no window, and `SystemDialogs.reportFailure(name, () -> ...)` runs the code that opens the app's window and its loop and shows what it throws in one before throwing it on (as when the GPU has no adapter or a library cannot load); when SDL itself cannot load, Windows shows it with user32's `MessageBoxW` (`Win32.errorBox`); the example Documents starts that way, and where no box can show the failure keeps that reason as a suppressed exception.
- What another application drops: SDL's drop events (`DROP_BEGIN`, `DROP_POSITION` while the drag moves, at the release one `DROP_FILE` per file or one `DROP_TEXT` per line, then `DROP_COMPLETE`, which alone means the drag left) become `WindowEvent.FileDragOver`, `FileDragLeave` and `FileDrop` with the paths, or the lines joined by line feeds, and go to `App.fileDragOver`, `fileDragLeave` and `fileDrop` as input. The innermost element under the point with `El.onFileDrop(handler)` gets `Drop`'s `OVER` on each move (payload null: the systems say what is dropped only at the release), `LEAVE` when the drag moves on or leaves, and `DROP` with a `List<Path>` or the text as its payload; text dropped on a text field that takes edits goes in at the point as a paste, with the focus. `El.onDrop` stays for the payloads of the app's own drags. `FileDropTest` drives it through `App` and scripts, `FileDropWindowTest` through SDL's events in a real window.
- Tests that open real windows run only with `-Dwindows.tests=true` (`mvn verify -Dwindows.tests=true`), since they open windows on the screen and take the pointer and the keyboard focus for a moment, and an ordinary `mvn verify` skips them; with the flag they still skip themselves without the natives module or a display. Run them after a change to `com.rethinkj.ui.window`, to the bindings of SDL or wgpu, or to `GpuPresenter`. The demo in the test sources draws the light switch with its label with `GpuPresenter`: build with `mvn -pl core -am test-compile`, then from the repository root `java --enable-native-access=ALL-UNNAMED -cp "core/target/classes;core/target/test-classes;natives-windows-x64/target/classes;fonts/target/classes" com.rethinkj.ui.window.WindowDemo` (on Linux, with `:` between the entries and `natives-linux-x64`). It prints every frame it presents with the atlas uploads so far; `--cpu-png=<file>` writes the CPU's image of the last frame when it stops, to compare with a screenshot of the window, and `--text=linux` or `--text=windows` overrides the platform's `TextRendering`. `--exit-after=<seconds>` and its other options are in its Javadoc; keep windows short-lived when you drive them with synthetic input. SDL drops the click that activates a window, so click once on the background first. Windows 11 rounds the corners of a frameless window and draws a 1-pixel border over its edge, so leave the edge out of such a comparison.

## CI and publishing

`.github/workflows/build.yml` runs `mvn -B -ntp verify` on `ubuntu-24.04` and `windows-latest` with Temurin JDK 25 for every push and pull request that changes more than the documentation site under `docs/`; a new push to a branch cancels its older run. It caches Maven's repository and what `scripts/FetchNatives.java` leaves in `natives-*/fetched/resources` (keyed by `natives.properties` and the tool), so that the native libraries are built from source only when they change; on Linux the packages of `natives-linux-x64/natives.properties` are installed only then. On Windows the tool finds the runner's Visual Studio with its CMake and Ninja. When a test fails, the run keeps the surefire reports and what the image tests left (`*/target/golden`, `core/target/gpu-vs-cpu`) as an artifact for a week.

The CI leaves out the tests that open real windows (`-Dwindows.tests=true`), since a runner has no desktop to open them on. The GPU tests take the adapter there is: on Windows that is WARP (Microsoft Basic Render Driver, Direct3D 12 on the CPU), on which `GpuRendererTest` passes within its tolerances; the Linux runner has no Vulkan driver, so they skip themselves there. The stored images come out the same on both runners as on the machines they were made on.

After both builds pass on a push to `main` of `rethinkj/ui`, or when the workflow is started by hand on `main`, the job `publish` deploys SNAPSHOTs to the Central Portal's snapshot repository (`https://central.sonatype.com/repository/maven-snapshots/`, the root POM's `distributionManagement`), first from Linux, then from Windows: Linux the root POM, `core` and `kit` (each with a sources JAR), `fonts`, `icons` and `natives-linux-x64`, Windows `natives-windows-x64` alone, each module once. It skips the tests, which `build` ran on the same commit, and `deployAtEnd` keeps a reactor that fails from uploading anything. The credentials are the repository's secrets `CENTRAL_USERNAME` and `CENTRAL_PASSWORD`, a user token of the Central Portal, which `actions/setup-java` puts into the runner's `settings.xml` as server `central-snapshots` (not `central`, whose credentials Maven sends only to repo.maven.apache.org); without them the job warns and publishes nothing. Started by hand on another branch, the same job is a dry run into `target/snapshots` on the runner, kept as the artifact `snapshots-<os>`. A dry run on a machine of your own: `mvn deploy -Dmaven.install.skip=true -DaltDeploymentRepository=local::file:///<folder>` (without `maven.install.skip`, `deploy` installs into `~/.m2` on the way). SNAPSHOTs on Central are removed after 90 days.

A release is not set up yet. Central wants for it, besides what the POMs have: `<developers>`, a Javadoc JAR beside each JAR (the modules without Java code need one too, empty or with a README), sources for the modules without Java code, PGP signatures of every file, a `<repository>` or the `central-publishing-maven-plugin` for the Portal's publisher API, and the version without `-SNAPSHOT`. Both natives JARs still have to come from their own platform, so a release needs the two runs as now, with the Windows JAR handed to the run that uploads the bundle, since the Portal takes a release as one bundle.

## Conventions

- A new module gets the directory `<name>/`, the artifactId `rethinkj-ui-<name>` and the base package `com.rethinkj.ui.<name>`, and is listed under `<modules>` in the root `pom.xml`; a natives module, in the profile of its platform.
- Shared build configuration (Java release, encoding, plugin and dependency versions) belongs in the root `pom.xml`. Module POMs declare only what is specific to them.
- Dependencies point one way: `kit` depends on `core`, never the reverse.
- The version is repeated in every module's `<parent>` block. Change it with `mvn versions:set -DnewVersion=<version>`, not by editing one POM.
- Java code is formatted by Palantir Java Format in its Google style (two spaces, 100 columns, one call of a chain per line), through Spotless: `mvn spotless:apply` formats every Java file of the modules and of `scripts/`, and `mvn verify` fails on a file that is not formatted, so the CI checks it. Format before committing; do not break lines by hand against it. `.git-blame-ignore-revs` lists the commits that only reformatted (`git config blame.ignoreRevsFile .git-blame-ignore-revs`).

## Changes

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <summary>`, for example `feat(core): add text shaping`. The scope is the module when the change stays in one. A breaking change gets `!` before the colon.
- Keep commit messages short: a subject line of at most 72 characters, and a body only when the diff doesn't show why. No lists of changed files and no test or verification reports.
- For a change that users of the library can notice (new or changed API, changed behaviour, a fix, a raised requirement), add `changelog/unreleased/<YYYY-MM-DD>-<slug>.md` with one top-level bullet written for those users. These files are folded into `CHANGELOG.md` at release.
- Don't add files that describe your own work: no `VALIDATION.md`, `SUMMARY.md`, plans, reports or review notes. What changed and why goes in the commit message; anything longer goes in the pull request description.

## This repo is public

Everything pushed stays public in history. Before committing, run `git diff --cached | grep -nE '/home/|/Users/|/private/var/|\.ts\.net|ses_[A-Za-z0-9]{20}'` and keep these out:

- secrets, tokens and credential file contents;
- home folder and temp paths, machine names and tailnet hostnames. Write repo-relative paths, and use `host.example.ts.net` in tests;
- session IDs, chat or Slack links, and quotes from private sessions, chats or calls;
- issue numbers, links and suggested branch names from a private issue tracker;
- teammates' names attached to their plans, opinions or internal discussions, and private repos or branches;
- quotes of, or citations to, internal guides and rules. Say what the code does and why on its own terms;
- agent handoff notes (`REVIEW-TO-PARENT.md` and similar), raw evidence, logs and benchmark dumps;
- generated videos and strips nothing links to. Commit the stills a doc shows.
