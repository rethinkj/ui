# rethinkj UI

A native, GPU-rendered UI framework for Java, modelled on [rune](https://github.com/anomalyco/rune) (Rust, MIT). Rune is the reference for scope and concepts: its own renderer, text, layout and animation, plus a headless mode in which an agent can render to PNG, dump the element tree and drive an app with scripted input.

Status: early. `core` runs an app with and without a window: element tree, flexbox layout, text (shaped with HarfBuzz, rasterised with FreeType, with fallback fonts), springs and fading, shadows, clipping and scrolling with scrollbars, lists that build only the rows in view, overlays for menus and dialogs, pointer, wheel and keyboard input with focus, hover and pressed looks and drags, single-line text fields, work off the app's thread, a CPU reference renderer and a GPU renderer that is checked against it, PNG, scripts that drive an app, and SDL windows. `kit` has a theme, icons and components up to a data grid, a tree, tabs, split panes, menus and dialogs; `examples` has runnable apps, among them a schema browser. The native libraries (SDL3, wgpu-native, FreeType, HarfBuzz) are packaged per platform and loaded on demand.

- Repository: https://github.com/rethinkj/ui
- License: MIT

## Targets

- Desktop only: Windows 11 or later and Linux. macOS, web and mobile are not targets.
- Runs on an ordinary JRE. GraalVM native image is not a goal, but it has to stay possible. That means:
  - `core` and `kit` depend on `java.base` only. No `java.desktop`: no AWT, no ImageIO, no `java.awt.Font`.
  - No reflection, dynamic proxies or classes generated at run time, in this code or in anything it depends on at run time.
  - Native code is called through the Foreign Function & Memory API only, not JNI or JNA. Every native function's descriptor is a `static final` constant, so it can be registered for native image.

## Build

Requires JDK 25 and Maven 3.9+.

```sh
mvn verify                # build and test everything
mvn -pl kit -am verify    # one module plus the modules it depends on
```

Image tests compare what `Headless.render` produces with the PNG and tree files under `core/src/test/resources/golden`. After a deliberate change of the output, rewrite them with `mvn -pl core -am test -Dgolden.update=true` (`-am` builds the natives module that core tests with) and look at the images before committing. A failing image test leaves the expected image, the actual image and their difference in `core/target/golden`.

The layout is tested against Taffy's flexbox cases in `core/src/test/resources/taffy`; `scripts/import-taffy-fixtures.sh` refreshes them.

On Windows and Linux, the first build downloads the native libraries (see below) and needs network access; later builds, `mvn clean` included, do not. On Linux it also builds SDL, FreeType and HarfBuzz from source, which takes about a minute and needs cmake, make, a C and a C++ compiler, pkg-config, tar with xz, and the development packages listed in `natives-linux-x64/natives.properties`. On Windows it builds FreeType and HarfBuzz from source, which takes one to three minutes and needs Visual Studio's C++ tools (see "Native libraries"). `mvn verify -P '!natives-<platform>'` builds without them and skips the tests that load them.

## Driving an app with a script

`com.rethinkj.ui.Script` drives an app without a window: a script of steps goes in, images and trees come out. An app's `main` passes its arguments to `Script.handle(args, app)`; with `--script <file> --out <folder>` that runs the script, prints the files it wrote and returns true, and without them it returns false and `main` opens the window. `Script.run(text, app, folder)` does the same from Java. On a mistake it throws `Script.Failure`, which names the line and says what to write instead; uncaught, the program exits with status 1.

One step per line. A `#` at the start of a line or before a space starts a comment.

| Step | What it does |
| --- | --- |
| `size <width> <height> [scale <factor>] [at <x>,<y>]` | Sets the window size in logical pixels and the physical pixels per logical pixel (default 1), and with `at` where its top left corner lies on the script's screen, in physical pixels (default 0,0). Needed before the first `frame`; for another window (`window`), it changes that one. |
| `window <name>` | The steps after it go to this window: `main` for the first, else the title a handler opened a window with (`App.windows()`), quoted if it has spaces, as in `window "Note 2"`. See "Several windows". |
| `close` | Asks the chosen window to close, as its close button does: runs its close handler (`Windows.Handle.onCloseRequest`) as input of its app, else closes it. |
| `press <target> [clicks <n>] [shift] [control] [alt] [meta]` | Pointer down and up on the target. `clicks 2` is the second press of a double press, `clicks 3` of a triple one; the modifiers are held during the press, as in `press #name shift`. |
| `press <target> right` | The same with the secondary (right) button, without clicks or modifiers: it runs the handler of `El.onSecondaryPress` with the position, where a context menu opens. `down <target> right` and `up <target> right` are its halves. |
| `down <target> [clicks <n>] [shift] [control] [alt] [meta]`, `up <target>` | The two halves, for a press that ends elsewhere. A press counts only when both land on the same element. Between them, `move` drags an element with a drag handler (`El.onDrag`) once the pointer is more than 4 pixels from where it went down, and then the press does not count. In a text field, `move` in between selects by dragging, from the first pixel, and drags no element around the field; on a scrollbar's thumb it drags the thumb, also from the first pixel. |
| `move <target>` | Moves the pointer onto the target, which hovers it and the elements around it. Presses do not move the pointer. |
| `leave` | The pointer leaves the window: nothing is hovered. |
| `wheel <target> <deltaX> <deltaY>` | Turns the wheel with the pointer on the target, by these distances in logical pixels; positive scrolls down or right. Along each axis the innermost scroll area under the pointer that can still move that way takes the whole distance, up to its end. |
| `scroll <target> row <index>` | Scrolls the list of rows (`El.rows`) at the target, or the one around it, so that the row `<index>`, counted from 0, is at its top, or as far as the end of the list allows. |
| `key <name> [shift] [control] [alt] [meta]` | Presses and releases a key with these modifiers held, as in `key Tab shift`. Keys have the web's key names (`Enter`, `Tab`, `Space`, `Escape`, `ArrowDown`, `F5`), and a key that types a character is named by it in upper case (`A`, `1`); the Javadoc of `com.rethinkj.ui.Key` lists them all. |
| `type "<text>"` | Text input for the focused element (`\"`, `\\`, `\n` for a line feed and `\t` for a tab inside). |
| `compose "<text>"` | The composition of an input method in the focused text field: shown underlined in place of the selection, not yet in the field's string. `compose ""` ends it; a `type` commits text. |
| `clipboard "<text>"` | Puts the text on the app's clipboard, where a paste takes it from. Needs no `frame`. |
| `focus <target>` | Gives the keyboard focus to the target, or the nearest focusable element around it, as Tab would. |
| `advance <seconds>` | Moves the app's clock; the actions the app asked for with `App.after` that are due then run at the next `frame`. |
| `await [<seconds>]` | Waits until the work the app started on other threads (`App.background`) has delivered or was cancelled, at most 10 seconds unless it says otherwise, and queues what it and other threads posted for the next `frame`. Posted tasks reach a script only here (see "Work off the app's thread"). When work still runs after the timeout, it fails and names that work. |
| `frame` | Runs one frame: the handlers and scrolls that input queued, a rebuild of the view, the animations at the current time. |
| `snap <name>` | Writes `<name>.png` and `<name>.tree.txt` of the last frame into the output folder, and `<name>.clipboard.txt` with the text on the app's clipboard if there is any. `<name>` may contain `/` but must stay inside the folder. With several windows open, each other window's frame goes under its title in lower case with hyphens before the name: `groceries-<name>.png`. |

Only `frame` runs a frame, as in a window, where input arrives between frames: `press`, `move`, `leave`, `key`, `type`, `compose`, `focus`, `wheel` and `scroll` queue what they do, `await` queues what other threads delivered and `advance` moves the clock, but the screen changes at the next `frame`. The frame dispatches the queued input in order, each against a tree built from the state the input before it left: after an input that a handler took, it builds the view again before the next, so two `key ArrowDown` before one `frame` move a selection by two rows, a `key` after the `press` that opened a menu goes to the menu, and a `press` after one that dismissed a menu finds no menu there. `snap` refuses to write a frame that does not show the steps before it. Scripts use an in-memory clipboard, the app's default; only a window gives the app the system's.

A `.tree.txt` has one line per element, children indented, with its rectangle in window coordinates as shown, that is, moved by the scroll offsets above it. After the rectangle come the element's states, what the app's state is, with their names from WAI-ARIA, only those that are set and always in this order: `disabled`, `readonly`, `password` (a masked field; there is no WAI-ARIA name for it, so it is UI Automation's `IsPassword`), `invalid` (a value that is not accepted, WAI-ARIA's `aria-invalid`), `selected`, `current` (the cursor's cell or row among the selected ones, WAI-ARIA's `aria-current`), `grabbed` (what is being dragged, WAI-ARIA's `aria-grabbed`, as a tab on its way to another place), `checked` (or `checked=false`, `checked=mixed`), `expanded` (or `expanded=false`; absent where nothing opens), `level=<n>` (from 1), `pos=<n>/<size>` (the position in its set, from 1, and the set's size), `sort=ascending` or `sort=descending`, and `value="<text>"`, as in `el #row-8 role=treeitem label="created_at" 8,184 264x22 selected level=5 pos=2/3`. The view sets them with `El.disabled(boolean)`, `invalid(boolean)`, `selected(boolean)`, `current(boolean)`, `grabbed(boolean)`, `checked(boolean)`, `checkedMixed()`, `expanded(boolean)`, `level(n)`, `position(n, size)`, `sortAscending()`, `sortDescending()` and `value(text)`; they change nothing about how the element looks or takes input. A text field's `disabled` (`editable(null)`), `readonly` (`readOnly()`) and `password` (`masked()`) come from the field, and each row of a list of rows (`El.rows`) has its index plus 1 among all rows as `pos` unless its row function sets another, as in `el #row-765436 role=row 8,119 964x22 selected pos=765437/1000000`. A scroll area that is scrolled adds its offset after the rectangle, as in `el #list role=list 16,16 208x168 scroll 0,90`. A list of rows (`El.rows`) adds before that the rows that exist, first and last, and how many rows it has, as in `el #rows role=grid 16,44 248x160 rows 765429-765440/1000000 scroll 0,21432096`, or `rows -/<count>` when none exist; its children are those rows in order. A line that ends in `exiting` is an element with a key and motion that a rebuild left out: it fades out where it was, takes no input, and is removed once invisible. Selectors do not match it, nor anything at opacity 0. The line of the element that a press under the pointer would go to ends in `hovered`, during a drag that of the dragged element, during a selection by dragging that of the text field and over a scrollbar or while its thumb is dragged that of the scroll area, and that of the element that has the keyboard focus in `focused`. A focused text field adds its caret as an index into its string, then the other end of a selection and an input method's composition: `text #name role=textbox label="Table name" "SELECT name FROM customers" 40,26 160x28 focused caret 17 anchor 26 composing "ni"`. A multi-line field adds, before its scroll offset, the lines that have a row in its content box, counted from 1, and how many lines it has, and after its caret the caret's line and column, both from 1, the column in UTF-16 units: `text #query role=textbox label="Query" "SELECT *\nFROM orders\nLIMIT 20;" 253,44 455x82 lines 1-3/3 focused caret 31 (3:9)`, or `lines 49998-50002/100000 scroll 0,899964` in a long text. A masked field shows its mask instead, one `•` per grapheme, with the caret, the anchor and the composition in it: `text #password role=textbox label="Password" "•••••••" 104,246 260x24 password focused caret 6 anchor 7`.

The overlays shown above the tree (see Overlays) follow it, in the order they are drawn, each under a line that starts with `overlay`, says where it is placed and ends with what it is anchored to, its key, role, label and rectangle as shown; the overlay's tree follows, indented by two spaces, in window coordinates:

```text
overlay at 120,85 bottom start on #list role=list label="Tables" 16,16 208x146
  el #menu role=menu 120,85 81x86
    el #open role=menuitem label="Open" 125,90 71x24 focused
overlay right start gap 6 on #export role=menuitem label="Export" 125,116 71x24
  el #formats role=menu 53,116 66x60
overlay center modal scrim on 0,0 240x200
  el #dialog role=dialog label="Delete" 34,55 172x91
```

An overlay placed against an edge of the window, as the kit's toast is, says so the same way: `overlay edge bottom center gap 16 on 0,0 360x240`.

Keys go to the focused element and then up through its ancestors until a key handler takes them; without focus only the root gets them. If none does, Tab and Shift+Tab move the focus through the focusable elements in tree order, around at the ends, and Enter and Space press the focused element. A press focuses the focusable element it lands in and clears the focus elsewhere, unless it lands in an element with `El.keepFocus()`, which leaves the focus where it is, with its ring (the button that shows a password leaves it in the field). `focusable().keepFocus()` is an element that only the keyboard focuses: Tab reaches it and Enter and Space press it, but a press leaves the focus where it was. The kit's buttons, toggles, checkboxes, selects, tab bar and split dividers are made so; text fields, the data grid, the tree and menus take the focus when pressed. Focus moved by the keyboard or by `focus` is drawn with a ring and scrolls into view; a press shows no ring. The ring lies 2 pixels outside the element's border box, or `El.focusRingGap(pixels)` beyond it, with what lies behind the element showing in the gap (the kit's primary button, whose fill is the accent its ring has), or just inside it, without a gap, where a clip around the element or the window's edge would cut it, as around a grid that fills a pane; it is clipped like the element, so an element scrolled half out shows half a ring. When a rebuild leaves out the focused element, or it can no longer take the focus, the focus goes to the nearest element along its old identity path, below the root, that takes the focus or holds one that does, then to that one, the first in tree order (`App.focused` says so): closing the active tab from its content puts the focus into the next tab's content, and an editor laid over a cell gives it back to the grid when it goes. With nothing focusable around it below the root, the focus is cleared and keys reach only the root. The ring stays as it was, so a focus that a key moved away shows it in its new place. `El.autofocus()` makes an element take the focus in the build that adds it, the first such in tree order (the editor that Enter lays over a cell), with the ring if the focus had one; `autofocus(key)` also takes it whenever a build gives it another key than the build before (the first field with an error, keyed by the count of Save presses). Among the elements a lost focus goes to, an `autofocus` one comes first. Besides `El.whenFocused`, `El.whenFocusWithin(look)` is a look for while the focus is on the element or inside it, as CSS's `:focus-within`, also in the rows of a list.

A target of `press`, `down`, `up`, `move` and `wheel` may also lie in another window, `in <window> <target>`, as in `move in Groceries #text`, or be a point of the script's screen, `screen <x>,<y>` in physical pixels, which goes to the window that lies there. Between `down` and `up`, `move` and `up` go to the window the press began in, wherever the target is, as the system's capture of the pointer has it.

A target is a position `x,y` in logical pixels, or a selector for exactly one element of the last frame: `#key` (anywhere in the tree and its overlays), `role=<role>`, `label="<text>"` (`\"` and `\\` inside), `text="<string>"` (see Text), a state as a `.tree.txt` writes it (`selected`, `current`, `grabbed`, `disabled`, `readonly`, `password`, `invalid`, `checked`, `checked=false`, `checked=mixed`, `expanded`, `expanded=false`, `level=<n>`, `pos=<n>/<size>`, `sort=ascending`, `sort=descending`, `value="<text>"`; `checked=true` and `expanded=true` also do), or several of them, as in `role=switch label="Lights"` or `role=treeitem expanded label="public"`. A selector presses the centre of the element's rectangle. When it matches nothing, the error lists the keys, roles, labels and states there are, and the texts if there are any, and the lists of rows with the rows that exist, since a selector finds only those; when only its states match nothing, it lists the lines of the elements that match the rest, which show their states; when it matches several, it lists them with their rectangles.

## Text fields

`El.text(value).editable(onEdit)` makes a single-line text field, and `.multiline()` after it one of several lines (see the points on multi-line fields below). The string belongs to the app: the view builds the field with the current value, and every edit hands the new string to `onEdit`, which stores it in the state. A handler may refuse an edit (store nothing) or change it (keep only digits, say); the field then shows the app's string, with the caret where it was before a refused edit, and otherwise at the same distance from the text after it or before it, whichever the change left alone. A value the app changes on its own keeps the caret near its text and ends the undo history.

- `App` keeps per field, by the element's identity as for scroll offsets: caret and anchor (indexes into the string), horizontal scroll, undo history (100 steps; a run of typing, a run of deleting, a paste or cut each one step; moving the caret ends a run) and an input method's composition. A step holds the edit, where it replaced what by what with the caret and anchor before and after, never a copy of the string; undo comes back to the selection of the moment before, redo to the one before the undo. An edit the app changes becomes one step from before it to what the app made. The editing core is `Editor`, package-private; it works on strings and does not assume one line except where a single-line field turns line breaks into spaces and Home and End go to the ends.
- What `App` keeps by identity it forgets when the field leaves the tree, as the content of a tab that is not active does. `El.fieldState(FieldState)` keeps it in an object of the app's state instead, in the manner of `Menu.State`: the field's `Editor` lives in the `FieldState`, so caret, anchor, scroll of both axes (saved as the field leaves and set again in `Editor.placeLines` as it returns, also where another field had the same identity), undo history and Tab's mode (`tabIndents`, Control+M) come back with it, and with them the `Lines` and the highlighter's spans: going back to a tab with 100 000 lines (3.5 MB) costs about 0.25 ms (`FieldStateTest` prints it). A string the app changed meanwhile ends the history, as any change of the app's does; a composition ends as the field leaves. Two fields of one build with one `FieldState` throw when the view is built. `CodeEditor.State` holds one. A field that moves to the tree of another `App` of the same state, as a tab to another window, takes it with it, whichever app builds first. `FieldStateTest`.
- The caret stops only at grapheme boundaries (`BreakIterator.getCharacterInstance`): never inside a surrogate pair, between a letter and its combining mark, or inside an emoji sequence; Backspace removes a grapheme. Words (Ctrl+arrows, Ctrl+Backspace, Ctrl+Delete, double press) are segments of `BreakIterator.getWordInstance` with a letter or digit, which takes `shop.public.orders` for one word; with `El.codeWords()`, which `TextField.codeArea` and `CodeEditor` set, a word is a run of letters, digits, marks and `_`, a run of spaces and tabs is one segment for a double press, and every other character one of its own (`Editor.codeWord`, `codeWordLeft`, `codeWordRight`, scanned from the caret without a `BreakIterator`). Ctrl+Right and Ctrl+Delete go to the end of a word on Linux and to the start of the next one on Windows (`Editor.WORD_ENDS`), so scripts with stored images avoid them.
- Keys: arrows, Home, End, with Shift to select and Control by words; Backspace, Delete; Control+A, C, X, V, Z, Y and Control+Shift+Z; Control+Insert, Shift+Insert and Shift+Delete. Keys that type are the field's (their text comes with `textInput`); Enter, Escape, Tab and unknown shortcuts go on to the `onKey` handlers. The field's own `onKey` sees every key first. While an input method composes, it has the keys. Tab into a single-line field selects its text; into a multi-line one it leaves caret and selection as they are.
- Pointer: a press places the caret at the nearest boundary, a drag selects (beyond the edge it scrolls, one step per pointer move), a second press (`clicks 2`) selects a word and drags by words, a third everything (in a multi-line field the line with its line feed, dragging by lines, and a fourth everything), Shift extends. `App.pointerDown(x, y, clicks, modifiers)` takes what the window reports. A press in a field is the field's, even inside an element with `onPress` or `onDrag`: moving from it selects from the first pixel, without the drag threshold, and never becomes a drag of an element around the field, which can be grabbed outside the field instead. Until the release the field counts as hovered and pressed (`El.whenPressed`) and keeps its cursor, wherever the pointer is, as a dragged element does. A selection has nothing to cancel: if the field leaves the tree or the release gets lost, it stays as far as it got.
- Caret positions come from the shaped `GlyphRun`: at the pen position of the glyph that starts the next cluster, so kerning counts, and inside a ligature (Inter's `->` with `.fontFeatures("+calt")`) in proportion to the graphemes before it. JetBrains Mono draws its ligatures with one glyph per character, so its carets are plain.
- Drawing: `Text.selection()` behind the glyphs, `Text.composition()` (the underline) and `Text.caret()` after them, all ordinary rectangles with edges on whole physical pixels, clipped with the glyphs to the content box across and the padding box from top to bottom; the glyphs move left by `Text.scroll()`, which keeps the caret in view with `Editor.MARGIN` (4 logical pixels) to spare when the text is wider than the field. Without the focus a field shows its start, no caret and no selection, and forgets its scroll; a window that loses the focus leaves all that as it is and only hides the caret (next point). The line is centred vertically; layout measures a field as 0 wide, so its style gives the width.
- The caret blinks on the app's clock, on for `App.BLINK` (0.5 s), off as long, and restarts on after each change; `frame()` returns true only when it turns, and `App.nextChange()` says when that is, which `WindowLoop` waits for. While the window is inactive (`App.windowActive(false)`, which `WindowLoop` passes on from the window's focus events) there is no caret and nothing blinks; focus, selection and ring stay as they are, and activation turns the caret on.
- `.masked()` (or `masked(boolean)`, which the view sets on every build) shows one mask character per grapheme, `Text.MASK` (U+2022, which Inter and JetBrains Mono have) unless `.maskCharacter(c)` sets another; the string is still the app's. Caret and selection are indexes into the real string at its grapheme boundaries, and grapheme `n` stands at mask glyph `n`: `Text` shapes only the mask (with the composition masked in it) and maps positions between the two (`toGlyphs`, `fromGlyphs`), so `Editor` works on the real string as before. Copy, cut, Control+Insert and Shift+Delete do nothing and leave the clipboard as it was; paste works. Word keys and a double press take the whole string as one word. `Text.string()` returns the mask, so the dump, selectors (`text="…"` matches the mask, never the value), `Script`'s errors and every message built from a `.tree.txt` line see only it; the dump shows the state `password` and caret, anchor and composition in the mask. The real string stays in the app's state, the element's `Text` (`value()`, package-private), the `Editor` and its undo history, as it would in any field. `App.inputArea().password()` makes `WindowLoop` start text input for a hidden password (`SDL_TEXTINPUT_TYPE_TEXT_PASSWORD_HIDDEN`, starting text input again when it changes), which SDL 3.4 passes on only on Wayland, as text-input-v3's purpose `password` with `hidden_text` and `sensitive_data`; on Windows and X11 the input method composes as in any field, and the composition is masked. Building the field without `masked` shows the string, and caret, selection, scroll and history stay, as they belong to the identity; it is then an ordinary field that copies. `MaskedFieldTest` checks all this, also that `Font.shape` never sees the string (`FontProbe`).
- `.readOnly()`: focus, selection and copy, no edits; it shows a caret and takes no text input. `editable(null)` disables the field: no focus, presses go to its ancestors. A `.tree.txt` says `readonly` or `disabled` after the field's rectangle without a call of `El.disabled`. `.maxLength(n)` limits typed and pasted text to `n` code points, cut at a whole grapheme. `.placeholder(text, argb)`, `.caretColor(argb)` (the text colour unless set), `.selectionColor(argb)`.
- The clipboard is `App.clipboard()`, a `Clipboard`: `Clipboard.inMemory()` at first, which scripts and tests use, and the system's (SDL) once a `WindowLoop` runs the app.
- `App.inputArea()` is the focused field's box and caret for the system's input method, or null when the focused element takes no text; from a primary press that lands in an editable field until the frame that dispatches it, it is that field's, since SDL makes text events only while text input is on, and a character typed before that frame would otherwise come as a key alone and be lost (`WindowLoop` asks again right after the press); `WindowLoop` turns the window's text input on with it (`Window.textInputArea`) and off without (`Window.stopTextInput`), so an on-screen keyboard shows only for a field. Compositions arrive as `WindowEvent.TextEditing` and go to `App.textComposition`; the window asks SDL to leave drawing them to the app (`SDL_IME_IMPLEMENTED_UI=composition`).
- A field in a row of a virtual list (`El.rows`) gets its editor when the list builds the row, by the row's index. The editor goes when the row leaves the rows that exist, as everything else the app keeps of a row, except the focused field's: it stays with the focus and comes back with the row, without its composition.
- Multi-line fields (`.multiline()`): the string has a line feed per line break. Carriage returns, with or without a line feed after them, and U+2028 and U+2029 become line feeds in typed, pasted and composed text and in the app's value, which the field shows and edits so (`Text.string()` and the dump see line feeds); the app's string keeps them until the first edit, which hands it the string with line feeds only. `.masked()` and `.multiline()` refuse each other with a message.
- Keys of a multi-line field, besides those above, which work across lines (Ctrl+Left goes over a line feed, Backspace at a line's start joins it to the one before): Enter and Shift+Enter break the line, and the field takes them, so an ancestor's Enter does not run, read-only or not; Control+Enter (and Alt, Meta) go on to the `onKey` handlers, so an app runs a query with it. Up and Down move by a row on screen, Page Up and Page Down by the rows the content box holds and scroll as far, all keeping a goal x in pixels that a horizontal move or an edit resets; above the first row Up goes to the start of the text, below the last Down to its end. Home goes to the start of the row, and on the first row of a line a second Home to the first character that is not a space or a tab, a third back; End to the end of the row, which for a wrapped row is before the space it wraps at (there is no caret affinity, so a caret at a wrap stands at the start of the next row). Control+Home and Control+End go to the ends of the text. All with Shift to select.
- Tab in a multi-line field moves the focus, unless `.tabIndents(spaces)`: then Tab puts a tab, or with `spaces` spaces up to the next stop, in place of a selection inside a line, and with a selection across lines indents each but empty lines by a tab or `tabSize` spaces; Shift+Tab takes up to one of those from the start of the caret's line or each selected line. A selection that ends at the start of a line leaves that line out, and a position at the start of a line stays there; each indent is one step of the history. Escape and then Tab (or Shift+Tab) move the focus, and Control+M switches Tab between moving the focus and indenting until it is pressed again; a read-only field leaves Tab to the focus. `.tabSize(n)` (4) sets the tab stops: a tab advances to the next multiple of n spaces of the font, from the start of its line, which `Text` does by shaping a space in its place and widening that glyph (`GlyphRun.tabbed`), so carets and selection on both sides follow.
- Layout and scrolling of a multi-line field: it is a scroll area of its own (`overflow-y: scroll`, and `overflow-x: scroll` unless it wraps), so the wheel scrolls it while it can and its ancestors beyond, `.scrollbars(look)` gives it bars that drag and page as any area's, `App.scrollTo` and the dump's `scroll x,y` work, and the offsets stay with its identity. Its rows start at the top of the content box and are clipped to the content box both ways, so they scroll by under the padding. Layout measures it 0 wide and `.lines(n)` (1) lines high, so a field without a height in its style is exactly n lines high at every scale. `.wrapText()` breaks lines at the content box's width (no horizontal scrolling); `wrapText(false)` lets them be as long as they are and the field scroll sideways, the width being the widest line shaped so far plus room for the caret, which grows as longer lines come into view, as in editors. An edit or a move of the caret scrolls just far enough to show the caret's row whole and the caret with `Editor.MARGIN` to spare sideways; the wheel and the bars may scroll it out of view, and the next key or edit brings it back. Without the focus it keeps its scroll, and shows neither caret nor selection.
- Selection of a multi-line field: one rectangle per row in view; on a row whose end is selected, its line feed or the end of a wrapped row, it reaches the right edge of the content box, as editors show a selected line break; an empty line in the selection is a full-width rectangle. There is no current-line highlight: it would need a background per row before the selection, which `Scene` draws from `Text.selection()` alone. `App.inputArea()` gives the caret's row (the field's x and width, the row's top and height, clamped into the field), with the caret's x as the cursor.
- Large texts: `Text` of a multi-line field shapes and lays out only the rows in the content box and three more above and below (`Text.lines()` holds those, their baselines moved up by the vertical scroll), however long the text. The field's `Editor` keeps `Lines`: the line starts as a sorted array, found by binary search and changed by each edit in place (the starts after it move by the difference, an `arraycopy` and an addition per later line: about 0.1 ms for 100 000 lines, less than the copy of the string the edit makes), and, while wrapping, the rows each line takes in a Fenwick tree: measured once shaped at the width, estimated from the length and the font's average advance until then, so that the row at a height, a line's height and the text's height cost a logarithm. An edit that changes the number of lines rebuilds the tree in one pass; another width, font or size forgets what was measured. When layout measures rows above the view for the first time, the view moves by as much, so what is in view does not jump; the thumb moves a little instead. The grapheme iterator of the JDK reads its whole text when set (about 110 ms for 5 MB), so the editor asks it about the line of a position alone. `TextAreaLargeTest` counts the lines shaped per frame (at most 28, from a counter in `Lines`) and prints timings, here alone on a desktop with 12 threads (under the load of a full build up to five times as long): with 100 000 lines of about 40 characters (4 MB) a typed key with its frame takes 2 to 7 ms, Enter with a key 3 to 12 (two edits, and one more line to put into the starts), Page Down under 1, a wheel step 0.1; single runs of Control+End and Control+Home took 0.1 to 8, of Control+A and Delete 0.1 to 11, and the undo of that 4 to 8, the larger ones with a garbage collection in them. Each edit still replaces the app's string: with 5.3 MB the copy with one more character takes 1.5 to 4 ms and allocates about two copies of the string (10 MB), and a key with its frame 2 to 3 ms. The next step, if that ever is too slow, is a document the app holds instead of a string (a piece table or rope behind a `CharSequence`), which `Lines` and the editor's edit steps already fit: they speak of offsets and replaced ranges, not of strings.
- Highlighting: `El.highlight(key, highlighter)` colours ranges of a text and sets them in other fonts of its size. A `Highlighter` gets a line, the state the line before ended in (null for the first) and a `Spans`, on which it calls `color(from, to, argb)`, `font(from, to, font)` (the font as given: give it the fallbacks the text needs), `background(from, to, argb)`, `underline(from, to, argb)`, `strike(from, to, argb)` (a line through the middle of the lower-case letters, as thick as an underline, behind the glyphs) and `lineBackground(argb)`, and returns the line's end state, compared with `equals` (null for none). A multi-line field asks only about the lines it shapes; `Lines` keeps per line the spans and the state they were given for, and the state each line starts in up to a high-water mark. An edit moves both arrays along with the starts, forgets the spans of the lines it touched and lowers the mark to the first of them, asking nothing; shaping a line at or below the mark first asks about the lines from the mark to it, with spans that keep nothing, and a line whose start state comes out equal keeps its spans. So `/*` typed at the top of 100 000 lines asks about the lines from the top to the view (about 20), and the first view of the end after it asks about every line once: about 30 ms with `Sql` once the JIT is warm, 60 ms cold (`CodeEditorLargeTest`, 4 MB); a jump back and forth then costs nothing. No slicing across frames: at this size a pass is shorter than a frame of a wheel that scrolls far; slicing would be the next step for texts ten times larger. The same key on every rebuild keeps everything; another key asks again. Other text, a single-line field among them, is one line, asked on every build; a masked field and a placeholder are not highlighted. Colours need no shaping: `Text.Line.colors()` holds a colour per glyph, from the colour of the character that starts its cluster, and `Scene` gives each glyph its colour and the correction for that colour. A range in another font is shaped on its own (`GlyphRun.concat` joins the parts, clusters moved to their place in the line), so carets, selection, wrapping and hit testing follow its glyphs; kerning across a font change is lost. Tabs, wrapping, fallback fonts and ellipses keep the colours (an ellipsis has the text's). `HighlightTest` checks all of it.
- Decorations: `El.decorate(decorator)` on a multi-line field: a `Decorator` gets each line in view and a few around it (index, start in the string, text, `Spans`) whenever the rows are laid out, keeps nothing, and gives backgrounds, underlines and the line's background, such as the caret's line, matches of a find, a bracket pair or an error. `Text.marks()` holds them for the rows laid out: line backgrounds across the content box (each row of a wrapped line), then range backgrounds, a line high, then underlines where a composition's underline lies, as thick, the highlighter's and the decorator's alike; `Scene` draws them after the field's fill and before its selection, with the selection's clip. Not in single-line fields. A wavy underline would need a drawing primitive of its own.
- Gutter: `El.gutter((line, caret) -> cell)` on a multi-line field builds a cell per line for the lines laid out, at each line's first row, a line high, in a column `#gutter` that `Editor.placeLines` makes the field's only child once the rows are laid out and scrolled: inside the field's border and padding, clipped to the content box's height, staying in place sideways and moving up and down with the text (the column is placed where the scroll that shifts the field's children brings it back). Layout treats a text element as a leaf whatever children it has. The column is as wide as the cell of the last line laid out at its natural width when `El.scaleText` runs (or as the cells set), and the field's left padding grows by as much, so text, carets, hit testing and the input area start after it. Cells are built again only when the lines laid out, their places, the scroll or the caret's line change (not for a blink); without a key they are `line-<index>`. Presses reach a cell's handlers; elsewhere in the column they focus the field. No hover or pressed looks on cells (they are built after the looks are applied), and `Headless.render` without an `App` draws no gutter. `GutterTest`.
- Documents: `.fitLines()` makes a multi-line field exactly as high as all its rows at its width, so it never scrolls up and down (every row is shaped), and `El.skipTab()` lets Tab pass a focusable element by while a press and `App.focus` still focus it: a read-only paragraph that selects and copies between the links Tab reaches. `El.range(from, to)` on a child of a multi-line field lays the child over those characters of the field's string instead of where layout would put it: its rectangle in the dump is the bounding box of the rows the range takes, but it is hit, filled (behind the glyphs) and ringed only on those rows, one rectangle per row (`El.rangeBoxes()`), placed after layout and again after the field's editor scrolls. It takes presses, cursor, hover looks and the focus like any element, and a press on it is its own, not the field's; Enter presses it when focused. A script's selector presses the middle of its first row. That is how a link is made: a range child with `role=link`, a label, `focusable()`, `cursor(POINTER)` and `onPress`, so that `press role=link label="…"` and Tab reach it. Ranges are a child rather than part of `Spans`, because a link needs an identity for the focus, a handler and a line in the dump, also for lines no highlighter has been asked about. `RangeTest`.
- Caret and selection for the app: `El.onSelect((caret, anchor) -> …)` is told the caret and the anchor whenever they changed: `App` asks each editor after every input and after the rebuild at the end of a frame (which it builds once more when a handler was told), so a refused edit and the app's own change of the string are told too, and a new field tells where its caret starts. `App.edit(field, from, to, text, caret)` replaces a range and puts the caret there as one step of the history, through `onEdit` as typed text, with the field's limits; `App.undo(field)` and `App.redo(field)` step through the field's history as Control+Z and Control+Y do, for an Edit menu; `App.select(field, caret, anchor)` selects and scrolls into view. Both take a field of the last frame's tree and run right after the handler that calls them, as `App.scrollTo` does, in the field of the same identity. An overlay with `.atCaret()` is placed beside its anchor field's caret, a line high, instead of the anchor's rectangle (`Editor.caretBox`), again after the editors are placed, so it follows the caret without a rebuild. `CaretTest`.
- `FieldTest` and `FieldGeometryTest` drive fields through `App`, `FieldRowsTest` drives them in the rows of a list and in a scroll area; `EditorTest` checks boundaries and needs no native libraries. `TextAreaTest` drives the keys of multi-line fields, `TextAreaPointerTest` presses, drags beyond all four edges, the wheel and the bars, `TextAreaLargeTest` 100 000 lines and 5 MB; `LinesTest` checks the line starts and rows against a fresh count after random edits, without native libraries.

## Overlays

A menu, a tooltip, a dropdown list or a dialog lies above everything else and is not clipped by the scroll area its anchor is in. The view declares it next to the element it belongs to, `anchor.overlay(menu)`, so that a component returns its anchor with what it opens attached; whether it is open is the app's state, as all state: `button.overlay(s.menuOpen ? menu : null)`. An overlay is an ordinary tree with layout, text, scrolling, motion and presence: its identity is the anchor's plus its key or index among the anchor's overlays, counted apart from the children, so one with a key and `motion` fades in as it opens and out as it closes. `El.overlays()` lists an element's overlays; after a frame, the root's `El.shownOverlays()` lists those shown, in drawing order, in window coordinates.

- Placement, after layout (`Overlays`, package-private): each overlay is laid out as a root of its own, at most as large as the window (its max size is limited to it; one with `scroll()` then scrolls), and placed beside its anchor's rectangle as shown, moved by the scroll offsets above it. `.side(Side, Style.Align, gap)` (default `BOTTOM`, `START`, 0) puts it on a side, aligned `START`, `CENTER` or `END` along it, or `STRETCH` for at least as wide as the anchor (a select's list); `.atPoint(x, y)` takes a point of the window instead of the rectangle (a context menu at the pointer); `.atCaret()` the caret of the anchor, a text field (completions; see Text fields); `.centerInWindow()` a dialog; `.atWindowEdge(side, align, gap)` lies against an edge of the window, `gap` away from it (a toast at the bottom). Where it does not fit, it goes to the other side, then to the other end along the side, then moves into the window as far as it needs; a tooltip (below) keeps its gap from the window's edges too where there is room, so that it does not sit flush with them. An overlay inside one that went to the other side than it asked tries that other side first when it asks the same side, so submenus go on to the left once one flipped at the window's right edge. An overlay that a delayed look attached (`whenHoveredFor`, `whenFocusVisibleFor`: a tooltip) and that would cover its anchor goes to a side across where one has room: under the pointer it would take the hover from its anchor and hide again. Positions are whole logical pixels. It is placed again in every frame that scrolls, moves or builds rows, so it follows its anchor.
- An overlay shows while its anchor shows. When the anchor is clipped away entirely (scrolled out of its area), made invisible by the view or leaving, the overlay is neither drawn nor hit, and stays open; an anchor that fades in counts from its first frame, as for the focus, so a submenu that a key opens in the frame its menu appeared in shows and takes the focus: the state is the app's, and the core never closes anything. In practice the wheel closes menus first (below); a programmatic scroll leaves them hidden until the anchor is back.
- Drawing (`Scene`): after the whole tree, in the order the overlays opened (the animator counts when an identity first appeared; a submenu opens after its menu, and ties keep tree order), each as a tree of its own from clip entry 0, so free of the anchor's clips and opacity, with its own (rounded) clips. `.scrim(argb)` draws a rectangle as large as clip entry 0 in that colour before the overlay, at its opacity. No new instance kind: order and clip indices only. An overlay's shadows (`El.shadow`, see GPU renderer) come with it, under it and free of the anchor's clips like the rest of it; the kit lifts its overlays with them and keeps a border from its tokens.
- Hit testing: overlays first, the topmost first; within a tree it descends from the root to the last child whose box holds the point, so a child is hit only inside its parent's box, also where the parent does not clip (`App`'s Javadoc says why); a hit inside an overlay goes no further than its root: press and drag targets, hover looks, the cursor and the scroll areas the wheel moves are those of the overlay, never its anchor's. Hover belongs to the topmost thing under the pointer.
- A press outside: the overlays above the first one the press lands in get their `.onDismiss` handler called, the topmost first. If the press lands in an overlay below them, it goes on there (a press on a menu item closes the item's sibling's submenu and chooses the item). If it lands outside all overlays and one was dismissed, that is all it does: the menu button pressed again closes its menu and does not open it again, and a press beside a menu does no second, accidental action. Overlays without a dismiss handler (a tooltip) let presses through. `El.dismissGroup(group)` on an overlay and on elements outside it (equal by `equals`; the kit uses the component's state object) makes a press on such an element, or inside it, count as landing in the overlays of the group: they are not dismissed and the press goes on to the element, whose handler decides. A menu bar puts its titles and their menus in one group, so that a press on another title switches menus with one click and a press on the open menu's title closes it; dropdowns, context menus, selects and dialogs set no group and dismiss as before. After the overlays, a press outside an element that holds the focus (`El.holdFocus`, below) calls its `onDismiss` handler and goes no further. The secondary button dismisses the same way. The handlers run when the frame reaches the press, in the order of input, and the input after it finds the tree they left.
- The wheel outside a non-modal overlay calls its dismiss handler and scrolls what is under the pointer, as Swing's popups and browsers' select lists close on scrolling: a menu that rode along with scrolled content would cover other content and lose its anchor.
- `.modal()`: input outside it reaches nothing below it. A press there calls its dismiss handler and nothing else (the scrim of a dialog), the wheel does nothing, hover finds nothing, `App.focus` refuses elements outside it, Tab and Shift+Tab go around inside it, and keys go up from the focused element only as far as its root, which gets them while nothing has the focus. Overlays that open above it, such as its select's list, work as usual. An overlay that is leaving no longer blocks. The parts of a frameless window's own frame (`El.windowPart`) stay usable under it: `App.windowPart` looks through it, so the window can still be moved, minimized, maximized and closed, and a press on such a part neither dismisses it nor reaches anything else. Closing the window closes it without the dialog's dismiss handler: dismissing means cancelling the dialog, which the user did not ask for, and the window's close request is where an app would ask whether to close.
- Focus: an overlay that opens moves the focus to its first `El.autofocus` element, else its first focusable element in tree order, without a ring (while it does, elements outside it that ask with `autofocus` get nothing); a modal one without such an element takes the focus away. When it closes, the focus goes back to where it was before it opened, with the ring it had, if the focus is still inside the overlay or nowhere and that element still exists; overlays that close in the same frame give it back the newest first, so that a submenu returns it to its menu and the menu to its button. This happens before the looks are applied, so the focus look shows in the same frame, and in every build of the view, also between two inputs of one frame, so that a key right after the press that opened a menu goes to the menu. Tab walks a non-modal overlay right after its anchor and everything inside the anchor. Overlays attached inside the rows of a virtual list are placed and drawn but do not take or give back the focus; attach a row's menu to the list. `El.keepFocus()` on an overlay opens it without moving the focus (a toast with Undo while the user types); when the keyboard has moved the focus into it and it closes, the focus goes back to where it last was outside it, and on any element makes a press inside it leave the focus where it is, also on focusable elements inside it, except in a text field (a menu bar's titles, so that the menu gives the focus back to the editor). `El.holdFocus()` makes an element hold the focus while the view marks it, as an overlay that opens and closes: the build that marks it moves the focus to it or its first focusable element, the one that unmarks it gives it back, and overlays inside it take it from it and give it back first (a menu bar from Alt or F10 until Escape).
- Keys: from the focused element up to the overlay's root, then on to its anchor and the anchor's ancestors, so that a handler of the menu's owner sees Escape. Escape closes nothing by itself: the overlay's own `onKey` calls the app. The root's handler sees what nobody before it took, which is where the kit's menu shortcuts are: a focused text field's editor takes its own keys (Control+C, Control+V, Control+Z, Control+Shift+Z, Control+A, Control+X, Control+Y, the arrows and the keys that type) before any ancestor sees them.
- The secondary button: `El.onSecondaryPress((x, y) -> ...)` runs when the right button goes down and up on the element or a descendant without such a handler, with the release's position in the window; it focuses as a press does and never drags or selects. `App.secondaryDown/secondaryUp` take it, `WindowLoop` passes the right button there, and the Menu key or Shift+F10 that no key handler takes run the nearest handler at the bottom left of the focused element's cursor: the first element inside it that is `current` (a grid's cursor cell), else the first that is `selected` (a tree's selected row), else the focused element, kept inside its box. That is how an element says where its cursor is: a component with a cursor marks it `current`, or `selected` where only one thing can be selected, as the grid, the tree and the menu do. Scripts write `press <target> right`.
- Delays on the app's clock: `.whenHoveredFor(seconds, look)` is a look that applies once the pointer has rested on the element (or inside it) that long, until it leaves or presses; it may attach an overlay, which is how a tooltip appears. `.onHoverFor(seconds, handler)` runs a handler once per stay (0: in the frame that finds the pointer there), which a menu uses to follow the pointer and to open a submenu after a delay. `.whenFocusVisibleFor(seconds, look)` is the keyboard's counterpart: a look once the element has had the focus with its ring that long, until the focus leaves or a key goes down that does not move it; a tooltip has both. `.onShownFor(seconds, handler)` runs a handler once an overlay has been open that long, once per opening (a toast closes itself). `App.nextChange()` reports when the next one is due, so an idle window wakes for it, and `frame()` returns false while it waits: no frames are presented. A press keeps the pointer's away until the pointer leaves and comes back.
- `OverlayTest` checks placement (submenus going on the way the first flipped, tooltips beside an anchor they would cover, the window's edge), following and hiding, drawing order and clips, dismissing and dismiss groups, modality, focus and keys with `keepFocus` and `holdFocus`, the secondary button, the delays of the pointer, the keyboard and an overlay's time, presence and the dump without text; `WindowPartTest` the frame's parts under a modal overlay; `ScriptTest` runs `overlay.txt` against the stored images `overlay-*`; `GpuRendererTest` compares those and a menu with its submenu across the rounded clip of a scrolled list and a dialog over a scrim at scales 1, 1.5 and 2.

## What a table needs from core

The kit's data grid is built from these; any view may use them. `TableTest` checks each without text.

- Presses: `El.onPress((clicks, modifiers) -> …)` is told the modifiers held when the pointer went down (Shift adds a sort key); Enter and Space give `1, 0`. `El.onPress((clicks, modifiers, x, y) -> …)` is also told where the pointer was released, in the element's content as `Drag.x` and `y` are (the left and top of its border box as shown, plus its own scroll offset), so that a slider's track can put its knob there; Enter and Space give the middle of the border box. `onPointerDown` has the same form, with where the pointer went down. `El.onPointerDown((clicks, modifiers) -> …)` runs as the primary button goes down on the element or inside it, before anything moves, without making the element the target of the press or drag that follows, which may belong to an ancestor; a press on a scrollbar, in a text field or outside an open overlay runs none. `El.onAnyPointerDown(handler)` runs whenever a button of the pointer goes down anywhere in the window, while the element is in the tree or a shown overlay, before the press does anything else and taking nothing from it, also in a text field or on a scrollbar: the menu bar tells Alt alone from Alt held during a press by it.
- `Drag` has `x` and `y`: where the pointer is in the dragged element's content, its border box as the last frame shows it plus its own scroll offset, doubles, so that a drag on a list of rows reads the row under the pointer also while the list scrolls. The wheel's scrolling of the frame that runs a step comes after it.
- `El.fixedX()` keeps an element in place sideways while the nearest scroll area around it that scrolls sideways (`scrollBoth`) scrolls, for drawing and input: frozen columns. It is drawn in tree order, so it comes after what it covers and needs a fill. `El.fix(root)` links such elements after each build, and a list links the rows it builds.
- `El.rows(count, rowHeight, (index, from, to) -> row)` builds each row for the part in view sideways, from `from` to `to` in the content box, which is the visible part (clipped by the window and the ancestors that clip) widened by half its width on each side; scrolling sideways beyond that part builds the rows anew, without the view. The `IntFunction` form builds whole rows as before.
- `El.reveal(key, x, y, width, height)` keeps a rectangle of a scroll area's content in view whenever a rebuild gives it another `key` than the tree before, as `revealRow` does for a row's index: the grid keeps its cursor's column, or a dragged edge, in view without jumping back when nothing moved.
- `El.rows(count, heights, row)` is a virtual list whose rows are each as high as their content at the list's inner width (or their own height), the blocks of a long document: a `RowHeights` the app keeps in its state holds each row's height, estimated by a function of the index until the row is built, then measured by its layout, in a Fenwick tree, so that where a row starts, the row at an offset and the total cost a logarithm. When rows above the one at the top turn out higher or lower, the offset moves by as much, so that what is in view stays; a frame builds the rows again (at most three passes) when the measured heights show other rows than the estimate did. `App.scrollToRow` goes to where a row starts as far as the heights are known. `RowHeightsTest`.
- `El.onRowsBuilt((first, last) -> …)` tells the app which rows a list built, when they change, not on every rebuild; the handler runs after the input of the frame that built the rows, or in the next frame when the rebuild at its end built them, and `App.nextChange()` returns the current time while a handler waits. There is no thread-safe way yet to hand state from another thread to an `App` and wake its window.

## Work off the app's thread

An app, its state and its elements belong to the thread that runs it; `App` is not thread-safe, and only handlers change the state, in the order of the input. A query or a file that takes long runs on another thread, and its result comes back through `App.post(Runnable)`, the one method of `App` that any thread may call. It never blocks. The task joins the queue of input after the input that came before it, the tasks of one thread in their order, and runs on the app's thread as the handler of an input: against the tree the input before it left, and the view is built again before the next input, so a key, a task and a key each see what the one before left, and the frame draws. A task posted while a frame runs, by a handler too, waits for the next frame.

- `App.background(name, compute, onResult, onFailure)` runs `compute`, a `Callable`, on a virtual thread of its own (`Thread.ofVirtual()`, no pool) and posts `onResult` with its result or `onFailure` with its exception. It returns a `Work`: `work.cancel()`, called on the app's thread, keeps both handlers from running, also when the answer already waits in the queue, and interrupts the thread, so the answer of a request the user closed or asked again never arrives. The computation gets only what the handler put in its closure (names, an SQL string, a connection), never the state or elements: the app's thread reads them while it builds the view, and nothing guards them. An `Error` it throws is thrown on the app's thread. Virtual threads do not keep the JVM alive, so work that runs when `main` returns is dropped. The Javadoc of `post` shows the same with a thread of the app's own, in three lines.
- A `WindowLoop` wakes for tasks. It gives the app `Window::wake` with `App.onPost`, which the first post after the app took the ones before it calls: it pushes an SDL event of a type from `SDL_RegisterEvents` (`SDL_PushEvent` may be called on any thread), which ends `Window.waitEvents`. The tasks that arrived until the frame takes them run in that one frame, and a thread that posts nothing costs nothing. On Linux under X11, `WindowLoopTest` measured about 1 ms from a post to its frame; a burst of 1000 tasks that arrives while the loop draws is one frame, and one that arrives while it waits is one or two, as the first task wakes it before the last is there. A task that arrives less than a refresh after the last frame began waits for that refresh, as input does (see GPU renderer), also when it ends the wait for input early, and goes into that refresh's frame.
- Without a window (`Headless`, tests that call `frame()`) a task runs at the next `frame()`. A task that throws ends the frame as a handler that throws does: the exception comes out of `frame()` and the input after it waits for the next frame; a `WindowLoop` ends with it, and a script fails at its `frame` step. After the window has closed, tasks still queue; they run if the app runs frames again.
- Scripts and tests do not wait for the clock on the wall. `App.await(Duration)` waits until the work that `background` started has delivered or was cancelled, then queues what it and other threads posted for the next `frame()`; when work still runs after the timeout, it throws and names it. A script holds every posted task until its step `await`, so a snap shows "Loading…" and, after `await` and `frame`, the answer, however fast the work was. An app whose made-up work sleeps makes it immediate under a script: `Workbench.main` sets its latency to 0 before `Script.handle`.
- What happens later without another thread, a delay or a timeout on the app's clock, is `App.after(seconds, action)`. The action runs as a task does, in the first frame that begins at or after its time, after the input and tasks that came before that frame; `nextChange()` reports it, so an idle window wakes for it, a script runs it with `advance` and `frame`, and `await` does not wait for it. Its Javadoc has the rest; `Workbench` clears a message of its status line with it.
- `PostTest` checks the order of ten threads' tasks, the dispatch rule, cancellation, failures, idle frames and scripts, and `AppTest` the actions of `after` beside tasks and input and under a script; `WindowLoopTest` the wake-up, the frames of a burst and a task posted while input waits for the refresh in a real window; `TreeTest` the kit's tree with a catalog whose staging server answers on another thread.

## Several windows

One `WindowLoop` runs any number of windows on the windows' thread, each with an `App` of its own (view, focus, hover, scroll offsets, animations, clock) and a presenter of its own. `new WindowLoop(window, app, presenter)` and `WindowLoop.run(...)` run one window as before; more open with `loop.open(title, width, height, options, app)` or from a handler through `app.windows()`, a `Windows`, which the loop and a `Script` set on every app they run; an app that no runner runs gets one that refuses to open. `examples/.../Notes.java` shows all of it.

- `Windows.open(title, width, height, Window.options()..., app)` opens and shows a window that runs `app` and returns a `Windows.Handle`: `app()`, `title()`, `isOpen()`, `close()`, `raise()`, `moveTo(x, y)`, `x()`, `y()`, `width()`, `height()`, `screenScale()`, `onCloseRequest(handler)`, `dropTarget(on)` and `window()`, the `Window` for its taskbar button (null in a script). `Window.Options.position(x, y)` places a window where it opens. The loop makes the window's presenter with `loop.presenters(window -> ...)`, a `GpuPresenter` unless set, and gives the app its clipboard, fonts and itself, as to its first app. `Windows.all()` lists the open windows, `of(app)` finds an app's. The state holds the main `App` (as `Workbench` and `DataBrowser` do) and reaches the windows with `s.app.windows()`.
- Shared state: apps that show one state are made with the same state object, as `new App<>(notes, Notes::view)` and `new App<>(notes, s -> s.noteView(note))`. When a handler, a posted task, an action of `App.after` or an `onHoverFor` handler of one app ran (`App.ranHandlers()`), the runner calls `App.invalidate()` on the other apps whose `state()` is the same object, and they build their views again in the same pass: a press in one window shows in the others in the same frames. A pass builds a frame in each window whose input does not wait, then again in those another app invalidated, for up to three rounds; windows of other states are not touched, and an idle loop presents nothing in any window.
- Waiting and pacing: the loop waits once for all windows, for the earliest of the refreshes that a window's input waits for, the next frame of each window that moves (by its own display's refresh rate), and the earliest `nextChange()` of all apps; for events alone when there is none. The hold-back is per window: input or a task that arrives less than a refresh after the last frame of its window began waits for that window's refresh, while another window draws at once. A post to any app wakes the loop once (`Window.wake`), and each app's tasks go into its next frame.
- Closing: `handle.close()` takes effect after the pass that runs: the loop presents nothing more there, closes the presenter (when it is `AutoCloseable`) and then the window. The loop ends when its last window closes, or with `stop()`; then it closes the windows it opened and leaves those given to it open for their owners. A close request (the close button, Alt+F4, a script's `close`) runs the window's `onCloseRequest` handler as a task of its app; the handler closes the window, now or after a dialog, or vetoes by not closing it. Without a handler the request closes the window, or, when it is the loop's last, ends the loop and leaves the window open, as a loop of one window always did.
- Drags that know the screen: each `Drag` step also has `screenX`, `screenY` (the window's position plus the pointer's place in it, in the units of `Window.moveTo`), `outside` (the pointer is outside the window the drag began in), `window` (the `Windows.Handle` under the pointer, the drag's own included, or null) and `windowX`, `windowY` in that window. The window under the pointer is the topmost one whose content holds the point among those that are drop targets; since the system does not say which window lies on top, the loop keeps them in the order they last opened, were raised or took the keyboard focus. `Window.pointer()` reads the system's pointer (`SDL_GetGlobalMouseState`) where no event says where it is; drag steps take the event's place instead, which keeps them in the order of the input and lets tests inject events.
- Drop targets: `El.dragPayload(object)` on an element with `onDrag` makes its drags carry the object, and `El.onDrop(drop -> ...)` lets an element take it: `Drop.Phase.OVER` on each step while the pointer is over it or inside it (no element inside with a drop handler of its own), `LEAVE` when the pointer leaves, the drag ends elsewhere or is cancelled, and `DROP` at a release over it, with the payload and the point in its content. The element is hit tested, overlays first, in the tree its own window shows, in the drag's window or in another window of the runner, and its handler runs in the drag's frame before the drag's own step; its app builds its view again. The same handlers reorder within a window. A drag that carries a payload goes on when its element leaves the tree, with `x` and `y` NaN, since what moves is the payload: a card or tab torn out of its row.
- A window that follows the pointer: the drag's handler opens the window when `d.outside()` first holds, at `d.screenX()` less where the pointer holds the element times `screenScale()`, sets `dropTarget(false)` on it so that the windows under it stay findable, and moves it there on each step; at `END` it stays, or a drop handler of the row took the payload and closed it. SDL hands the pointer to a window that maps under it, also during a press, and on X11 its moves then come only while the pointer is over that window, and a release outside it is lost; the loop therefore gives what another window reports between a press and its release to the window the press began in, at the same point of the screen, and captures the pointer again (`SDL_CaptureMouse`). The keys that another window reports during a press go to the window the press began in too, so that Escape, which gives up a drag (`Drag.Phase.CANCEL`, and the release presses nothing), reaches the drag although the new window took the keyboard focus. A window the app moves during a press (`moved`) reports the pointer from where it has just moved to, while its position comes from the window manager a step late, and SDL drops each move that leaves the pointer where it was in that window, which is every move once it caught up: while such a window reports the pointer or is the pressed one, the loop takes the system's pointer (`Window.pointer()`) for the drag's place on the screen and reads it once per refresh until the release, also for the release itself, whose drop the next frame places (until the next press the window counts as moved), where positions are known (not on Wayland). Injected events into the pressed window alone, as tests send them, never start that. This was tried on X11 with a real pointer: the new window took the keyboard focus, the drag's moves and its release kept arriving, the window stayed exactly under the pointer, and Escape gave the drag up. On Windows, SDL captures the pointer for the window under it with `SetCapture` (SDL's source), so the same routing applies; it is not tried there.
- Platforms: on Windows and X11 a client places its windows anywhere and moves them; screen units are physical pixels and `screenScale()` is the window's scale. Wayland lets no client position a top-level window: `SDL_SetWindowPosition` moves only popups in SDL 3.4, `x()` and `y()` stay 0, and SDL 3.4 has no toplevel-drag protocol (`xdg-toplevel-drag-v1`, which would let the compositor move a window with the pointer). There a torn-off window opens where the compositor puts it and does not follow the pointer, and `Windows.place` finds no window but the drag's own, so a drop into another window cannot be detected; dropping back needs another gesture there, such as closing the window. The global pointer on Wayland is the pointer's place in the focused window. The session this was built on runs X11.
- Scripts: a `Script` is a runner too. The app it runs is the window `main`; a handler's `open` adds a window named by its title, at the position the options give or 32 pixels further than the last, at the first window's scale, with the first app's text rendering and clipboard, and posts held until `await` as for the first. `frame` runs a frame in every open window with the rounds of the loop, `advance` and `await` act on all apps, `snap` writes every open window, and `window`, `close`, `size … at x,y`, `screen x,y` and `in <window>` steer them (see the table above). A script that runs after another on the same app finds its windows.
- Tests: `SeveralWindowsTest` runs real windows through one loop: a press in one window shown in another in the same pass and nothing presented while idle, a handler that opens a window and one that closes all, which ends the loop, a vetoed close request, a drag from one window that is over and drops in another, a press whose pointer another window reports, pacing per window and posts to two apps. `DropTest` checks drop handlers in one app without a runner, `WindowsScriptTest` tearing off, following, dropping back, shared state and close requests by scripts, and `NotesTest` the example's windows against stored images.
- Tear-off tabs are built on this in the kit (`TabGroups`, see Kit). What core does not offer: a window that takes no focus as it opens (SDL has `SDL_WINDOW_NOT_FOCUSABLE` and `SDL_HINT_WINDOW_ACTIVATE_WHEN_SHOWN`), the stacking order from the system, and on Wayland any of the screen.

## Kit

`kit` (`com.rethinkj.ui.kit`) holds components built on `core`: `Label.label`, `Icon.icon`, `Button.button`, `Toggle.toggle`, `Checkbox.checkbox`, `TextField.textField` (and `passwordField`, `revealable`, `textArea`, `codeArea`), `DataGrid.dataGrid`, `Split.split`, `Tabs.tabs` (with `TabGroups` for tabs in several windows), `Menu`, `MenuBar.menuBar`, `Tooltip.tooltip`, `Dialog.dialog`, `Select.select`, `Toast.toast`, `Card.card`, `Group.group` with its rows, `Section.section` and `page`, `Form.form`, `Divider.divider`, `NavList.navList`, `Radio.radioGroup`, `Segmented.segmented`, `NumberField.numberField`, `Slider.slider`, `Callout.callout`, `EmptyState.emptyState`, `CodeEditor.codeEditor` with the highlighter `Sql`, `Completion.complete` and `Markdown.markdown` with its reader `MarkdownDocument`, `StatusBar.statusBar`, one file each. A component is a static function that returns an `El`, which the caller may chain further, as in `.key("save")`; there is no base class.

- The look is layered: the window's background (`surface().window()`, also the title bar's) is a page on which each region lies as a card (`surface().panel()`, lifted by `elevation().card()`); a tab bar, a grid's header and a card's footer are quiet bands inside a card (`surface().band()`); controls and popups are `surface().raised()`. Hairlines of low contrast (`border().subtle()`) separate surfaces and rows; buttons and popups have the slightly stronger `border().control()`, fields and boxes the 3:1 `border().strong()`. Radii go by rank: cards `radius().large()` (10), controls `medium()` (6), small parts `small()` (4). The full accent fills primary buttons and what is on; its lighter `accent().edge()` draws lines and outlines: the focus ring, the active tab's line, the grid's cursor, a selected card's edge and a navigation list's mark. Selections in lists, the grid and menus are the calm tint `grid().selected()` with primary text. Headings are Inter SemiBold, strong text, column titles and buttons Inter Medium.
- The theme is `Theme`, a record of token groups: surfaces (with the band and the scrim under a modal dialog), text colours, borders, accent (with its edge), status colours, spacing, radii, type (with the headings `title` over a page, `heading` over a section or a card's toolbar and `strong` over a card; `Label.Variant` has all three), sizes, motion (with the delays of submenus and tooltips, the fade of popups and dialogs, and how long a toast stays), the data grid's, elevation, the shadows under cards, popups and dialogs, and code, the colours of an editor of code (keyword, string, number, comment, operator, and translucent backgrounds of the caret's line and of a bracket pair; `ThemeTest` holds the token colours to 4.5:1 on the field's raised surface, hovered and on the caret's line, and to 3:1 under the selection). A theme made with the constructor without code gets `Code.DARK` or `Code.LIGHT` by the lightness of its raised surface. The last group, caption, is the red fill and white cross of a frameless window's own close button under the pointer, as Windows 11 draws its own (the examples' `TitleBar`); the constructor without code gives the default. The comment above `Theme.DARK` states the rules the default themes follow, which `ThemeTest` checks. `Theme.DARK` and `Theme.LIGHT` are the neutral default; an app copies one and changes a group with `withAccent(...)` and the other `with` methods. Fonts are `Supplier<Font>`, so that making or reading a theme loads no native library; the defaults need `rethinkj-ui-fonts`.
- A component takes the theme as its first parameter, `button(theme, PRIMARY, "Run", onRun)`. The view gets it from the app's state or a constant. There is no global or per-thread theme: a view says what it draws with, and two themes can be on screen at once, as in the gallery. Every focusable component draws its focus ring in `theme.accent().edge()` (`El.focusRing`), a primary button, whose fill is the accent, `size().ringGap()` (2) away from it (`El.focusRingGap`), so that the surface behind it shows between fill and ring; a view that switches its theme switches the ring with it. `Theme.over` mixes an overlay into a surface in linear light, as the renderer blends a translucent fill, so the hover and pressed overlays give one colour whether a component fills with the mixed colour or draws them translucent.
- Components read only tokens: no colour, size or spring of their own. `TokenTest` fails on an eight-digit hex literal or a `Spring` constant in any file of the package but `Theme.java`. A component that needs a new value gets a new token, with a value in both themes; `ThemeTest` checks the default themes: contrast (WCAG AA, 4.5:1 for text on every background it is used on, 3:1 for the strong border, the accent's edge and the focus ring, disabled text between 2.5:1 and 3.5:1), hover 4 L* and pressed 3 L* more from each surface, an inactive selection apart from a hovered row, and shadows stronger and tighter in the dark theme.
- A null handler disables a component: it takes no focus, shows no pointer cursor and draws in the disabled colours, a press on it goes to its ancestors, and its line in a `.tree.txt` says `disabled`.
- Each component sets the states it knows (see "Driving an app with a script"): buttons `disabled`; toggles (`role=switch`, on is `checked`, as WAI-ARIA has it) and checkboxes `checked` or `checked=false` and `disabled`; text fields `disabled`, `readonly` and `password` from core; the data grid `selected` and `current` on the selected rows or cells and the cursor's, `pos=<column>/<columns>` and `sort=` on the header and the other cells, and the rows their `pos` from the list; the tree `selected`, `expanded` or `expanded=false` (not on leaves), `level` and `pos` among the node's siblings on each row; tabs `selected` on the active tab and `disabled` without a select handler; the split's separator its position as `value`, `first 200`, `second 320` or `share 0.5`.
- Toggle and checkbox are a row of the control and its text, and the row takes the press and, from Tab, the focus; its `whenHovered` and `whenPressed` looks restyle the track or box, which they capture. The row is `Len.FIT_CONTENT` wide, so a column that stretches its children leaves press area and ring as wide as control and text, and one that centres them still centres it.
- `textField(theme, value, placeholder, onChange)` is the core's text field (see Text fields) in a frame: `size().control()` high and `size().field()` wide unless the view sets a width, the body type, the strong border, a lighter fill under the pointer and the accent border while focused, the placeholder in muted text, the selection in `accent().selection()` and the caret in the text colour. The placeholder is also the label unless `.label(...)` sets one. The result is the field itself, so `.readOnly()`, `.maxLength(n)` and `.w(...)` chain onto it. `TextField.withIcon(theme, field, symbol)` puts a muted icon at the left inside the frame, such as `Symbol.SEARCH` before a filter; a press on the icon reaches the box around them, not the field.
- `Button.button(theme, variant, [icon,] text, onPress)` is a button of `size().control()` with its text in `type().strong()` and an optional icon before it; `PRIMARY` is the accent with text on accent, `SECONDARY` the raised surface with the control border, `GHOST` shows the hover and pressed overlays only. `Button.icon(theme, variant, symbol, label, onPress)` is a square button with the icon alone, muted unless primary, the label in a dump and in a tooltip after the theme's delay.
- `passwordField(theme, value, placeholder, onChange)` is that field `masked()`, and `revealable(theme, field, revealed, onToggle)` puts a button at the right inside the field's frame that shows and hides the string: the field is masked unless `revealed`, the app's state, which `onToggle` flips. The result is a box with the field and the button, as wide as the field, so `.key`, `.label`, `.w` and `.readOnly()` go onto the field before. The button (`role=button`, `label="Show password"` or `"Hide password"`, `Symbol.EYE` or `EYE_OFF` in muted text, the ghost button's hover and pressed overlays, `radius().small()`) is `size().control()` less twice `space().xs()` square, `space().xs()` from the top and the right, and the field's right padding is `size().control()`, so the text stops before it. It keeps the focus where it is when pressed (`El.keepFocus`), so the caret stays in the field; Tab reaches it after the field, and Enter and Space press it, while the field keeps the accent border of the focus (`El.whenFocusWithin` on the box). It is disabled with a disabled field or without a handler; a read-only field shows its string too. While the pointer is over the button the field loses its hover fill, as hover belongs to the element a press would reach. `PasswordFieldTest` drives it; the gallery has the rows `password` and `password shown`.
- A new component: a file with a static function whose first parameter is the theme, with `role`, `label`, `focusable()`, `cursor(Cursor.POINTER)`, `onPress` and the looks while it is enabled, and that sets its states. Decide whether a press focuses it: a component that the user types or moves around in (a field, a grid, a list, a tree) takes the focus; one that acts on something else (a button, a toggle, a checkbox, a select, a divider, a tab) gets `keepFocus()` as well, so that a press leaves the focus in the editor or grid it acts on and only the keyboard focuses it; the `pressed` cells of the gallery's `.tree.txt` say `focused` only for the former. It sets at least `disabled(handler == null)`, and whatever of its state an agent would otherwise read from a colour. Add its rows to `Gallery.ROWS` and its cases to `ComponentTest.components()` in kit's tests (or tests of its own there, as the text field has, when it is not pressed), rewrite the stored images with `mvn -pl kit -am test -Dgolden.update=true`, and look at them.
- `DataGrid.dataGrid(theme, columns, rowCount, DataGrid.options()…)` shows query results; the options turn on what the grid does, and state stays the app's:
  - Each `Column` has its title, width, alignment, whether it is monospaced and sortable, and a function from a row index to the cell's text (null is SQL NULL, shown muted). Hiding or reordering a column is the app's: it changes its list.
  - Icons: `new Column(title, width, DataType.INTEGER, cell)` takes alignment, font and header icon from a `DataGrid.DataType` (integer, decimal, text, boolean, date, time, date and time, interval, UUID, JSON, binary, array, enum, geometry, other without an icon), to which an app maps its driver's types once; `.typeName("bigint")`, `.icon(symbol[, variant])` and `.cellIcon(row -> CellIcon)` return changed copies. A header cell is icon, title, type in muted text and sort mark, in this order at the left or the right as the column aligns, the mark on the outer side; where the column is narrow the type gives way first (the title has `flex-shrink: 0` and `max-width: 100%` in a box that clips, the type shrinks, and with less room than its first character and an ellipsis it is left out entirely rather than shown as a stub of the ellipsis), then the title ends in an ellipsis, while icon and mark keep their size; a tooltip shows title and type where anything is cut, and a fit counts every part. A `CellIcon` (symbol, `Icon.Variant`, `alone`, tooltip; `CellIcon.before(...)`, `CellIcon.instead(...)`, `.tooltip(...)`) stands before the text or in its place, aligned as the column; the icon function runs after the text function for loaded rows only and should return constants, so a cell costs one element more where it has an icon before its text and nothing more otherwise (`GridIconsTest` counts it on 300 columns). A cell whose icon stands alone has its text as its label (`label="true"`), as its tooltip unless the icon has one, and in copies. Icon colours stand out 3:1 from rows, stripes and selection (`ThemeTest`).
  - `.select(selection)`: a `DataGrid.Selection` the app keeps and the grid changes, as a `Menu.State` (`onSelect` tells of a change): a cursor, an anchor and `Range`s, whole rows in `Mode.ROWS`, cells in `Mode.CELLS`; a million selected rows are one range. A press selects at pointer down (`El.onPointerDown`), Shift extends from the anchor, Control adds or removes; dragging extends to the cell under the pointer (`Drag.x/y` on the list of rows) and beyond an edge scrolls one step per pointer movement, as core has no timer; the keys move the cursor (arrows, Page Up/Down, Home/End, with Control to the first and last cell) and show it again where the wheel scrolled away, also when it stays where it is (Home and End among rows go back to the rows' start sideways), Shift extends, Control+A selects all. The rows follow the cursor (`revealRow`), the columns too (`El.reveal` keyed by the selection's moves). A press on a row number (`.rowNumbers()`, `role=rowheader`, `number-<row>`) selects rows.
  - `.copy(clipboard)`: Control+C and Control+Insert put the selection on the clipboard as tab-separated lines (`DataGrid.copyText`: the rows and columns with a selected cell, quotes only where a tab, line break or quote needs them, NULL as `.nullText`, "" by default); beyond `.copyLimit(cells, handler)` (100 000 cells) or with rows not loaded the grid copies nothing and hands a `Copy` to the handler. `.contextMenu(state, items)` opens a `Menu` at a secondary press, after selecting the cell unless it is selected: Copy, Copy with headers, then the app's items.
  - `.sort(keys, onSort)`: a press on a sortable header cycles ascending, descending, none and replaces the keys; Shift with a press adds or cycles a further key; arrows from the icon font (`Theme.Grid.mark`) and, with several keys, their number. `.onResize`: dragging a header edge resizes (beyond the grid's side the grid scrolls along), a double press fits the column to the title and the text of its rows that exist, within `minColumn` and `maxColumn`. `.frozen(n)` keeps the first n columns, and the row numbers, at the left (`El.fixedX`).
  - Rows are an `El.rows` list built for the columns in view sideways (`RowBuilder`), so a frame costs about the same for 300 columns as for 20; the header is built whole, so a rebuild of the view costs in proportion to the columns. Cell text shows on one line, a line break as `⏎` and a tab as `⇥` (`DataGrid.LINE_BREAK`, `TAB`; a copy keeps them), ends in an ellipsis where it does not fit and shows whole in a tooltip after the theme's delay. `.loading(loaded, onRows)`: rows not loaded show a muted `…` in each cell without asking the cell functions, and `onRows` is told the rows the grid built when they change (`El.onRowsBuilt`). `.onEdit((row, column) -> …)`: Enter, F2 and a double press ask the app to edit the cursor's cell; the app lays a text field over it (`CellEditorTest`).
  - Its look: the header a quiet band (`grid().header()`) with titles in `type().strong()` and a `border().control()` line under it, its bottom border, a hairline along the bottom of each row, the row's bottom border, which the cells end above (no element of its own, so a row costs one element less and a `.tree.txt` has no line for it), no lines between columns but after the frozen ones (a column's edge shows the strong border under the pointer and the accent while dragged), the selection a tint without an edge, the cursor's cell a `cursorWidth()` outline in `grid().cursor()` with `radius().small()`, and no outer border, so that it sits flush in a card (`Card.flush`). The row numbers lie on the row's fill.
  - In a dump: `role=grid`, `columnheader` `column-<i>` with `pos` and `sort` and its title and type as text inside, `separator` `resize-<i>`, `row` `row-<i>`, `gridcell` `cell-<row>-<column>` with `pos=<column>/<columns>`; `selected` on selected rows or cells and `current` on the cursor's; an icon is `text label="<symbol>"` (see `Icon`). Its tokens are `Theme.Grid`: the cursor's outline stands out 3:1 from rows and selection (`ThemeTest`). The sort arrows need `rethinkj-ui-icons`.
  - `DataGridTest` runs `grid.txt`, `cells.txt` (a range, two sort keys, frozen columns, a tooltip, the menu, rows not loaded) and `rows.txt` against a million orders (`Orders`) in both themes and compares the snaps with `golden/<script>-<dark|light>-<snap>.png`; `GridCellsTest` drives the rest by scripts and reads the dump's states, and prints a frame's cost with 20 and 300 columns; `GridSelectionTest` checks selection, copied text and sort keys without the native libraries; `GridIconsTest` runs `icons.txt` against `Orders.typed` (types in the headers, a key, links, checks, NULL markers and status marks, selected, narrowed, with tooltips, frozen and scrolled) in both themes at scales 1 and 2 (`golden/grid-icons-<dark|light>-<1|2>x-<snap>.png`) and checks the rest by the dump.
- `Tree.tree(theme, model, isOpen, selected, onSelect, onToggle, onActivate)` shows nodes that open and close, such as a database's servers, databases, schemas, tables and columns. The app implements `Tree.Model`: the roots, a node's children (null while they are not known), whether it is a leaf, its label, and optionally an `El` before the label (an icon) and the text of the loading row. It owns which nodes are open and which is selected; the tree reports a selection (only a change), a node to open or close (`Tree.Toggle`), and an activation. A press selects, a press on the mark (the icons `Tree.CLOSED` and `Tree.OPEN`, chevrons, which need `rethinkj-ui-icons`) selects and opens or closes, a double press opens or closes and activates (it reads the count from `El.onPress(IntConsumer)`); with the focus, Up, Down, Home, End, Page Up and Page Down move, Right opens and then goes to the first child, Left closes and then goes to the parent, Enter activates. The rows follow the selection (`revealRow`), and whenever nodes open or close the tree also scrolls the selected node's children into view below it, as far as its height allows with the node in view (`El.reveal` keyed by the number of rows), so a node opened at the bottom shows what it holds. A secondary press on a row selects it and then runs the tree's own `onSecondaryPress` handler, so that a `Menu.contextMenu` on the tree acts on the row it opened on. Each rebuild of the view walks the open nodes from the roots to number the rows, in proportion to the nodes shown (`TreeTest` prints it: about 1.3 ms for 100 000), and the rows are an `El.rows` list, so scrolling builds rows, never the view. An open node whose children are null shows one muted loading row; the app starts the load in `onToggle` and changes its state when the data is there. Rows are rounded (`radius().medium()`), so a tree in `Card.inset` shows its selection and hover as a tinted row inside the card's padding. Rows are `role=treeitem` with the node's label and the key `row-<index>`, marks have the key `mark-<index>`; each row says its level, whether it is open and its position among its siblings as states (`expanded level=2 pos=1/3`), which costs two more ints per node shown in the walk. Its tokens are the grid's row height and selection colours, `space().xl()` per level and `surface().hover()` over the rows. `TreeTest` runs `kit/src/test/resources/scripts/tree.txt` against `Catalog`, three servers with a schema of 300 tables, in both themes, and compares the snaps with `golden/tree-<dark|light>-<snap>.png`.
- `Icon.icon(theme, symbol[, variant[, size]])` shows a `Symbol` of `Font.icons()` as a text element of one glyph, `size().icon()` (16) wide and high unless the call gives another size, that does not shrink, in the text colour or the variant's: `MUTED`, `DISABLED`, `DANGER`, `WARNING` or `SUCCESS`, the text and status colours. It has no role; its label is the symbol's name in lower case (`text label="chevron_right" "\u{F2AF}"`), so that a dump says which icon it is, and one that stands alone, such as a button without text, gets a label on the element that takes the press. `Symbol` is an enum of 114 of the font's icons, among them the kinds of data and the parts of a table's columns (`NUMBER_SYMBOL`, `CALCULATOR`, `TEXT_CASE_TITLE`, `CALENDAR_CLOCK`, `FINGERPRINT`, `KEY`, `LINK`, `BOOK_NUMBER` for an index, `NUMBER_CIRCLE_1` for unique, `TEXT_ASTERISK` for not null, `FLASH` for an identity, `PROHIBITED` for NULL, `RECORD` for a status), with Fluent's names in upper case (`CHEVRON_RIGHT` is `ic_fluent_chevron_right_<size>_regular`) and the code point of each size's drawing; `Symbol.codePoint(size)` picks the drawing made for the size, else the nearest. `Symbol.java` is generated: add a name to the list in `scripts/GenerateSymbols.java` and run `java scripts/GenerateSymbols.java` from the repository root, which reads the names from the font's own `post` and `cmap` tables. The font has one name per glyph, so a name Fluent's site gives as an alias may be missing (`arrow_export_ltr`, not `arrow_export`). A theme does not choose the icon font: the code points belong to this one. Apps that show icons, the tree and a sorted data grid among them, add `rethinkj-ui-icons`. `IconTest` stores a sheet of every symbol at 16 and 20 with its name and the colour variants, `golden/icons-<dark|light>-<1|2>x.png`.
- Scrollbars: `Theme.scrollbars()` is core's `Scrollbars` look, so any scroll area or list shows the themed bars with `.scrollbars(theme.scrollbars())`. Its thumbs, at rest, hovered and dragged, stand out 3:1 from the surfaces and the grid's rows, which `ThemeTest` checks. `DataGrid` has a bar along the right edge of its rows, below the header, and one along the bottom of the grid. `ScrollbarsTest` runs `kit/src/test/resources/scripts/scrollbars.txt` against a list in both themes at scales 1 and 2 and compares the snaps with `golden/scrollbars-<dark|light>-<1|2>x-<rest|hovered|dragged>.png`. The bars lie over the content, and an area scrolls its last row and last column out from under a bar that crosses them, its own or that of an area around it along the same edge (`El.scrollbars` says when); the grid has the room of its rows' bar after its last column for that, and the column that follows its cursor stops clear of that bar too.
- `CodeEditor.codeEditor(theme, value, state, highlighter, onChange)` is `TextField.codeArea` with line numbers in a gutter (muted, the caret's line's in primary text, right-aligned, `space().m()` before the text), `code().line()` behind the caret's line, `code().bracket()` behind the bracket before or after the caret and its partner (looked for up to 100 000 characters away; brackets in strings and comments count), and an error underlined in `status().danger()`. The app keeps a `CodeEditor.State`, which the editor tells the caret and anchor (`onSelect`) and on which the app sets `error(from, to)`; it holds the field's `FieldState`, so an editor keeps its caret, scroll and history while it is out of the tree (one per tab). The highlighter is also the field's key for it, so the view passes the same object or an equal one: `Sql.of(theme)` is a record. `Sql` scans each line by hand, without regular expressions: keywords (a set of SQL and PostgreSQL's, case-insensitive), strings with doubled quotes, identifiers in double quotes (no colour, no keywords inside), dollar-quoted strings (`$$`, `$fn$`), numbers and `$1`, `--` comments, nested block comments and operators; strings, identifiers, dollar quotes and comments go on across lines in the state. `Spans(length)` and its `toString` test a highlighter without native libraries (`SqlTest`). `CodeEditorTest` runs `code-editor.txt` in both themes at scales 1 and 2 and compares with `golden/code-editor-<dark|light>-<1|2>x-<rest|brackets|scrolled>.png`; `CodeEditorLargeTest` counts the lines asked of the highlighter on 100 000 lines and prints the times. The gallery has no row for it yet, since its stored images are being redone.
- `Completion.complete(theme, app, field, caret, state, suggest)` gives a text field completions at its caret, a `CodeEditor` above all: while the app's `Completion.State` is open, a list (`role=listbox`, `label="Completions"`, entries `role=option` `option-<index>` with the text as label, the highlighted one `selected`) lies below the caret (`El.atCaret`), at least `size().field()` wide and at most eight rows high, then it scrolls; it keeps the focus in the field (`keepFocus`) and has the look of a `Menu` (raised surface, control border, `elevation().popup()`, the fade, rows of `size().control()`, the selection's tint for the highlight). The app's function gets the part of the word before the caret (code words: letters, digits, `_`; empty after Control+Space) and returns `Completion.Entry`s (text, optional `Symbol`, optional kind shown muted); the kit filters nothing. The component wraps the field's `onEdit` and `onKey`: a single letter, digit or `_` typed opens the list once the word has two characters and the caret stands right after it (an undo that brings a character back opens nothing), a deletion keeps it open while the word is not empty, any other edit closes it; Up and Down move the highlight around, Page Up and Down by eight, Enter and Tab take the entry through `App.edit` (one step of the history; Tab does not indent then), Escape closes, the arrows sideways, Home and End close and move the caret, a press on an entry takes it, a press elsewhere or the wheel dismisses the list. Keys it does not take reach the field's own handler, Control+Enter among them. `CompletionTest`.
- `Markdown.markdown(theme, document, Markdown.options()…)` shows a `MarkdownDocument` (`Markdown.parse(source)`, which the app keeps in its state) in the look of `Theme.Prose`, a token group with the body's type, the six heading styles, the link colour, inline code's translucent background, the quote's line and the measure (720) the text runs to; `ThemeTest` holds text, quoted text and links to 4.5:1 on the panel, under the pointer and on inline code, and links to 3:1 under the selection.
  - The reader (`MarkdownParser`, package-private) follows the CommonMark specification 0.31.2: blocks line by line with a stack of open containers, then the inline parts with a stack of delimiters and one of brackets, and GitHub's tables, task list items, strikethrough and bare URLs (`www.`, `http://`, `https://`). It never throws (a fault would show the text as code) and takes time in proportion to the text: a megabyte of each of 18 kinds of input that make careless readers quadratic takes 1 to 120 ms (`MarkdownParserTest`, which also reads 222 examples of the specifications against `kit/src/test/resources/markdown/commonmark.txt`). Left out on purpose: HTML blocks and inline HTML (text), tabs inside a line after a container's marker other than right after it, bare e-mail addresses, and nesting deeper than 32, which becomes text. `MarkdownDocument.tree()` is the tree as text, `headings()` the headings with GitHub's anchors (`id`, unique in the document), `plainText` the text of inline parts.
  - The result is a scroll area (`role=document`) and a virtual list (`El.rows(count, heights, row)`) whose rows are the top-level blocks and the items of top-level lists, centred up to the measure, so only those in view and three more on each side are built: with the 165 KB of this file, reading takes 12 to 23 ms, a rebuild of the view with its frame 7 to 9 ms and a wheel step of 400 pixels 6 to 9 ms (the first frame of a cold JVM 0.8 s). What the component makes of a document for a theme (the text and ranges of each block, the heights of its rows) it keeps with the document.
  - Each block of text is a read-only multi-line field (`fitLines`, `skipTab`): a press and a drag select within it and Control+C copies that; Control+A selects the whole document (`Markdown.State`, shown as a background on every block) and Control+C then copies `Markdown.text(document)` to the clipboard of `options().copy(clipboard)`; a press anywhere ends it. A selection across blocks would need one editor over several fields. Inline styles are a highlighter of the block's own: Inter Italic, SemiBold and Bold Italic, JetBrains Mono on `prose().code()`, `strike` lines, links in `prose().link()` and underlined. A link is a child over its range (`El.range`): `role=link`, its text as the label and its destination as the value, the pointer cursor, `surface().hover()` under it, one stop for Tab, Enter presses it; `options().onLink` gets the destination. Headings are `role=heading` with `level` and the key `heading-<id>`, levels 1 and 2 over a hairline; `Markdown.rowOf(document, id)` is the row to `App.scrollToRow` for a link `#id`. Code blocks are `role=code` with the language as the label, on the raised surface with the subtle border, scrolling sideways, highlighted by `options().languages(language -> highlighter)` or `Sql` for `sql`, with a copy button (`label="Copy code"`) in the corner under the pointer. Quotes have a line at their left and muted text; lists hang their text after the marker, numbers right-aligned in tabular figures; task items show the kit's checkbox disabled; tables (`role=table`) have a header band, hairlines, the columns' alignment and widths measured from their cells up to half the measure, and scroll sideways; a thematic break is a `Divider`; an image alone in its paragraph shows its description in a frame (`role=img`), and inline its description in muted text, as the kit has no images yet.
  - `MarkdownTest` drives it by scripts: the roles and states of the blocks, links by the pointer and by Tab and Enter, copying a word, a code block and the whole document, and a document of 4000 blocks that builds only those in view. The example `Manual` shows it.
- `Split.split(theme, direction, position, reset, onMove, first, minFirst, second, minSecond)` puts two parts side by side (`Direction.ROW`) or one above the other (`COLUMN`) with a line between them. The app keeps a `Split.Position` and gets a new one of the same kind while the line is dragged or moved by keys: `Position.first(pixels)` keeps the first part's size when the split grows, as a side panel does, `second(pixels)` the second's, and `share(fraction)` the first part's share of the room, as an editor over its results. The handler turns the pointer's distance into a position from the sizes of the view the drag began in, whose elements it captured after their layout, so the view needs no container size. Layout keeps both minimums when the split is smaller than the position allows, without changing the position, so a wider window brings the layout back. The line is `border().subtle()` and `size().stroke()` wide; a strip of `size().handle()` around it takes the pointer, with the resize cursor of its direction, the strong border under the pointer and the accent while it is dragged. So that the strip lies over both parts, the second part and the strip are in a box of their own (`#rest`) in reverse order. The strip (`role=separator`, labelled `Resize` and the first part's label) is one stop for Tab, which reaches it after the second part (drawing order is tree order, and the strip has to lie on top of both parts), a press or drag on it leaves the focus in the part that has it (`keepFocus`), the arrow keys along the split move it by `size().step()`, and a double press (`El.onDoublePress`) reports `reset`. Each part fills a box that clips it (`#first`, `#second`), and splits nest. `Split.cards(...)`, with the same parameters, splits two cards on the window: the parts lie `space().m()` apart, the line shows in the middle of that gap only under the pointer and while dragged, and nothing clips the parts, so their lifts show. Neither the split nor its parts take a minimum size from what the parts hold, so a list of rows or a tree in a part scrolls inside it, also in a column that grows.
- `Tabs.tabs(theme, tabs, active, onSelect, onClose, content)` is a card whose first row is a bar of tabs over the content of the active one, which the app builds alone and which fills the card edge to edge, as in `Card.flush`. Each `Tab` has its title, whether it can be closed, whether it is modified (a dot before the title) and an optional icon (`tab.icon(Symbol.TABLE)`); the app owns the list and the active index and gets the index of a chosen or closed tab. The bar is the quiet `surface().band()` with a hairline under it, its bottom border, its tabs `size().control()` plus `space().m()` high; the active tab has primary text and a line of `size().indicator()` (2) in `accent().edge()` along its bottom, the others muted text, with the hover and pressed overlays and primary text under the pointer; a closable tab's cross (the font's `×`, as the checkbox's mark is `✓`) shows on the active tab and under the pointer, at opacity 0 otherwise, so it takes no press there. The bar (`#tablist`, `role=tablist`) is one stop for Tab: Left, Right, Home and End choose tabs. Control+Tab, Control+Shift+Tab, Control+W and Control+F4 are on the component's root, so they work from the bar and its content; the arrow keys leave the focus on the bar, as WAI-ARIA's tabs do, and from the content the focus goes into the new content, to its `autofocus` or first focusable element, else to the bar (see the focus rules in the script section). An app gives its root the same handler with `root.onKey(tabs.onKey())` for the shortcuts while the focus is elsewhere. Middle-button close waits for a second pointer button in core. The bar scrolls sideways only (`overflow-y` hidden): `App.wheel` turns a wheel that turns only up and down sideways in such an area, and `El.revealRow(active)`, which on a scroll area that is not a list of rows keeps the child with that index in view, shows the active tab whenever it changes. The component takes no minimum size from its content, so a list of rows there scrolls inside it. Each input reaches the handlers of a view built after the input before it, so keys in one frame go on from each other's choice, and a second Control+W closes the tab the first made active.
- Moving, tearing off and docking tabs: `Tabs.tabs(theme, tabs, active, onSelect, onClose, content, Tabs.options()...)`. `onMove((from, to) -> …)` lets the user move tabs: Control+Shift+Page Up and Page Down move the active tab one place (as Chrome, Firefox and VS Code do on Windows and Linux; not around the ends), and with `drag(state)`, a `Tabs.Dragging` the app keeps, a tab dragged along its bar (after core's threshold of 4 pixels; a press without it chooses as before) shows muted in its place (`text().disabled()`, `grabbed` in a dump) and a line of `size().indicator()` in `accent().edge()`, `size().control()` high, where it would go (`#marker`, absolute in `#bar`, from the laid-out tabs the drop handler captured); near an end of the list each step scrolls it by `space().m()` (`El.reveal` with a new key per step); the release moves the tab, Escape or a lost release leaves the order. `Tabs.move(list, active, from, to)` moves an element and returns the active index. `onTearOff(handler)` is told the step on which the pointer leaves the bar, more than `size().control()` above or below it or out of the window, and every step after it, as a `Tabs.TearOff` (bar, index, the `Drag`, where the pointer holds the tab, where the bar's first tab lay in its window); `tearOffAtStart(true)` tears from the first step (a window's only tab). `onDock((fromBar, from, at) -> …)` lets a bar take a tab dragged from another bar with the same `Dragging` state, told apart by `id(bar)`; the payload is the state itself. `contextMenu(menuState, items)` opens a menu for a tab after choosing it at a secondary press, at the Menu key on the bar and beside the tabs. While a tab is dragged no tab shows hover looks: the drag's element is found by its key `tab-<index>`, which another tab has once the dragged one left. Without these options nothing differs from before.
- `TabGroups<T>` keeps an app's tabs in groups, one per window: `new TabGroups<>(tabs, (group, options) -> app.windows().open(title, w, h, options.frameless()..., new App<>(state, s -> s.view(group))))`, and each window's view calls `groups.tabs(theme, group, t -> new Tab(...), t -> content)` (the content function gets null for an empty group, whose bar still takes tabs). It wires everything above: moving; a tab torn off leaves its group for a new one whose window opens under the pointer with the tab where the pointer holds it (from the source bar's place, corrected from the new window's own tree after its first frame) and follows until the release (`dropTarget(false)` meanwhile); over a bar the window moves down below the bar's tabs so the marker shows; a drop on a bar docks the tab there and a group left empty closes its window, raising the window that took it; a window's only tab moves its window; Escape or a lost release puts a torn tab back where it was, or a moved window back where it lay; the menu has Move to new window (where the system places it) and, in a group's window, Move back to main window, which are the way on Wayland; closing a group's window runs `onWindowClose` (`dockAll` unless set, or `closeAll`), and `onClosed` hears of each closed tab. Content is built for each group's active tab only; what hangs on element identity (caret, undo, scroll) stays with the window that showed it. `TabGroupsTest` drives all of it by scripts with several windows; `com.rethinkj.ui.window.TabTearOffWindowTest` (in kit's tests, for SDL's bindings) tears a tab off and docks it in real windows with SDL events.
- `SplitTest` runs `kit/src/test/resources/scripts/split.txt` and `TabsTest` `tabs.txt` against the state in `Workbench`, and `WorkbenchTest` `frame.txt`, the frame of a database tool: the schema beside queries in tabs, the active one an editor over its results, at scales 1 and 2. They compare the snaps with `golden/<script>-<dark|light>-<snap>.png`.
- `Menu` shows items in an overlay (see Overlays): `Menu.item(label, onChoose)`, disabled with a null handler, with `.shortcut(Key.CONTROL | Key.SHIFT, "N")` for a key combination that runs it, shown at the right in muted text as the platform writes it (`Menu.shortcutText`: `Ctrl+Shift+N`, Ctrl, Alt and Shift in that order after `Win` or `Super`, `Del` and `PgUp` on Windows where Linux writes `Delete` and `Page Up`), `.shortcut("…")` for a text that only shows, `.icon(Symbol)` before the text and `.checked(true)` for a check mark in its place; `Menu.separator()`; `Menu.submenu(label, items)`, opening beside the item, to any depth. The check mark (`Menu.CHECKED`) and the submenu arrow (`Menu.SUBMENU`) are icons, and the column before the text is `size().icon()` wide in every item, so texts line up with and without icons. The app keeps a `Menu.State` per menu in its state (open or not, the point it opened at, at each level the highlighted item and the item whose submenu is open: `active(level)`, `submenu(level)`) and opens it in its own handlers: `Menu.dropdown(theme, button, state, items)` hangs the menu below a button whose press calls `state.toggle()`, `Menu.contextMenu(theme, target, state, items)` opens it at a secondary press with `state.openAt(x, y)` unless the target already has such a handler (rows can select themselves first), and `Menu.menu` is the panel alone. The menu takes the focus as it opens: Up and Down move the highlight around the items and past separators, Home and End, Enter and Space choose, Arrow Right opens a submenu and Arrow Left or Escape close it, at every level, Escape and Tab close the menu, a letter or digit goes to the next item that starts with it. The pointer highlights the item it rests on (`El.onHoverFor(0, ...)`), and after `motion().submenuDelay()` on an item opens its submenu or closes another of its level, with the ones inside it. Choosing closes the menu and then runs the handler; a press outside closes it and does nothing else. `Menu.shortcuts(items)` is a key handler for the root that runs the enabled item of a combination, in submenus too, when no element on the focus path took the key, open menu or not; two items with one combination are refused with an exception naming both when the view is built. Items are `role=menuitem` with their text as the label and the keys `item-<index>` or, in a submenu, `subitem-<index>`, separators counted; the highlighted item is `current`. Its tokens: the raised surface with the control border and the medium radius, rows of `size().control()`, the selection's tint `grid().selected()` with primary text for the highlight (the full accent belongs to primary buttons), and the hover overlay for a highlighted disabled item; it lies on `elevation().popup()` and fades in and out with `motion().fade()`, as tooltips, dialogs and toasts do; scripts advance the clock 0.25 seconds past the fade before a snap or before they point at its items, which are not there for the pointer while invisible. `MenuTest` runs `menu.txt` (dropdown, keys into the submenu, choosing, the submenu after a rest, dismissing), `context.txt` (a secondary press on a row, letters, Escape), `corner.txt` (a menu in a scrolled panel in the bottom right corner, flipped above and to the left and drawn whole across the panel's clip) and `select.txt` against `Bench`, the workbench of a database tool in a window of 360 by 240, in both themes at scales 1 and 2, and compares the snaps with `golden/<script>-<dark|light>-<1|2>x-<snap>.png`; it also checks that a menu fading out takes no press and that nothing is drawn after the fade.
- `MenuBar.menuBar(theme, state, menus)` is a row of titles, File, Edit and so on, each a `Menu.submenu("&File", items)` whose `&` marks its mnemonic (`&&` is an ampersand), opening its menu below it; a title without items is disabled. The app keeps a `MenuBar.State` and gives the root `MenuBar.keys(state, menus)` (`onKey`, combined with others by `Predicate.or`) and `MenuBar.keysUp(state, menus)` (`onKeyUp`). The pointer: a press on a title opens its menu, a press on the open one's title closes it, and while a menu is open a press on another title, or the pointer moving onto it, switches to its menu; the titles keep the focus where it is (`keepFocus`), so the menu gives it back to the editor, and lie in one dismiss group with the open menu. The space between them takes no press, so in a title bar marked `windowPart(DRAG)` it still moves the window. The keys: Alt pressed and released with no other key and no press of the pointer between (`El.onAnyPointerDown`), or F10, gives the bar the keys (`holdFocus`) with the first title highlighted; Left and Right move, Down, Up, Enter and Space open, a letter opens the menu of that mnemonic, and Alt with a mnemonic's letter opens it from anywhere the root gets keys. In a bar's menu, Right on an item without a submenu and Left in the menu itself go to the next and previous menu; Escape steps back one level, a submenu, the menu, then the bar, which gives the focus back to where it was; Alt or F10 again, Tab, choosing and a press outside leave the bar. Mnemonics are underlined (`El.underline`) while Alt is held or the bar has the keys. `keys` also runs the items' key combinations, as `Menu.shortcuts` does, and closes the bar's menu first; a combination that is Alt with a title's mnemonic is refused like two of one. `role=menubar`, titles `role=menuitem` with the keys `title-<index>` and `expanded`. Its tokens: the body type, `surface().hover()` under the pointer and `surface().pressed()` on the open or highlighted title. Keys the app does not get: on Windows SDL drops the system's menu activation by Alt, F10, Alt with a letter and Alt+Space (`SDL_WINDOWS_ENABLE_MENU_MNEMONICS` off), so these reach the app, and `WindowLoop` opens the window menu for an Alt+Space that no handler takes; Alt+F4 does too, and SDL also asks the window to close, which ends the `WindowLoop`; Windows keeps Alt+Tab, Alt+Esc, Ctrl+Esc, Ctrl+Shift+Esc, Ctrl+Alt+Del and the Windows key's combinations. On Linux SDL's X11 code keeps nothing, but the desktop takes its shortcuts first, usually Super's, Alt+Tab, Alt+F4, Ctrl+Alt+Delete and Ctrl+Alt+F1 to F12, often Alt+F1, Alt+F2, Alt+F7, Alt+F8, Alt+F10, Alt+Space and Print Screen. `MenuBarTest` runs `menubar.txt` (a press opens File, the pointer switches to Edit) and `nested.txt` (File's Export three submenus deep with the keys in a window of 480 by 280, the last opening to the left at the window's edge) against `Studio`, a query editor in a frameless window with the bar in its title bar, in both themes at scales 1 and 2, and drives the rest by scripts: switching, the window's parts around the titles, Alt and F10, mnemonics, the underlines, the combinations, conflicts and their text.
- Elevation: cards lie on `Theme.elevation().card()`, menus, a select's list, tooltips and toasts on `elevation().popup()`, dialogs on `elevation().dialog()`, each a list of `Shadow`s for `El.shadow`: a tight one that darkens the edge and a wide one that shows the height. `Theme.DARK`'s are stronger and tighter than `Theme.LIGHT`'s, since a shadow shows little on a dark surface; the light theme's have about twice the alpha a CSS shadow has, as the renderer mixes in linear light. Cards keep the subtle border, popups and dialogs the control border, which the dark theme still needs to separate a raised surface from a card. `TokenTest` also refuses `new Shadow(` outside `Theme.java`.
- `Tooltip.tooltip(theme, anchor, text)` shows the text below the anchor, centred, once the pointer has rested on it for `motion().tooltipDelay()`, and hides it when the pointer leaves or presses; likewise once the keyboard has given the anchor the focus with its ring for as long, until the focus leaves or a key goes down. Where it would cover the anchor it goes beside it. It keeps no state: it is a delayed look of the anchor (`El.whenHoveredFor`, `El.whenFocusVisibleFor`) that attaches the overlay, and the app's clock carries the delay, so an idle window wakes for it and presents nothing while it waits. `role=tooltip` with the text as the label; the raised surface, the subtle border and the small radius. `TooltipTest` runs `tooltip.txt` against `Bench`, nothing after 0.4 seconds and the tooltip after 0.5, and `keytip.txt`, the help button reached with Tab.
- `Dialog.dialog(theme, title, content, buttons, [defaultButton,] onDismiss)` is a modal overlay in the middle of the window over `surface().scrim()`: the title as a heading, the content and the buttons at the bottom right. Enter without modifiers presses the default button, one of `buttons`, while it is enabled: in a field of the dialog, as nothing before the dialog takes Enter there, while a focused button, checkbox or select presses itself and a multi-line field keeps Enter for its line breaks; a held Enter presses once. `Dialog.enterPresses(button)` is that key handler alone, for a window that is a dialog itself (ConnectionDialog puts it on its root). The app attaches it to the root while its state says it is open: `root.overlay(s.renaming ? dialog(...) : null)`. The focus goes to its first focusable element as it opens and stays inside it, Escape and a press on the scrim call `onDismiss`, and when it closes the focus goes back to where it was, with the ring it had. A frameless window's own title bar stays usable under it (see Overlays). `role=dialog` with the title as the label. `DialogTest` runs `dialog.txt` against `Bench`: opened with the keyboard, Tab around the field and both buttons, Escape, the ring back on the button that opened it.
- `Select.select(theme, choices, selected, state, onSelect)` is a button with the current choice and a chevron (`Select.OPENS`) that opens a `Menu` of the choices below it, at least as wide as itself (`Style.Align.STRETCH`), the current one checked and highlighted; a press, Enter, Space and Alt+Arrow Down or Up open it, and Alt+Arrow Down or Up close it again. While it is closed and focused, Arrow Down and Up choose the next and the previous choice, Home and End the first and the last, and a letter or digit the next choice that starts with it. `role=combobox` with the choice as the label; the text field's frame and width. `MenuTest` checks the keys.
- `Toast.toast(theme, message, action, onAction, onClose)` is a message at the bottom of the window, in the middle (`El.atWindowEdge`), with an optional action button such as Undo, that the app attaches to the root while its state holds the message. It closes itself after `motion().toast()` seconds (5) of the app's clock (`El.onShownFor`), without frames meanwhile, and when its action runs or Escape reaches it; a press elsewhere leaves it. It keeps the focus where it is (`El.keepFocus`), also when its action is pressed, and Tab reaches the action last; when it closes from there, the focus goes back to where it was before Tab. `role=status` with the message as the label; the raised surface, the subtle border and the medium radius on `elevation().popup()`. `ToastTest` runs `toast.txt` against `Studio` (Edit's Clear) in both themes at scales 1 and 2 and drives Undo, Tab, Escape and the time.
- Structure: a page of settings, a detail panel or a dashboard is built from `Section.page(theme, title, sections...)` (a scroll area with the title as a heading of level 1, `space().xxl()` of padding and between sections), `Section.section(theme, title, description, content...)` (a heading of level 2, the description `xs` below it, content `m` below and apart), cards and groups; null content is left out, so `changed ? callout(...) : null` composes. Headings are `role=heading` with `level`.
- `Card.card(theme[, variant], content...)` is a column on a surface, `space().l()` of padding and gap, `radius().large()`, that clips its content to its rounded corners. `OUTLINED` (default) is the panel with the subtle border and `elevation().card()`, `FILLED` the panel without a visible edge or lift (the border is there, transparent, so the variants lay out alike), `ELEVATED` the panel with the edge and `elevation().popup()`. Nesting rule: a card in a card is `OUTLINED`, the same surface set off by its edge; `FILLED` is for the window. `Card.flush(theme, parts...)` is an outlined card without padding whose parts lie edge to edge, clipped by its corners, and take no minimum size from what they hold: `Card.toolbar(theme, title, secondary, actions...)` (the title in `type().heading()`, a heading of level 3, a muted text beside it, the actions at the right, inside `space().m()` and `space().l()` of padding), a body such as a data grid that grows, `Divider.divider(theme)` where a hairline belongs, and `Card.footer(theme, start, end...)` (a band with a hairline above it, its top border, `start` at the left, the rest at the right). `Card.inset(theme, list)` insets a list with rounded rows, such as a tree or a navigation list, by `space().s()`. `Card.header(theme, title, description, actions...)` is the title in `STRONG` (a heading of level 3), a muted description that wraps and actions at the right; `Form.buttons(theme, buttons...)` ends a card, a form or a page. `Card.pressable(theme, card, label, selected, onPress)` makes the whole card `role=button` with the label, focus, pointer, hover and pressed overlays over its fill, `selected` with the `accent().edge()` edge, and `disabled` without a handler; controls inside keep their presses.
- `Group.group(theme, rows...)` is an outlined card with `Scene.RING` of padding and a hairline (`border().subtle()`, `size().stroke()`) between each two rows, across the card. Rows: `row(theme, [icon,] title, description, control)`, `switchRow(..., on, onToggle)` (the row is `role=switch`, `checked`, one stop for Tab, a press anywhere flips it; the switch is `Toggle.track`, which takes no input), `linkRow(..., value, onPress)` (`role=button`, `value`, the value muted and a chevron), `expander(..., open, onToggle, content...)` (`role=button`, `expanded`, `CHEVRON_DOWN` or `UP`; the content below, indented by `space().xl()`, with hairlines) and `box(theme, content...)` for anything else with a row's padding. Height rule: the text starts `space().l()` inside the card, a row is at least `size().control()` plus `space().m()` above and below (40 with the ring's band), a description wraps and makes it higher, the control keeps its width (`shrink(0)`). Hover, pressed and the ring lie inside the card: the ring in the `Scene.RING` band around the row, whose radius is the card's less its border and the band, so it follows the card's corner. A row names its control after its title (`Form.named`): a text field or a control without a label gets the title as its label; a select keeps its choice. `GroupTest`, `StructureTest` (`structure-rows-*`, and `structure-rows-narrow-*` at 300 wide, where descriptions wrap and controls keep their widths).
- `Form.form(theme, Labels.BESIDE | ABOVE, field(label, control).help(text).error(text).required()...)`: labels beside the fields in a column as wide as the widest label, measured with `Text.measure` at build time, and centred on the field's first line (`size().control()` high), the fields `space().m()` apart; or above them, `space().l()` apart. A required field has a `*` in `status().danger()`. Help is muted and wraps; an error replaces it in the danger colour and makes the field `invalid`: `TextField.invalid(theme, field)` gives a text field the danger border also while focused and `El.invalid(true)`. Each label names its field (the field, or the first control inside it, such as the field of `revealable`). `ConnectionDialog` uses it.

## Native libraries

The window (SDL3), the GPU renderer (wgpu-native) and text (HarfBuzz shapes, FreeType rasterises) will call native libraries. They reach users in one JAR per platform, `rethinkj-ui-natives-<platform>`, where the platform is `windows-x64` or `linux-x64`. Both hold SDL 3.4.20, wgpu-native 29.0.1.1, FreeType 2.15.0 and HarfBuzz 15.1.0. FreeType and HarfBuzz are built from the same source archives with the same options on both platforms, without dependencies beyond the C runtime: on Linux HarfBuzz needs no libstdc++, and on Windows both link the C runtime statically and need only `KERNEL32.dll`.

- The JAR has no Java code. Under `META-INF/rethinkj-ui/natives/<platform>/` it holds the libraries, `manifest.txt` and the licence texts in `licenses/`. `manifest.txt` lists the libraries in load order, one line each: `library <name> <version> <file> <sha256>`, after the lines `rethinkj-ui-natives 1` (the format) and `platform <platform>`. A library built from source is followed by `built <name> <sha256 of the source archive>`, because its own hash differs between machines. `com.rethinkj.ui.natives.Manifest` reads it, ignores `built` and documents the format.
- No binaries are committed. `natives-<platform>/natives.properties` pins each library: version, archive URL, the archive's SHA-256 and the file inside it. `scripts/FetchNatives.java` (run with `java scripts/FetchNatives.java natives-windows-x64`; it needs only the JDK) downloads the archives into `natives-<platform>/fetched/archives/`, checks their hashes, and unpacks the libraries and writes `manifest.txt` into `natives-<platform>/fetched/resources/`, which the module packages. The module's build runs it in `generate-resources`; it does nothing while `fetched/` matches `natives.properties`. `fetched/` is ignored by git and survives `mvn clean`; delete it to fetch again. Offline, put the archive at the path the error message names.
- A library with a `<name>.cmake` line (on Linux every library but wgpu-native, on Windows FreeType and HarfBuzz) comes from a source archive, a `.zip` or a `.tar.xz`: the tool builds it with cmake in `fetched/builds/<name>/`, on Linux with make, and reuses that build while archive, options and entry stay the same. It fails if cmake turns off an option the line sets `ON`, such as `SDL_X11` or `SDL_WAYLAND` when their development files are missing.
- On Windows the tool builds with Visual Studio 2022 or later, or its Build Tools, and needs nothing on the PATH. It takes the installation of the developer prompt it runs in (`VSINSTALLDIR`), else the newest one with the C++ x64 tools that `vswhere.exe` finds (one that also has Visual Studio's CMake first), and runs every command in the environment that its `VsDevCmd.bat -arch=amd64` sets up. cmake is the file the environment variable `CMAKE` names, else the first `cmake.exe` on that environment's PATH, where Visual Studio's own (the component "C++ CMake tools for Windows") comes before the user's PATH. The generator is the Ninja that the same component brings, else NMake: FreeType and HarfBuzz take about 70 s with Ninja and about three minutes with NMake. Windows' `tar.exe` reads `.tar.xz` but cannot make a symbolic link without a privilege, so the tool has it rewrite the archive as a zip and unpacks that; a link becomes a file holding its target, as Git makes links where it cannot. The libraries link the C runtime statically (`CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded`), because `VCRUNTIME140.dll` comes with the Visual C++ Redistributable, not with Windows.
- A fresh Windows machine needs Visual Studio or its Build Tools with the workload "Desktop development with C++", whose defaults include the x64 tools, a Windows SDK and "C++ CMake tools for Windows"; nothing else needs installing or setting. Where cmake is missing, the build stops with a message that says what to do; it does not download CMake itself. The fix is needed once, as later builds reuse `fetched/builds/`, and the build cannot get Visual Studio by itself either. Without installing anything, unpack the Windows x64 ZIP from cmake.org anywhere and build once with `$env:CMAKE = '<folder>\bin\cmake.exe'`. An agent working unattended does that, or builds with `-P '!natives-windows-x64'` when it needs no native libraries.
- A Linux library is packaged under its SONAME (`libSDL3.so.0`), so that a library that needs it finds the loaded copy; the tool checks that. HarfBuzz's CMake build gives it the SONAME `libharfbuzz.so`, without the `.0` of its Meson build.
- To change a version, edit `natives.properties`, build, and update the licence texts under `natives-<platform>/src/main/resources` if the release changed them.
- A natives module is built only on its own platform: the root `pom.xml` lists it in a profile of the same name, activated by the operating system and architecture, and `core` has a profile with that id that adds it as a test dependency.
- `com.rethinkj.ui.natives.Natives.lookup("sdl3")` returns a `SymbolLookup`, loading the library and every library listed before it on first use. The package is internal to `core`. It finds the manifest of the current platform on the class path and unpacks the libraries into a per-user cache, `%LOCALAPPDATA%\rethinkj-ui\natives\` on Windows and `$XDG_CACHE_HOME/rethinkj-ui/natives/` (default `~/.cache`) on Linux, in a subfolder named after their hashes. Two system properties change that:
  - `rethinkj.ui.natives.dir`: load from this folder, which holds the libraries and their `manifest.txt` as the JAR has them. Nothing is unpacked or hash-checked, and the class path is not read. For packaged apps and GraalVM native image.
  - `rethinkj.ui.natives.cache`: unpack into this folder instead. Core's tests set it to `core/target/natives-cache`.
- Native access must be enabled for core: `--enable-native-access=com.rethinkj.ui` (core's tests pass it). On the module path, the natives JAR is resolved only with `--add-modules com.rethinkj.ui.natives.<os>.x64`.
- Loading happens only on first use. Never call `Natives` from a static initialiser that the headless path can reach: rendering without a window must not need the libraries.
- Linux cannot load a library from a file system mounted `noexec`; then the cache has to move. On Linux, a failed load reports the dynamic linker's reason, which the JDK leaves out.
- The libraries built for Linux need the glibc of the machine that built them (2.38 on Ubuntu 24.04, for SDL and FreeType), and SDL lacks what that machine had no headers for (IBus, libdecor). A build on an older distribution does not exist yet.

## GPU bindings

`com.rethinkj.ui.gpu` (internal to `core`) binds wgpu-native in two layers. `Wgpu` and `Structs` are the raw layer: constants, function and callback descriptors, struct layouts written by hand and the header's `*_INIT` defaults (zero is not always the default). Everything else is the safe layer, which the renderer uses; renderer code never sees a handle or a `MemorySegment` of wgpu.

wgpu-native ends the process where WebGPU would report an error, so the safe layer has to keep these from happening:

- Every call that can fail runs inside a validation and an out-of-memory error scope and throws `GpuException` with wgpu's text and the label. A command encoder keeps its scopes open until `finish`, which throws instead of handing out a command buffer that recorded an error. Push and pop scopes only through `Device`: popping one too many ends the process, and so does the `Internal` filter.
- Every device gets the uncaptured-error and device-lost callbacks. Upcalls catch everything and hand it to the calling code. The stubs live in `Callbacks` for the process and find their target by an id in `userdata1`.
- Check arguments that wgpu-native panics on before calling: sizes of 0, a second surface texture while one is held, a buffer still mapped when commands using it are submitted, a command buffer submitted twice, NULL handles, a bind group entry with neither buffer nor view, a texture entry of a bind group layout without a view dimension (WebGPU would take 2D, wgpu-native panics), a texel copy with 0 bytes per row or rows per image.
- Do not bind any of the 35 functions wgpu-native leaves unimplemented (`WgpuTest` lists them), and do not rely on `wgpuInstanceWaitAny`: callbacks run inside the call or inside `wgpuDevicePoll`.
- Textures for shaders to read: `Device.createTexture` makes a 2D texture, `createTextureArray` an array of layers whose views are always 2D arrays, even of one layer. `BindGroupLayout.Entry.texture` and `textureArray` (`texture_2d<f32>`, `texture_2d_array<f32>`) bind a view that the shader reads with `textureLoad`, without a sampler: the sample type is unfilterable float, which takes every float format, `R8_UNORM` among them. `BindGroup.Entry.texture` binds the view. `Queue.writeTexture` writes a rectangle of texels into one layer from memory, rows `bytesPerRow` apart from an offset, so a region of a larger image goes without copying it out first; unlike a copy between buffer and texture, the rows need no alignment of 256.

Objects belong to the thread that created their `Instance`; closing one closes what it created, newest first. After adding or changing a struct, function or callback, run `scripts/LayoutCheck.java` (its header has the commands; it needs jextract, which stays out of the repository).

## Text

Text is shaped with HarfBuzz, rasterised with FreeType into greyscale bitmaps and drawn by `CpuRenderer` and `GpuRenderer`.

- `El.text("…")` makes a text element, a leaf that layout sizes to its shaped text. Chained calls: `.font(Font)`, `.fontSize(<logical pixels>)`, `.color(0xAARRGGBB)`, `.wrapText()`, `.ellipsis()`, `.fontFeatures("+calt")`, `.textAlign(Style.Align.CENTER)` (or `END`: each line in its box, on the grid of glyph positions, also a line shortened with an ellipsis; not in fields, which scroll; `Text.Line.x()` says where a line starts; `TextRenderTest` stores `text-align-<1|2>x`), `.highlight(key, highlighter)` (see Text fields), and `.editable(onEdit)` for a text field, with `.multiline()` one of several lines (see Text fields). With `.ellipsis()` a line wider than its box ends in `…` (`Text.ELLIPSIS`): as many graphemes as fit, without the spaces before it, shaped anew with the ellipsis; layout sizes the text as before, so the element needs a width or `minSize(0, 0)` to shrink below its text, as a table's cells have. `Text.shortened()` says whether a line was shortened; the tree dump keeps the whole string, and a right-to-left run is cut before it, not inside it. `TextRenderTest` stores `text-ellipsis-<1|2>x`, and `GpuRendererTest` compares them. The defaults are `Font.sans()`, 14, opaque black and no wrapping. Each line feed starts a line; with `wrapText` it also breaks where `java.text.BreakIterator` allows, and a word wider than the box stays whole. Characters the font lacks come from fallback fonts (below); a character no font has shows as the first font's glyph 0.
- `Font.sans()`, `sansMedium()`, `sansSemibold()`, `sansBold()`, `sansItalic()`, `sansBoldItalic()`, `mono()` and `monoBold()` are Inter 4.1 (regular, medium, semibold, bold, italic and bold italic) and JetBrains Mono 2.304 (regular and bold), the static hinted TrueType files of their releases. They come in `fonts/` (`rethinkj-ui-fonts`, under `META-INF/rethinkj-ui/fonts/` with their SIL Open Font License 1.1 texts in `licenses/`); `core` uses that module only in tests, and without it these methods throw a message that names it. Other fonts: `Font.of(bytes)` or `Font.resource(owner, name)`, freed by `close()`.
- `Font.icons()` is Fluent UI System Icons Regular (MIT), the TrueType file the project publishes at its tag 1.1.345, unchanged: 2.9 MB, in `icons/` (`rethinkj-ui-icons`, under `META-INF/rethinkj-ui/icons/` with its licence in `licenses/`), loaded like the default fonts. An icon is a glyph at a private-use code point, drawn anew for some of 12, 16, 20, 24, 28, 32 and 48 pixels, each drawing at its own code point and sharp at its size. Two things set this font apart (`Font.wholePixels()`): its line is the em square, which the drawings fill, so an icon is as high as its font size (the font asks for a line gap of 0.09, which would put it a pixel low in a box a pixel too high), and its glyphs sit on whole physical pixels at every scale, also where text would use quarter pixels, so a 16-pixel drawing at scale 2 keeps strokes of two whole pixels in a box scrolled by a fraction. Icons are hinted alike under every `TextRendering`, with FreeType's auto-hinter in both directions (`Font.ICON_HINTING`), which puts the straight strokes it finds on whole pixels: the light auto-hinter that `LINUX` uses for text moves outlines vertically only and left an arrow's shaft at 16 pixels and scale 1 across two rows of pixels, 29 and 72 % covered, where the auto-hinter fills one row. A drawing whose strokes lie between two pixels in its design, such as `ADD` at 16, stays half covered under any hinting. At scale 1.5 the 16-pixel drawings have strokes of 1.5 pixels, which no position makes sharp.
- `Font.shape(text, size, scale, features...)` shapes with HarfBuzz into a `GlyphRun` in physical pixels: at `size * scale`, advances and offsets rounded to whole pixels below scale 1.5 and to quarter pixels from 1.5 on. Kerning is on and `calt` off (JetBrains Mono's ligatures); features use HarfBuzz's syntax, such as `"+calt"` or `"-kern"`. Each font keeps the last 1024 runs.
- Fallback fonts: `font.withFallback(Font...)` is a font that falls back to those fonts in order, `font.withSystemFonts()` one that then falls back to the fonts installed on the system; both are the same object for the same arguments, own no native objects, and keep the first font's metrics, so the line height stays its own. `Runs` splits the text into runs of one font and one script, without native libraries: each grapheme cluster (`BreakIterator.getCharacterInstance`: a letter with its marks, an emoji sequence, a flag, a variation selector with its base) goes to the first font that has all its characters but joiners, variation selectors, format and control characters (or all of its NFC form), else to the first font; neutrals (scripts Common and Inherited: spaces, punctuation, digits) the first font has stay with the font of the clusters on both sides when that is one font that has them. Each run is shaped on its own with HarfBuzz, in its script (`hb_buffer_guess_segment_properties` on the run alone) and direction, with the whole string as context, at the element's size, and the runs follow each other on one baseline in the order of the string. A glyph's font is `GlyphRun.font(i)`, which the scene passes to the atlas; the renderers did not change.
- Right to left: a run of Arabic, Hebrew and other right-to-left scripts is shaped right to left, so its letters join and stand in their order, and a neutral is right to left only between two right-to-left letters, not next to a number, whose digits stay left to right. Lines are not reordered by the bidirectional algorithm: runs follow each other from left to right. A right-to-left run is one cluster (every glyph at its first character), so a line does not break inside it, and in a field the caret moves through it from its left edge in proportion to its graphemes.
- The system's fonts (`text.SystemFonts`, through FreeType, without fontconfig or DirectWrite): the first cluster that no font of a chain has walks `/usr/share/fonts`, `/usr/local/share/fonts`, `$XDG_DATA_HOME/fonts` (or `~/.local/share/fonts`) and `~/.fonts` on Linux, `%WINDIR%\Fonts` and `%LOCALAPPDATA%\Microsoft\Windows\Fonts` on Windows, maps each `.ttf`, `.otf`, `.ttc` and `.otc` in turn and keeps each face's family, style and characters as ranges; it runs once per process, and the lookups are kept. Faces without outlines are left out (CBDT, COLR version 1). A cluster gets the first face with all its characters by the platform's preferred families for its script (Linux: Noto Sans, Noto Sans Symbols and Symbols 2, the Noto Sans family of the script, such as Noto Sans Arabic, DejaVu Sans, Noto Emoji, Symbola; Windows: Segoe UI, Segoe UI Symbol, Segoe UI Emoji, Leelawadee UI, Nirmala UI, Segoe UI Historic; emoji first to the emoji families), then the style nearest the text's font. The CJK families (Noto Sans CJK, or Yu Gothic UI, Microsoft YaHei UI, Microsoft JhengHei UI and Malgun Gothic) come first for Han, kana and Hangul, ordered by `Locale.getDefault()` (Japanese for other languages), with Korean first for Hangul and Japanese for kana. Private-use and unassigned characters are never looked up. A chosen face is mapped and opened as a `Font` for the process; the others are unmapped after the scan. On a Linux desktop with 408 font files in the file cache, the scan takes 0.15 to 0.25 s in a fresh process (up to 0.45 s while tests run beside it), and the index holds about 0.75 MB; on Windows 11 with 145 files it takes 0.2 s with the files in the cache and 1.1 s without, and holds 0.66 MB. So that no frame waits for it, `App.systemFonts(true)`, which a `WindowLoop` calls when it starts, begins the scan on a virtual thread (`Font.prepareSystemFonts`); a lookup before it ends waits for the rest. In a window on Windows that took the first Japanese character typed from 139 ms to 12 ms between the key and its frame.
- `App.systemFonts(boolean)` switches system fallback for the app's text; it is off, so scripts, `Headless` and tests draw the same everywhere and never scan, and a `WindowLoop` turns it on when it starts unless `loop.systemFonts(false)`. Stored images use only explicit chains: `Examples.fallbackChain()` is Inter with JetBrains Mono (its box drawing and maths), Noto Sans Hebrew and Noto Sans Thai, small OFL fonts in `core/src/test/resources/fonts`.
- Colour: glyphs are coverage in one colour, so a colour font draws only where its glyphs have outlines, in the text colour (the base glyphs of COLR version 0, as in Segoe UI Emoji, whose COLR table on Windows 11 is version 1 with version 0's records and outlines for its base glyphs; monochrome fonts such as Noto Emoji or DejaVu Sans). This FreeType has COLR layers but no PNG, so CBDT bitmaps (Noto Color Emoji) fail to load (error 7) and are left out; COLR version 1 needs a painter of its own and SVG glyphs a renderer. Colour emoji would need an RGBA atlas and a third kind of instance besides that.
- `App` and `Headless` pass the window's scale, and `App` whether to use the system's fonts, to every text element before layout (`El.scaleText`); `Flex.layout` alone shapes at scale 1. After layout, `el.text().lines()` holds what a renderer draws: per line a `GlyphRun`, its width and its baseline, in physical pixels from the top left of the content box. Layout hands the final content size to `Measure.placed`, and the lines are broken for that width.
- In a `.tree.txt`, a text element's line starts with `text` instead of `el` and has its string in quotes after the key, role and label: `text #save "Save\nall" 0,0 32x36`. Strings and labels are quoted with `\"`, `\\`, `\n` for a line feed, `\t` for a tab and `\u{E0EB}` for a character of a private use area, such as an icon, which would otherwise show as nothing or a box. A string longer than 200 UTF-16 units shows its first 100 and its last 40, each quoted, with `…` between them and its length after them: `text #query "SELECT …" … "… 1;" length 104857`. The selector `text="<string>"` matches the exact string, written the same way, so it finds a short multi-line field but not a long one, which a key or a role finds.
- `Scene` turns the glyphs of each line into glyph instances, `KIND` 1, in the same list as the rectangles (`KIND` 0), so text and boxes overlap in tree order. Their 64 bytes (of an instance's 96), the WGSL struct and the coverage formula are in `Scene`'s Javadoc; `CpuRenderer` is the reference. A glyph's bitmap is drawn one texel to one physical pixel, never resampled: the content box of a text element is snapped to the grid of the glyph positions, whole pixels vertically and, horizontally, whole pixels below scale 1.5 and quarter pixels from there, so text in a moving or scrolled box keeps its bitmaps.
- Bitmaps live in a `text.Atlas`: pages of 8-bit coverage (`scene.pages()`), keyed by font, physical size, hinting, glyph and quarter-pixel offset, bounded in entries and bytes, least recently used out first but never what the current scene uses. `Page.takeChanged()` gives the region written since the last call, for uploads; the GPU renderer takes it, so it must be the only one that does for an atlas. An `App` keeps one atlas; `Headless.render` and `Scene.of(root)` make their own.
- `TextRendering` holds the hinting and the two exponents of the coverage correction: `LINUX` (FreeType's light auto-hinter, 1.8 and 1.8) and `WINDOWS` (the font's own hints in FreeType's v40 interpreter, 1.8 and 1.4); `TextRendering.platform()` is the default. Set it with `app.textRendering(...)` or `Headless.render(root, width, height, scale, rendering)`. Tests that compare images pin `TextRendering.LINUX`, and so does `Examples.main`, so that the stored images do not depend on the machine.
- The correction thickens text darker than its background, `1 - (1 - a)^darkGamma`, and thins lighter text, `a^lightGamma`. The scene finds the background in the fills of the text element and its ancestors; it misses earlier siblings, absolutely placed boxes, borders and what lies outside rounded corners, and then decides by the text colour, biased towards thickening (thicken up to L* 60, thin from 80). When the answer is wrong, state the background: `El.text("…").textBackground(0xFFFFFFFF)`.
- The switch and list examples have text, so the tests that render them call `TextLibraries.assumeLoaded()`; tests about input, focus and motion use `Examples.switchAlone`, which has none and runs without the natives module. The views behind the stored text images are in `Examples` (`textSizes`, `greyOnLight`, `textOpacity`, `scrolledText`), so that the image tests and `GpuRendererTest` draw the same; `Examples.laidOut` lays out a view with its text shaped for a scale, as `Headless.render` does.
- The bindings are in `com.rethinkj.ui.text.ffi`, not exported, in the style of `com.rethinkj.ui.gpu`. FreeType's C `long` (64 bits on Linux, 32 on Windows) is handled only in `FreeType`: `C_LONG`, its method handles, which take a Java `long` for it, and `getLong`/`setLong`. Tests that need the libraries skip themselves where there is no natives module.

## Pixel grid

The scene that `App` and `Headless` draw (`Scene.of(root, …, scale)`) puts the boxes at rest on the physical pixel grid, as browsers do; `Scene.of(root)` without a scale draws them where layout put them. Layout stays in whole logical pixels, which at scales 1 and 2 are whole physical pixels, so there the scene is the same as before and so is every stored image; at 1.25, 1.5 and 1.75 the scene snaps. It does so in its own numbers only: `CpuRenderer`, `ReferenceCpuRenderer` and the WGSL did not change.

- Edges: each edge of a border box at logical `x` is drawn at `round(x * scale)` physical pixels, halves up, so that neighbours that share an edge in layout share it on screen, with no seam, and a box may be a pixel wider than its neighbour of the same logical width. An edge that lies on the content box of a parent with a border snaps to the inner edge of the border as drawn, so what fills a bordered box meets its border.
- Widths: borders, each side's on its own, the focus ring (`Scene.RING`) and its gap, and a side of a box of at most `Scene.HAIRLINE` (2) logical pixels, such as a separator, are `max(1, floor(width * scale))` physical pixels, as browsers round border widths. A hairline of 1 is 1 pixel at 1.25, 1.5 and 1.75, 2 at 2 and 2.5, and 3 at 3. Radii are not rounded: with whole edges and widths the straight parts of a rounded rectangle are whole rows and columns, and its border is as wide all round.
- Clips are the snapped boxes intersected; a text field's text clip is its content box widened to whole pixels, so that it cuts no glyph. Shadows are drawn from the snapped box. A text element's content box starts from its snapped box and is then put on its glyph grid as before (see Text), so text and icons move with their box by whole pixels and are drawn from the same bitmaps wherever it is; a label may sit a pixel nearer one edge of its button at one position than at another.
- Motion: while a spring moves an element's position or size (`El.isMoving`, which `Animator` sets), it and everything inside it are drawn where they are, between pixels, so that it glides instead of stepping a pixel at a time, which shows at the slow end of a spring; once it rests it snaps, by at most half a physical pixel. A scrollbar's thumb is snapped across its bar, not along it: its place and length measure the offset and move with it.
- Pointer: a window reports the pointer, which the system gives as a whole physical pixel, at the centre of that pixel, a 256th of a pixel towards its top left (`Window.position`). A pixel is drawn as part of a box exactly when that point lies in the box's layout rectangle, edges included, so a press reaches the box that drew the pixel under it at every scale, and not the box that ends where the pixel begins; `PointerPixelTest` checks every pixel of a row of boxes at 1, 1.25, 1.5, 1.75, 2 and 2.5.
- Scroll offsets stay in logical pixels, as the wheel (also in fractions from a touchpad), `revealRow` and the thumbs give them. At 1.25 a step of one logical pixel moves the content by 1 or 2 physical pixels; its edges and text land on whole pixels anyway, as above.
- `PixelGridTest` in core measures borders and hairlines at every position, neighbours, a child filling a rounded clip, scrolled content, text and an icon in a moved box, a moving knob and the scene's numbers; kit's `PixelGridTest` measures the kit's field, buttons, checkbox, tabs, a card with rows and hairlines, the data grid, a menu with its shadow and the focus ring at 1.25, 1.5, 1.75, 2.5 and 3, and stores the sheet at 1.5 on whole and on half pixels (`pixel-grid-1.5x-whole`, `-half`).
- Icons stay in the drawing for their logical size (`Symbol.codePoint`). At 1.5 the 24-pixel drawing of a 16-pixel icon has crisper straight strokes than the 16-pixel drawing scaled, but strokes of 1 pixel instead of 1.5 and other proportions; at 1.25 and 1.75 the drawings for 20 and 28 pixels had more half-covered pixels than the 16-pixel drawing (15 and 40 % of the inked pixels against 11 and 19 % for icons of straight strokes).

## GPU renderer

- `render.GpuRenderer` draws a `Scene` with wgpu. Its WGSL is the constant `GpuRenderer.WGSL`, and every line of the fragment shader has a counterpart in `CpuRenderer` and in `ReferenceCpuRenderer` (see below): change them together. The instance block and the clip table go unchanged into two read-only storage buffers, and one instanced draw call, four vertices per instance as a triangle strip, draws all instances in order, rectangles, glyphs and shadows alike. The buffers double when a scene needs more and are kept for the next frame. The shader declares the slots in which the kinds differ as `u32` and bitcasts them to `f32` where they hold floats: a glyph's small integers read as floats would be subnormals, which a GPU may flush to zero.
- Corners and sides: `El.radius(topLeft, topRight, bottomRight, bottomLeft)` gives each corner its radius, which fill, border, clip, shadows, the focus ring and hit testing follow, and `El.border(top, right, bottom, left, argb)` each side its width in one colour; a side of 0 has none, so `border(0, 0, 1, 0, c)` is a line along the bottom of a box with no element for it. An instance is 96 bytes since then (`Scene`'s Javadoc says why it grew, and keeps the first 64 bytes as they were): a rectangle's and a shadow's other three radii at 64, a rectangle's other three borders at 80; the clip table's entry holds the four radii in its 32 bytes. A pixel takes the radius of the corner on its side of the centre; with every corner alike the formulas and the bits are those of a single radius. The fill shows inside the rectangle moved in by each side's border and out by a physical pixel on a side without one, so that no border colour shows in its smoothed edge; its corners have the radius less the border on either side, as in CSS, and where the two differ a quarter of an ellipse, whose first-order distance (`(k - 1) k / |q / r|`) the renderers take. A shadow whose corners differ is the box less each rounded corner's square plus its quarter disc, the crossed boxes' blur where all four are alike (`ShadowTest` holds it within 0.006 of a brute-force sum too). `CpuRenderer` keeps its runs: along a row that the fill does not reach, as the bottom border of a grid's row, they are runs of the border colour; a fill with elliptic corners is measured at every pixel. `Examples.shapes` (`shapes.txt`, stored as `shapes-1x` and `shapes-2x`) shows them all with a ring with a gap; `GpuRendererTest` compares it and a scene of fractional borders and radii (`sides`) at scales 1, 1.5 and 2, and `aWrongShapeShaderIsNoticed` swaps the right corners, makes the inner corners circles, leaves the fill's edge on a side without a border, and gives a shadow's or a clip's corners all the top left radius, each failing hundreds to thousands of pixels.
- Shadows (`El.shadow(Shadow...)`, CSS's `box-shadow` without `inset`: offset, blur, spread and colour, the first on top) are a third kind of instance, `Scene.SHADOW`, drawn right before their element with its clip and opacity, over the shape grown by three deviations. A shadow shows also under a translucent fill, and it does not spring with `motion`. Its coverage is an analytic Gaussian blur of the rounded rectangle, evaluated per pixel with no offscreen pass or texture: two crossed boxes, whose blur is a product of `erf` differences and exact, and four quarter discs at the corners, each in eight slices of exact Gaussian mass across within three deviations; the deviation is half the blur radius with a pixel's share added (variance 1/12), so a shadow without blur gets an antialiased edge. `erf` is Abramowitz and Stegun's 7.1.28, arithmetic only and within 3e-7, written the same in WGSL and `CpuRenderer`, where the only other function is `sqrt`. `ShadowTest` compares the formula with a brute-force sum over a grid of cells: square corners within 1e-5, rounded ones within 0.006 (radius 0, small, half the height, blur below and above the radius, a spread, a menu's tight layer). A dialog of 400 by 240 with the dark theme's two shadows adds 8 ms at scale 1 and 33 ms at scale 2 to a CPU frame, most of it near the rounded corners, where each pixel takes the eight slices. Within three deviations at most 0.14 % of the colour is cut off, below a step for a dark shadow; a light glow on black can show that edge faintly. Gradients of a dark shadow on a dark surface step by single 8-bit levels, a few physical pixels apart, as in browsers; dithering in both renderers would hide them.
- A glyph's quad covers exactly its texels, from the physical pixel `floor(x * scale + 0.5)` on, as the CPU's `Math.round`; the fragment reads its texel with `textureLoad`, never a sampler. The atlas pages are the layers of one `r8unorm` texture array, page `i` in layer `i`: one array keeps the single draw call, since WGSL cannot choose among bound textures by a per-instance index. Before each draw the renderer writes into each layer the region `Page.takeChanged()` reports, nothing for an unchanged page, and a page it has not seen in that layer whole, once. More pages than layers, or pages of another size, replace the array by one with the next power of two of layers (at most `maxTextureArrayLayers`, 256 or more), and every page is written whole again. `GpuPresenter.atlasUploads()` counts the writes; a frame without new glyphs, and an idle window, upload nothing.
- It draws only into sRGB targets, with premultiplied blending (`one, one-minus-src-alpha`), so that the GPU blends in linear light and the target encodes: `RGBA8_UNORM_SRGB` for images, `BGRA8_UNORM_SRGB` (or `RGBA8_UNORM_SRGB`) for windows. `GpuRenderer.create()` and `render(scene, width, height, scale)` draw into `Pixels` without a window, like `CpuRenderer.render`.
- `render.GpuPresenter` is the `WindowLoop.Presenter` that owns a window's surface (Direct3D 12 on Windows, Vulkan on Linux, FIFO, opaque) and configures it with the window's size in physical pixels. FIFO paces nothing where the display holds no frame back: on a machine whose display is virtual, FIFO, MAILBOX and IMMEDIATE all returned from presenting at once, more than a thousand times a second in a tight loop, on Direct3D 12 and Vulkan alike. So `WindowLoop` itself draws input and posted tasks that arrive less than a refresh after the building of the last frame began only once that refresh has passed, with whatever else arrived meanwhile, and input after a pause at once. It draws nothing while the window is minimized. When the surface is out of date, lost or times out, it reports `pending()`, and the loop offers the newest frame again a refresh later; the presenter then reads the window's size again. Close it before the window.
- `GpuRendererTest` compares the GPU's images with the CPU's: the views behind every stored image of core, which it builds as their tests and scripts do and checks against the stored PNG first (`theCasesIncludeTheViewBehindEveryStoredImageOfCore` fails when a stored image has no case), and scenes that stress one formula each, at scales 1, 1.5 and 2. The text scenes have 11 to 14 pixels in both fonts on light, dark and grey with both `TextRendering`s, opacity, rounded clips, translucent boxes over and under text, an atlas of 64-texel pages that a frame fills several of, and empties for the next, text fields with a selection, a caret and a composition, scrolled and in the rows of a list, and fallback fonts in lines and a field (`Examples.fallbackText`, `fallbackField`). Overlays are there too: a menu with its submenu across the rounded clip of a scrolled list, and a dialog over a scrim, all with shadows. So are shadows of their own (`shadows`): on light and dark, under text and translucent boxes, cut by a rounded clip, at half opacity, overlapping, wide, sharp, coloured and three on one element; `aWrongShadowShaderIsNoticed` makes the blur a tenth wider, leaves out the pixel's share or the corners, takes the slices at their top and leaves out the clip, and each fails hundreds to thousands of pixels. The kit's data grid is there too: core's tests cannot see the kit, so `Examples.grid` builds the grid of `Orders` as `DataGrid` does, from core's elements in `Theme.DARK`'s values; the test first checks that it draws the kit's stored images `grid-dark-*` from kit's `grid.txt`, then compares at scales 1.5 and 2. A change of the grid's look shows there, and `Examples.grid` follows it. A channel may differ by 1 step of 8 bits, and by half a step more for each further instance that draws into the pixel, because the GPU rounds into the 8-bit target after every draw (`tolerance` says why). On top of that comes what the GPU's blending can add: it takes the source's alpha at the 8 bits of the target, so a layer lets up to 1/255 more or less of the light under it through (`ALPHA_STEP`); under nearly opaque dark text on white that measured up to 4 steps near black, and the test adds what it can be at each pixel, from the CPU's blends (`CpuRenderer.Blends`). `aWrongGlyphShaderIsNoticed` breaks the texel mapping, the reading of texels, the correction and the clip one at a time; each fails thousands of pixels. A failing scene leaves `.cpu.png`, `.gpu.png` and `.diff.png` in `core/target/gpu-vs-cpu`. The test is skipped without the natives module or an adapter.
- `Png.decode` reads PNG files without `java.desktop`: grey, grey with alpha, RGB, RGBA and palette images of 1, 2, 4, 8 and 16 bits per sample as the format allows them (sixteen keep their high byte), the transparency of `tRNS` by palette and by colour key, the five row filters and every chunk's CRC, into straight RGBA `Pixels`; interlaced images are refused with a message that says so. `PngTest` reads images that Pillow wrote (`core/src/test/resources/png`) against the pixels Pillow reads, and rows of all five filters. Nothing draws an image yet: an image element needs a fourth kind of instance, or a texture per image, in `Scene`, both CPU renderers and the WGSL.
- `CpuRenderer` draws the same bits as a loop that evaluates every formula at every pixel of every instance, and is fast by leaving out only what it knows, never by computing it another way: in each row, the pixels that a rounded rectangle, its fill and its clip cover whole (coverage exactly 1) are one run, whose ends it finds by evaluating from both sides, and a clip that covers the four corner pixels of an instance's box covers all of it, because every step of the coverage is monotonic also in doubles (`CpuRenderer.Box` says why); a glyph's corrected coverage is computed once per texel value and frame, a shadow's blur across x once per column and across y, with the slices of its corners, once per row; the encoding to sRGB is kept per pixel value and per channel value. `CpuRendererEquivalenceTest` compares it with `ReferenceCpuRenderer` in the test sources, the plain loop as it was, byte for byte, the floats before encoding and every blend `Blends` sees included: on `GpuRendererTest`'s scenes, the shapes of `ShadowTest`, 3000 random scenes with fractional and non-finite values, and frames that make the encoder's slots collide. Against the plain loop, on a desktop with 12 threads under a load of 4 to 6: an 800 by 600 rectangle 5 ms (was 137), the data grid at scale 2 14 ms (216), text at scale 2 8 ms (112), the rows of a million at scale 2 3 ms (85), each with 3 to 13 ms of `Png.encode` on top when a script snaps it.

## Windows

- `com.rethinkj.ui.window` opens windows through SDL 3 (`Window`), turns SDL's events into `WindowEvent`s and runs an `App` in a window (`WindowLoop`), which hands each new frame to a `Presenter`. `Sdl` and `Win32` hold the handwritten bindings: a new function gets its descriptor as a constant there and its handle in the class's lazy holder.
- Windows are used on the thread that opened the first one, until all are closed. Every event is translated in an SDL event watch as SDL queues it (a wheel that turns only up and down with Shift held as one that turns sideways, as in the system's own apps) and delivered in that order by `Window.pollEvents` or `waitEvents`; SDL's own queue only ends the wait. On Windows the listener is also called from inside the system's move and resize loop, with `Redraw(live = true)`.
- The hit test, the event watch and the Windows subclass are upcalls: each catches every `Throwable` and hands it to `Window.fail`, and the next `pollEvents` or `waitEvents` throws it. One that escapes ends the JVM.
- Text input is off until `Window.textInputArea` turns it on, which `WindowLoop` does while the focused element takes text (`App.inputArea`), and `stopTextInput` turns it off. `WindowLoop` also gives the app the system clipboard (`SystemClipboard`, through SDL) and the system's fonts (`App.systemFonts`), passes the click count and modifiers of a press (a second press counts as a double one within the system's distance, half of `SM_CXDOUBLECLK` on Windows and 5 pixels elsewhere, which `Window` sets as SDL's `SDL_MOUSE_DOUBLE_CLICK_RADIUS` in place of its 32 for touch screens), and wakes an idle window for the caret's blink, hover delays and the actions an app asks for with `App.after` (`App.nextChange`).
- A frameless window draws its own title bar: the view marks elements with `El.windowPart`, and `App.windowPart` answers SDL's hit test. Where a press would go to a control (`WindowPart.CONTROL`: an element with a press or drag handler, a text field, a scrollbar's strip) or to a minimize, maximize or close part, the resize margin narrows to `Window.CONTROL_MARGIN`, 2 pixels, so that a scrollbar along the window's edge can be grabbed at its outer pixels; the corners keep their reach. The Windows 11 parts (rounded corners, snap layouts on the maximize part, system menu on a right click) are in `Win32Frame`; Alt+Space that no key handler takes opens the system menu below the drag area at the left edge (`Window.showSystemMenu`, which `WindowLoop` calls through `App.keyDown(key, untaken)`), on a framed window too, since SDL keeps the key from the system, whose Javadoc also says why the resize margin lies inside the window. `Win32Frame` also gives a minimized frameless window no client area, as Windows does for a framed one; otherwise SDL reports the 160 by 28 pixels of a minimized window when the system restores it.
- Icons: `WindowIcon.of(Pixels...)` (square, straight alpha, as `Pixels` is) or `WindowIcon.of(size -> view)`, a view laid out in a square of `size` logical pixels at scale 1 and drawn by `Headless.render` (without natives unless it has text); `AppIcon.appIcon(theme, size, colour, symbol)` in the kit is a rounded square in the app's colour with a symbol of the icon font. `Window.options().icon(icon)` sets it before the window shows, `window.icon(icon)` later. It goes to `SDL_SetWindowIcon` as a surface with alternate images (Linux: 64 with 128 and 256, which only Wayland's `xdg_toplevel_icon_v1` uses; X11 gets the base). SDL's Windows driver makes one `HICON` of the base image for both sizes, so `Win32Shell`, a second window subclass beside `Win32Frame`'s, also sets the small (16 × scale) and big (32 × scale) icon with `WM_SETICON`, again when the scale changes, and again with new handles when `TaskbarButtonCreated` arrives: the taskbar asks for the icon when it makes the button, and while the app's thread is busy (setting up the GPU right after the window opens) it times out and keeps java.exe's class icon.
- Identity: `Window.identity(id, name)`, before the first window, goes to `SDL_SetAppMetadata` (Wayland app id, X11 class) and on Windows to `SetCurrentProcessExplicitAppUserModelID`: the app's windows group under a taskbar button of their own with the window's icon, instead of under java.exe. Its jump list then offers no "Pin to taskbar", since Windows cannot tell how to start the app; with a Start menu shortcut that carries the same `System.AppUserModel.ID` and an `.ico`, the list names the shortcut, pinning works and the pinned button starts what the shortcut says and shows its icon. That shortcut is a packaging matter (an installer, jpackage). The examples each have an id `com.rethinkj.ui.examples.<class>` and an icon (`Identity`).
- Appearance: `Window.systemAppearance()` is a `SystemAppearance`: the scheme from `SDL_GetSystemTheme` (on Windows `AppsUseLightTheme`), the accent as 0xFFRRGGBB from `HKCU\Software\Microsoft\Windows\DWM\AccentColor` (the colour chosen in Settings, stored as ABGR; `DwmGetColorizationColor` is the frame's colorization colour, the same RGB with alpha C4, and only the fallback) and high contrast from `SPI_GETHIGHCONTRAST`. Every window gets `WindowEvent.AppearanceChanged`: from SDL's `SDL_EVENT_SYSTEM_THEME_CHANGED`, and on Windows when `Win32Shell` sees `WM_SETTINGCHANGE`, `WM_SYSCOLORCHANGE` or `WM_DWMCOLORIZATIONCOLORCHANGED` after SDL has handled it and the value differs. `WindowLoop.appearance(handler)` hands it to the app as a posted task at the start and on each change; the kit's themes stay values, and Showcase's look "System" and Settings' theme "System" pick dark or light from it. Linux reports no accent (0) and no high contrast. What high contrast should mean for an app is in `SystemAppearance`'s Javadoc. Drive the Settings switch with `AppsUseLightTheme` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` and a `WM_SETTINGCHANGE` broadcast with `"ImmersiveColorSet"`, and restore it.
- Taskbar: `window.attention(Attention.BRIEFLY | UNTIL_FOCUSED | NONE)` is `SDL_FlashWindow`. `window.badge(icon, description)` is `ITaskbarList3::SetOverlayIcon` with an icon of 16 × scale pixels (`AppIcon.count`, `AppIcon.dot`), through a taskbar list that `Win32Shell` creates with `CoCreateInstance` on the windows' thread (SDL initialised COM there) and releases before `SDL_Quit`; it waits for `TaskbarButtonCreated` and is set again when Explorer restarts. COM methods are called through the vtable by hand (`Win32.method`, address-less downcall handles). Linux has no badge. Workbench counts its questions on the badge and flashes when an answer arrives in the background.
- `window.frameDark(boolean)` sets `DWMWA_USE_IMMERSIVE_DARK_MODE`: a framed window's caption and border follow the app's theme instead of the system's. SDL already makes every window follow the system's setting (`WCA_USEDARKMODECOLORS`, `SetPreferredAppMode`), and a frameless window's border and every system menu stay with it; the attribute does not change a frameless window's border (`DWMWA_BORDER_COLOR` would). Mica and acrylic (`DWMWA_SYSTEMBACKDROP_TYPE`) need the content to be transparent where they show, and wgpu offers only an opaque surface for an HWND (D3D12 and Vulkan both report `OPAQUE` alone); wgpu-native's other Windows source is a WinUI `SwapChainPanel`.
- Tests that open windows skip themselves without the natives module or a display. The demo in the test sources draws the light switch with its label with `GpuPresenter`: build with `mvn -pl core -am test-compile`, then from the repository root `java --enable-native-access=ALL-UNNAMED -cp "core/target/classes;core/target/test-classes;natives-windows-x64/target/classes;fonts/target/classes" com.rethinkj.ui.window.WindowDemo` (on Linux, with `:` between the entries and `natives-linux-x64`). It prints every frame it presents with the atlas uploads so far; `--cpu-png=<file>` writes the CPU's image of the last frame when it stops, to compare with a screenshot of the window, and `--text=linux` or `--text=windows` overrides the platform's `TextRendering`. `--exit-after=<seconds>` and its other options are in its Javadoc; keep windows short-lived when you drive them with synthetic input. SDL drops the click that activates a window, so click once on the background first. Windows 11 rounds the corners of a frameless window and draws a 1-pixel border over its edge, so leave the edge out of such a comparison.

## Conventions

- A new module gets the directory `<name>/`, the artifactId `rethinkj-ui-<name>` and the base package `com.rethinkj.ui.<name>`, and is listed under `<modules>` in the root `pom.xml`; a natives module, in the profile of its platform.
- Shared build configuration (Java release, encoding, plugin and dependency versions) belongs in the root `pom.xml`. Module POMs declare only what is specific to them.
- Dependencies point one way: `kit` depends on `core`, never the reverse.
- The version is repeated in every module's `<parent>` block. Change it with `mvn versions:set -DnewVersion=<version>`, not by editing one POM.

## Changes

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <summary>`, for example `feat(core): add text shaping`. The scope is the module when the change stays in one. A breaking change gets `!` before the colon.
- Keep commit messages short: a subject line of at most 72 characters, and a body only when the diff doesn't show why. No lists of changed files and no test or verification reports.
- For a change that users of the library can notice (new or changed API, changed behaviour, a fix, a raised requirement), add `changelog/unreleased/<YYYY-MM-DD>-<slug>.md` with one top-level bullet written for those users. These files are folded into `CHANGELOG.md` at release.
- Don't add files that describe your own work: no `VALIDATION.md`, `SUMMARY.md`, plans, reports or review notes. What changed and why goes in the commit message; anything longer goes in the pull request description.

## This repo is public

Everything pushed stays public in history. Before committing, run `git diff --cached | grep -nE '/home/|/Users/|/private/var/|\.ts\.net|ses_[A-Za-z0-9]{20}'` and keep these out:

- secrets, tokens and credential file contents;
- home folder and temp paths, machine names and tailnet hostnames. Write repo-relative paths, and use `host.example.ts.net` in tests;
- session IDs, chat or Slack links, and quotes from private sessions, chats or calls;
- issue numbers, links and suggested branch names from a private issue tracker;
- teammates' names attached to their plans, opinions or internal discussions, and private repos or branches;
- quotes of, or citations to, internal guides and rules. Say what the code does and why on its own terms;
- agent handoff notes (`REVIEW-TO-PARENT.md` and similar), raw evidence, logs and benchmark dumps;
- generated videos and strips nothing links to. Commit the stills a doc shows.
