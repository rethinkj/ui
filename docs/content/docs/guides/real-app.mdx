Everything lives in one class, `Customers`.

## 2. Loading data in the background

Loading from a server can be slow, so never block the app thread. Call `app.background(...)` to run the request on a background thread and deliver the result back to the app thread, where handlers can safely update state (see [Work off the app's thread](/docs/concepts/background-work)).

Store the returned `Work` handle in your state:
- When `loading` is non-null, a load is in progress.
- Calling `cancel()` prevents either callback from running and interrupts the worker thread (the computation itself stops only if it responds to interruption, so clicking **Reload** while a non-interruptible request is running may overlap with the previous request).

Here, switching away from the Customers view cancels an active load, and clicking **Reload** cancels the previous load before starting a new one.

## 3. Editing a record

The dialog edits a copy of a customer. An `Editing<Customer>` object in the state tracks the current values, unparsed input text, and validation errors. When `editing` is non-null, the dialog is shown.

Each form field receives a `Prop` from `editing.at(...)`, such as `editing.at(Customer.EMAIL)`. This avoids wiring separate value, change handler, and error fields by hand (see [Form](/docs/components/form#with-a-prop)).

- The name field rejects blank text. Its error appears after the user edits the field or calls `showErrors()`.
- A cross-field validation rule checks `company` and `vatId` together and displays its error on the VAT ID field immediately.
- **Save** becomes enabled once the user makes a change. Clicking **Save** while invalid calls `showErrors()` so untouched required fields display their errors too.

## 4. Saving and handling server errors

Saving runs in the background just like loading:
- While saving, `saving` puts the **Save** button in a busy state and disables **Cancel**.
- The mock server rejects duplicate email addresses by throwing an exception with the field name. Calling `prop.error(message)` attaches the server error to that field until the user edits it.
- On success, the handler updates the customer list, closes the dialog (`editing = null`), and displays a [Toast](/docs/components/toast).
- Fields stay editable during the save. If the user keeps typing while the request is running, the dialog stays open with those new edits on top of the saved customer instead of discarding them.
