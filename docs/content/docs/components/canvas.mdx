`Canvas.canvas` lays nodes, any elements, at positions in diagram coordinates on an area that the user pans and zooms. It is the base of the diagrams in the optional module `rethinkj-ui-diagram`, package `com.rethinkj.ui.diagram`:

```xml
<dependency>
  <groupId>com.rethinkj.ui</groupId>
  <artifactId>rethinkj-ui-diagram</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

Javadoc: [`Canvas`](/api/com/rethinkj/ui/diagram/Canvas.html).

## Example

```java snippet="canvas"
```

Keep a `Canvas.Viewport` and the nodes in your app state and pass `Canvas.canvas(viewport, nodes, content, onMove)`:

| Parameter | Description |
| --- | --- |
| `viewport` | The diagram point at the canvas's top left and the zoom; `fit()`, `zoomIn()`, `zoomOut()`, `zoomBy(steps, x, y)` and `panTo(left, top)` change it |
| `nodes` | `Canvas.Node(key, label, x, y, width, height, pinned)`, in diagram coordinates at 100 % |
| `content` | Builds a node's element at the zoom of the moment, sized `width × zoom` by `height × zoom` |
| `onMove` | Receives a dragged node, moved and pinned, and the node as it was when Escape cancels the drag (`null` fixes the nodes) |

Zoom does not scale a picture: the canvas lays its nodes out again at their sizes times the zoom, so text stays sharp. The `content` function multiplies its own sizes by the zoom and is the level of detail: zoomed out, a node can show less, as the tables above drop their columns below 75 %. The zoom moves in the steps of `Viewport.ZOOMS`, 25 % to 200 %.

The canvas builds only the nodes that lie inside it, so a large diagram stays fast. Pins are plain values in your state: the canvas only reports that the user moved a node.

The canvas learns its size from layout when that size changes. To show another diagram in the same place with a new `Viewport`, give the canvas another key, such as `canvas(...).key(diagram.name())`; with the same key the new viewport learns no size and shows no nodes.

## Edges

Pass a list of `Canvas.Edge` to draw lines between the nodes, under them:

```java snippet="canvas-edges"
```

<Shot src="examples/docs/canvas-edges/view-{theme}" alt="Three tables with a straight gray edge from customer to order and a highlighted blue edge with two bends from address to order, each with crow's foot markers" />

An edge runs from one `Canvas.Port(node, y)` to another: a node's key and the middle of a row in it, from the node's top at 100 %. The canvas routes the edges again in each build, so they follow a node while it is dragged:

- Each edge leaves a node on its left or right side, whichever faces the other end, and bends at right angles with rounded corners. It goes around the nodes in the way where it finds a free path. Its ends run straight for as far as their markers need; where two nodes face each other too closely for that, the edge goes around them.
- Every edge gets a lane of its own beside the others, also where several end at the same port. There they join when they show the same marker; with different markers, they end beside each other, so that each shows its own.
- An edge from a node to itself loops on one side of it. Where both sides are as good, it takes the one where fewer other edges end. One from a port back to the same port goes around the node, or, where its two markers differ and so end beside each other, loops between them.
- Two edges between the same two points at one height do not lie on each other: later ones bump out a lane at a time, below and then above, to the nearest place where neither a node nor another edge is in the way. Where the gap between the nodes has no room for a bump's bends and markers, they share the line.

| Field | Description |
| --- | --- |
| `key` | Unique among the canvas's nodes and edges |
| `label` | The text of its tooltip and its label in a tree dump; `null` for neither |
| `from`, `to` | The ports it connects |
| `fromMarker`, `toMarker` | `NONE`, `ONE` (`\|\|`), `ZERO_OR_ONE` (`o\|`), `ONE_OR_MANY` (`\|<`), `ZERO_OR_MANY` (`o<`), or `ARROW` |
| `emphasis` | `NORMAL` in the strong border color, `HIGHLIGHTED` in the accent color and wider, `DIMMED` mixed towards the canvas color |
| `description` | A muted line below the label in the tooltip, such as `ON DELETE SET NULL`; `null` for none |

The edges' sizes, such as the bend radius, the space between lanes and the markers' length, are in `EdgeStyle`. Zoomed out so far that a marker would be smaller than `smallestMarker`, edges show none. Give the canvas other sizes with `app.provide(EdgeStyle.CURRENT, ...)`. Edges have no colors of their own: they take the theme's.

## Saving as an image

`Canvas.png(nodes, view)` returns the whole diagram as PNG bytes, not only the part a canvas shows, and your app decides where they go. `view` builds the canvas at the viewport it is given, as your view does, such as `viewport -> canvas(viewport, nodes, Tables::card, null)`, so that everything the canvas draws is in the image. The image is cropped to the nodes with a margin, at 100 % and a scale of 2, and drawn without a window or a GPU. It takes the theme of `Theme.CURRENT` where it is called; a handler runs outside the view's, so it gives your theme again: `Theme.CURRENT.with(state.theme, () -> Canvas.png(...))`. Above 16 megapixels it falls back to a scale of 1, and a diagram too large for that as well throws an `IllegalArgumentException` before anything is drawn.

A canvas with edges passes them too, `Canvas.png(nodes, edges, view)`, so that the image takes in the edges with their markers, also an edge that loops outside the nodes.

## Pointer and keyboard

Dragging empty space pans. Dragging a node moves it; Escape cancels the drag and puts it back. Node content with a press or drag handler of its own, such as a button, keeps the pointer there: a drag that starts on it does not move the node. While the canvas has the focus, **+** and **-** zoom in and out around its center and **0** fits all nodes in.

## Arrange

`LayeredLayout.arrange(nodes, edges)` places the nodes in layers, so that the edges between them run one way. It is a plain function: it returns the nodes in the same order at new places, and your app keeps them as it keeps a drag. Javadoc: [`LayeredLayout`](/api/com/rethinkj/ui/diagram/LayeredLayout.html).

<Shot src="examples/docs/canvas-arrange/view-{theme}" alt="Five tables arranged in three layers by their foreign keys" />

```java snippet="canvas-arrange"
```

An `Edge(from, to)` goes from a node to the one it refers to, such as a table's foreign key to the table it references, and the one referred to comes first, on the left. Edges to keys that are not among the nodes, such as tables you filter away, and edges from a node to itself are left out. The layout breaks cycles, reduces crossings and runs most edges straight. Parts that no edge connects, and clusters, are packed in rows.

A pinned node stays where it is: each cluster moves so that its pinned nodes lie where it would put them, and a node that would overlap one moves past it. Unpinned nodes keep clear of all others, while pinned ones stay put even on top of each other, so where pins bring clusters together, the clusters' areas can overlap. To arrange everything, unpin the nodes first. The places of unpinned nodes going in do not matter, so the same input always gives the same output. `LayeredLayout.options()` changes the rest:

| Option | Description |
| --- | --- |
| `direction(direction)` | `LEFT_TO_RIGHT` (the default) or `TOP_TO_BOTTOM`, with the nodes referred to on top, for trees |
| `gaps(layer, node, cluster)` | The room between layers, between the nodes of a layer and between clusters: 80, 32 and 96 |
| `cluster(node -> name)` | Lays out each cluster, such as each schema, on its own with the edges inside it |

The first run of each edge is `role=graphics-symbol` with its key and label, and the value `Highlighted` or `Dimmed` for that emphasis.
