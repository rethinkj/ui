`Canvas.canvas` lays nodes, any elements, at positions in diagram coordinates on an area that the user pans and zooms. It is the base of the diagrams in the optional module `rethinkj-ui-diagram`, package `com.rethinkj.ui.diagram`:

```xml
<dependency>
  <groupId>com.rethinkj.ui</groupId>
  <artifactId>rethinkj-ui-diagram</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

Javadoc: [`Canvas`](/api/com/rethinkj/ui/diagram/Canvas.html).

## Example

```java snippet="canvas"
```

Keep a `Canvas.Viewport` and the nodes in your app state and pass `Canvas.canvas(viewport, nodes, content, onMove)`:

| Parameter | Description |
| --- | --- |
| `viewport` | The diagram point at the canvas's top left and the zoom; `fit()`, `zoomIn()`, `zoomOut()`, `zoomBy(steps, x, y)` and `panTo(left, top)` change it |
| `nodes` | `Canvas.Node(key, label, x, y, width, height, pinned)`, in diagram coordinates at 100 % |
| `content` | Builds a node's element at the zoom of the moment, sized `width × zoom` by `height × zoom` |
| `onMove` | Receives a dragged node, moved and pinned, and the node as it was when Escape cancels the drag (`null` fixes the nodes) |

Zoom does not scale a picture: the canvas lays its nodes out again at their sizes times the zoom, so text stays sharp. The `content` function multiplies its own sizes by the zoom and is the level of detail: zoomed out, a node can show less, as the tables above drop their columns below 75 %. The zoom moves in the steps of `Viewport.ZOOMS`, 25 % to 200 %.

The canvas builds only the nodes that lie inside it, so a large diagram stays fast. Pins are plain values in your state: the canvas only reports that the user moved a node.

The canvas learns its size from layout when that size changes. To show another diagram in the same place with a new `Viewport`, give the canvas another key, such as `canvas(...).key(diagram.name())`; with the same key the new viewport learns no size and shows no nodes.

## Pointer and keyboard

Dragging empty space pans. Dragging a node moves it; Escape cancels the drag and puts it back. Node content with a press or drag handler of its own, such as a button, keeps the pointer there: a drag that starts on it does not move the node. While the canvas has the focus, **+** and **-** zoom in and out around its center and **0** fits all nodes in.

## Arrange

`LayeredLayout.arrange(nodes, edges)` places the nodes in layers, so that the edges between them run one way. It is a plain function: it returns the nodes in the same order at new places, and your app keeps them as it keeps a drag. Javadoc: [`LayeredLayout`](/api/com/rethinkj/ui/diagram/LayeredLayout.html).

<Shot src="examples/docs/canvas-arrange/view-{theme}" alt="Five tables arranged in three layers by their foreign keys" />

```java snippet="canvas-arrange"
```

An `Edge(from, to)` goes from a node to the one it refers to, such as a table's foreign key to the table it references, and the one referred to comes first, on the left. Edges to keys that are not among the nodes, such as tables you filter away, and edges from a node to itself are left out. The layout breaks cycles, reduces crossings and runs most edges straight. Parts that no edge connects, and clusters, are packed in rows.

A pinned node stays where it is: each cluster moves so that its pinned nodes lie where it would put them, and a node that would overlap one moves past it. Nodes never overlap, but where pins bring clusters together, their areas can meet. To arrange everything, unpin the nodes first. The places of unpinned nodes going in do not matter, so the same input always gives the same output. `LayeredLayout.options()` changes the rest:

| Option | Description |
| --- | --- |
| `direction(direction)` | `LEFT_TO_RIGHT` (the default) or `TOP_TO_BOTTOM`, with the nodes referred to on top, for trees |
| `gaps(layer, node, cluster)` | The room between layers, between the nodes of a layer and between clusters: 80, 32 and 96 |
| `cluster(node -> name)` | Lays out each cluster, such as each schema, on its own with the edges inside it |
