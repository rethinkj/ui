`Canvas.canvas` places nodes (any elements) at diagram coordinates in an area that users can pan and zoom. It is the base for diagrams in the optional `rethinkj-ui-diagram` module (package `com.rethinkj.ui.diagram`):

```xml
<dependency>
  <groupId>com.rethinkj.ui</groupId>
  <artifactId>rethinkj-ui-diagram</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

Javadoc: [`Canvas`](/api/com/rethinkj/ui/diagram/Canvas.html).

## Example

```java snippet="canvas"
```

Keep a `Canvas.Viewport` and your nodes in your app state, and call `Canvas.canvas(viewport, nodes, content, onMove)`:

| Parameter | Description |
| --- | --- |
| `viewport` | Stores the zoom level and the diagram point at the top-left corner of the canvas. Change it with `fit()`, `zoomIn()`, `zoomOut()`, `zoomBy(steps, x, y)`, and `panTo(left, top)` |
| `nodes` | List of `Canvas.Node(key, label, x, y, width, height, pinned)` items, in diagram coordinates at 100% zoom |
| `content` | Builds each node's element for the current zoom level, sized `width × zoom` by `height × zoom` |
| `onMove` | Called with the moved, pinned node when a user drags it, or with the original node if Escape cancels the drag (pass `null` to lock nodes in place) |

Zooming does not scale a static image. Instead, the canvas lays out each node again at its size multiplied by the zoom, so text stays sharp. Your `content` function scales its own sizes by the zoom and can change the level of detail. For example, the tables above hide their columns below 75%. Zoom levels follow the steps in `Viewport.ZOOMS`, from 25% to 200%.

The canvas only builds nodes inside the visible area, so large diagrams stay fast. Pins are plain values in your app state. The canvas only reports that the user moved a node.

The canvas records its size from layout whenever that size changes. If you switch to a different diagram with a new `Viewport` in the same spot, give the canvas a new key, such as `canvas(...).key(diagram.name())`. If you reuse the same key, the new viewport gets no size and shows no nodes until the canvas size changes.

## Edges

Pass a list of `Canvas.Edge` items to draw connecting lines under the nodes:

```java snippet="canvas-edges"
```

<Shot src="examples/docs/canvas-edges/view-{theme}" alt="Three tables with a straight gray edge from customer to order and a highlighted blue edge with two bends from address to order, each with crow's foot markers" />

An edge connects two `Canvas.Port(node, y)` points, where `node` is the node's key and `y` is the offset from the node's top at 100% zoom (such as the center of a row). The canvas recalculates edge routes whenever the nodes, edges, or edge style change, so edges follow a node while you drag it. Panning, zooming, and hovering reuse the existing routes:

- Each edge leaves a node on its left or right side (whichever faces the other end) and bends at right angles with rounded corners. It routes around nodes in the way whenever it can find a clear path. Each end stays straight long enough for its marker. If two facing nodes are too close for that, the edge routes around them.
- Each edge gets its own lane beside the others, even when multiple edges end at the same port. Edges at the same port join together if they have the same marker. If they have different markers, they end side by side so each marker stays visible.
- An edge from a node to itself loops on one side of the node. If both sides are equally good, it picks the side where fewer other edges end. An edge from a port back to the same port goes around the node. However, if its two markers differ, they end side by side and the edge loops between them.
- Two edges between the same two points at the same height do not overlap. Each extra edge steps out one lane at a time (trying below first, then above) to the nearest spot that is clear of nodes and other edges. If the gap between the nodes is too narrow for those bends and markers, the edges share the same line.

| Field | Description |
| --- | --- |
| `key` | Unique key across all nodes and edges on the canvas |
| `label` | Text used for the tooltip and tree dump label (pass `null` for neither) |
| `from`, `to` | The ports it connects |
| `fromMarker`, `toMarker` | `NONE`, `ONE` (`\|\|`), `ZERO_OR_ONE` (`o\|`), `ONE_OR_MANY` (`\|<`), `ZERO_OR_MANY` (`o<`), or `ARROW` |
| `emphasis` | `NORMAL` (strong border color), `HIGHLIGHTED` (wider, in the accent color), or `DIMMED` (blended toward the canvas color) |
| `description` | Optional muted second line in the tooltip, such as `ON DELETE SET NULL` (pass `null` for none) |

Edge sizes (such as bend radius, lane spacing, and marker length) come from `EdgeStyle`. When zoomed out so far that a marker would be smaller than `smallestMarker`, edges hide their markers. Use `app.provide(EdgeStyle.CURRENT, ...)` to change these sizes. Edges have no colors of their own. They use colors from the theme.

## Saving as an image

`Canvas.png(nodes, view)` exports the entire diagram as PNG bytes, not just the visible viewport. Your app decides where to save or send those bytes. Your `view` function builds the canvas using the viewport it receives, just like your normal view (for example, `viewport -> canvas(viewport, nodes, Tables::card, null)`), so everything the canvas draws appears in the image. The image is cropped around the nodes with a margin. It renders at 100% zoom and scale 2, without needing a window or a GPU. It reads the theme from `Theme.CURRENT` where you call it. Because event handlers run outside your view's theme scope, wrap the call with your theme: `Theme.CURRENT.with(state.theme, () -> Canvas.png(...))`. If the image would exceed 16 megapixels, it falls back to scale 1. If the diagram is still too large at scale 1, it throws an `IllegalArgumentException` before drawing anything.

If your canvas has edges, pass them too: `Canvas.png(nodes, edges, view)`. Then the crop includes the edges and their markers, also an edge that loops outside the nodes. If your app uses a custom `EdgeStyle`, wrap the whole call with it just like the theme: `EdgeStyle.CURRENT.with(style, () -> Canvas.png(...))`. That way, the crop fits the edges the image draws.

## Pointer and keyboard

Drag empty space to pan the canvas. Drag a node to move it, or press **Escape** to cancel the drag and move it back. If an element inside a node has its own press or drag handler (such as a button), dragging from that element does not move the node. While the canvas has focus, **+** and **-** zoom in and out around the center, and **0** fits all nodes into view.

## Arrange

`LayeredLayout.arrange(nodes, edges)` arranges nodes in layers so that edges flow in one direction. It returns a list of the same nodes in the same order at their new positions. Store the result in your app state just like positions from a drag. Javadoc: [`LayeredLayout`](/api/com/rethinkj/ui/diagram/LayeredLayout.html).

<Shot src="examples/docs/canvas-arrange/view-{theme}" alt="Five tables arranged in three layers by their foreign keys" />

```java snippet="canvas-arrange"
```

An `Edge(from, to)` points from a node to the node it references (for example, from a table with a foreign key to the referenced table). The referenced node (`to`) is placed first, on the left. Edges using keys not in `nodes` (such as filtered-out tables) and self-edges (from a node to itself) are ignored. The layout breaks cycles, reduces edge crossings, and keeps most edges straight. Unconnected parts and clusters are packed into rows.

A pinned node stays where it is. Each cluster shifts to line up with its pinned nodes, and any unpinned node that would overlap a pinned node moves past it. Unpinned nodes stay clear of all other nodes. Pinned nodes stay put even if they overlap each other, so cluster areas can overlap when pinned nodes bring clusters together. To arrange everything, unpin the nodes first. The starting positions of unpinned nodes do not matter, so the same input always gives the same output. Use `LayeredLayout.options()` to configure the layout:

| Option | Description |
| --- | --- |
| `direction(direction)` | `LEFT_TO_RIGHT` (default) or `TOP_TO_BOTTOM` (places referenced nodes on top, useful for trees) |
| `gaps(layer, node, cluster)` | Spacing between layers, between nodes in a layer, and between clusters (defaults: 80, 32, and 96) |
| `cluster(node -> name)` | Groups nodes into clusters (such as schemas) and lays out each cluster separately using only its internal edges |
