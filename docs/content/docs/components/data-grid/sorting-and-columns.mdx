The grid shows sort keys and lets the user change them, resize columns, and choose, move, hide and freeze them. It sorts nothing and keeps nothing: the app gets the new keys, widths and layout, keeps them and gives them back on the next build. That way sorting can happen in the database, where a million rows live.

## Sorting

`options().sort(keys, onSort)` shows a `SortKey(column, descending)` list in the header, an arrow per key and their order when there are several. A press on a sortable column's header cycles ascending, descending and unsorted, replacing the keys; Shift with a press adds the column as a further key or cycles it. `onSort` gets the new list. The arrows need `rethinkj-ui-icons`.

## Resizing

`options().onResize((column, width) -> …)` lets the user drag the right edge of a header cell (beyond the grid's side, the grid scrolls along) and fit a column to its content with a double press on the edge, within the theme's `grid().minColumn()` and `maxColumn()`. The app keeps the widths and passes them to the columns.

## Fitting columns

`options().fitColumns(fit)` makes every column as wide as its header and the cells of the rows that exist, as a double press on its edge does, once per result, so that a table opens with its headers and values whole. The widths stay the app's: the grid tells each one to `onResize`, which the option needs (without it, building the view throws). `fit` is a `DataGrid.Fit` the app keeps beside the widths; `fit.reset()` fits every column again, as for a new result, where the app calls `Selection.reset()`.

```java snippet="grid-fit"
```

- The fit happens in a handler of the first frame whose rows that exist are loaded, all widths in that one handler, and the view is built once with them; a script needs one `frame` more before a `snap` shows them. In a window the first frame shows the widths the app gave, and the next the fitted ones.
- With `loading`, it waits for the first page: placeholders and headers alone are nothing to fit to. A grid without rows waits for its rows.
- Each width lies within the theme's `grid().minColumn()` and `maxColumn()`, so a column of long text does not take the grid.
- A column the user resized before the fit came is left as it is. A column a `Layout` hides is fitted when it is first shown, unless the app gave it another width meanwhile.
- It measures every column, also those out of view sideways, for the rows that exist (about 30), once: 300 columns of a million rows took 6 to 13 ms. The frames after it cost what they did.

| `Fit` | |
| --- | --- |
| `new Fit()` | A fit still to come |
| `reset()` | Fit every column again at the next build with loaded rows, also those resized by hand |
| `isPending()` | Whether the columns are still to be fitted for the result they show |

## Choosing, moving and hiding

A `DataGrid.Layout`, made with the titles of all columns and kept in the state, holds their order and which are hidden. With `options().columns(layout)`:

- the grid shows the layout of all the columns it gets;
- a header cell dragged past the threshold moves its column, with a line where it will go;
- the header's context menu has Sort ascending, Sort descending, Clear sort, Filter…, Hide column, Freeze up to here (with `onFreeze`), Fit width and Columns…;
- `DataGrid.columnsButton(t, layout)` is a toolbar button that opens the chooser: a checkbox per column, a search field beyond eight columns, Show all and Reset. Alt+Arrow Up and Down move the focused column.

With a layout, every handler, sort key and filter speaks of columns by their index among all of them; only the selection's ranges count the columns shown. `layout.shown(all)` gives the shown columns in order, and `hide`, `show`, `showAll`, `reset` and `moveBefore` change it from code.

## Freezing

`options().frozen(n)` keeps the first `n` columns, and the row numbers, at the left while the rest scroll sideways. `onFreeze(n -> …)` lets the header's menu change it.

## Reading the layout

Two kinds of column index meet in a grid with a layout. The columns the app passes to `dataGrid` are *all* columns, and handlers, sort keys, filters, `onResize`, `onFreeze` and the cells of `GridChanges` speak of them by their index in that list. The selection's `Range`s, `Selection.column()` and the keys in a tree dump (`column-<i>`, `cell-<row>-<i>`) count the columns *shown*, in the order shown. `shownColumns()` turns one into the other: `layout.shownColumns()[selection.column()]` is the index among all columns of the cursor's column.

| `Layout` method | |
| --- | --- |
| `new Layout(titles)` | All the app's columns by their titles, shown in their order |
| `shown(all)` | Those of `all` that are shown, in the order shown; throws when `all` has another size than the titles |
| `shownColumns()` | The indexes among all columns of those shown, in the order shown |
| `shownCount()` | How many columns are shown |
| `isHidden(column)` | Whether a column, by its index among all, is hidden |
| `order()` | The order of all columns, hidden ones included |
| `hide(column)`, `show(column)` | Hide and show one; the last column shown does not hide |
| `showAll()`, `reset()` | Show every column in the order they have, or in the app's order |
| `moveBefore(column, before)` | Move a column to just before another, or to the end with -1 |
| `toggleChooser()` | Open or close the chooser on the `columnsButton`, as a press on it does, for a menu item or a key of the app's |
