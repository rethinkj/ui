`Dialog.dialog` displays a centered modal overlay over a dimmed backdrop (scrim). It opens with focus on the first field Tab reaches; with none, as in a dialog of read-only `Properties`, on `defaultButton`, else on the first button. It traps keyboard focus inside while open and restores previous focus when closed. Use it for confirmations and short forms.

For lightweight non-blocking overlays, use [Popover](/docs/components/popover). For brief status messages, use [Toast](/docs/components/toast).

Javadoc: [`Dialog`](/api/com/rethinkj/ui/kit/Dialog.html), [`Dialog.Options`](/api/com/rethinkj/ui/kit/Dialog.Options.html).

Control visibility from your state by attaching `root.overlay(open ? dialog : null)`.

| Parameter | Description |
| --- | --- |
| `title` | Dialog heading and accessibility label |
| `content` | Body element (set its width, e.g. `.w(320)`, to size the dialog) |
| `buttons` | Bottom-right action buttons (omitted if empty and no `start(...)` items exist) |
| `defaultButton` | Button triggered when pressing **Enter** in a single-line or read-only field (while enabled) |
| `onDismiss` | Handler called on **Escape** or clicking the backdrop |

For a standalone dialog window, register `root.onKey(Dialog.enterPresses(button))` on the container holding the form, passing the button element from the same view build.

Custom frameless title bars remain usable behind a dialog so users can still move or close the window.

## A dialog over a dialog

A dialog can open a second one over itself, such as a form that asks for a detail or a "Discard changes?" prompt. Attach both to the root, the second one last so it lies on top. Every dialog has the key `"dialog"`, so chain a unique `.key(...)` on the second one:


Keys go to the dialog on top; while it is covered, the `onKey` handlers of the one below get none:

- **Escape** goes to the focused element first, so a focused combo box with its list open closes the list. An Escape that nothing in the top dialog takes calls the top dialog's `onDismiss` only; the one below stays open.
- **Enter** stays in the top dialog: the focused control takes it, as a combo box that opens its list, or it presses the top dialog's default button. It never presses the default button of the dialog below, not even while the top dialog's is disabled.
- **Focus:** when the top dialog closes, the focus goes back to the element that had it before the top dialog opened. That is the button that opened it if the button had the focus, as after Tab and Enter; a pointer press on a button leaves the focus where it was, such as in a field. The focus finds that element by its place among its siblings: if the build that closes the top dialog adds or removes siblings before it, as the line of properties in the example does, give the element a key (see [keys for identity](/docs/concepts/app#rules-for-your-view-function)).

| Option | Description |
| --- | --- |
| `leading(El)` | Element placed before the title |
| `trailing(El...)` | Elements at the right end of the header (long titles truncate with a tooltip) |
| `start(El...)` | Left-aligned elements in the button row |
| `defaultButton(El)` | Sets the default Enter-key button |

## Tall content

If the dialog content is taller than the window, the body scrolls automatically while the header and button row stay pinned:

## Keyboard

| Key | Action |
| --- | --- |
| Tab, Shift+Tab | Cycle focus inside the dialog |
| Enter | Click `defaultButton` (from single-line and read-only fields) |
| Escape | Call `onDismiss` |
| Page Up, Page Down | Scroll overflowing dialog content |
