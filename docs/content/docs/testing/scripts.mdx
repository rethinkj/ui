A script is a plain text file with one command per line that drives your app without a window.

Lines starting with `#` are comments. Later on a line, `#` starts a comment only when it is a standalone word outside quotes (so `#lamp` is an element key, not a comment).

## How scripts execute

Only `frame` renders a frame. Input commands (`press`, `move`, `key`, `type`, etc.) queue events, `await` queues background results, and `advance` moves the app clock. Changes appear on the next `frame`.

Inside `frame`, queued inputs run in order, each seeing the updated view from the previous input. For example, two `key ArrowDown` lines before one `frame` move a selection down two rows, and a `key` right after a `press` that opens a menu goes to that menu.

`snap` fails if you have queued steps without running `frame` afterward, preventing stale screenshots. Scripts use an in-memory clipboard.

## Window and frames

| Command | Description |
| --- | --- |
| `size <width> <height> [scale <factor>] [at <x>,<y>]` | Sets window size in logical pixels, display scale factor (default `1`), and optional screen position in physical pixels. Required before the first `frame`. |
| `frame` | Processes queued input and background callbacks, rebuilds the view, and updates animations at the current clock time. |
| `snap <name>` | Saves `<name>.png` and `<name>.tree.txt` from the last frame into the output folder (plus `<name>.clipboard.txt` if the clipboard has text, and `<name>.opened.txt` with the addresses the app opened with `openUri` so far, one per line). `<name>` may include `/`. Additional windows are saved with their lowercase hyphenated title as a prefix (e.g., `groceries-<name>.png`). |
| `advance <seconds>` | Moves the app clock forward. Due `App.after` timers and animations update on the next `frame`. |
| `await [<seconds>]` | Waits for all `App.background` tasks to finish or cancel (default timeout: 10 seconds) and queues their callbacks for the next `frame`. Fails if tasks are still running after the timeout. |
| `await "<name>" [<seconds>]` | Waits only for the `App.background` tasks started with that name, such as `await "save"`, then queues everything posted so far for the next `frame`. Other tasks keep running, so a test can hold one at a gate and still see the result of another. Returns at once if no task of that name is running. |
| `await progress [<seconds>]` | Waits until a running background task reports progress via `Work.Progress` (default timeout: 10 seconds) and queues the update for the next `frame`. Fails if no task is running or none reports in time. |

## Pointer (mouse)

| Command | Description |
| --- | --- |
| `press <target> [clicks <n>] [shift] [control] [alt] [meta]` | Left-clicks the target. Use `clicks 2` for a double-click, and add modifier keys if needed. |
| `press <target> right` | Right-clicks the target (`El.onSecondaryPress`), for example to open a context menu. `down <target> right` and `up <target> right` perform the press and release separately. |
| `down <target> [clicks <n>] [modifiers]`, `up <target>` | Presses or releases the left mouse button separately. A click only triggers when both land on the same element. |
| `move <target>` | Moves the mouse over the target (triggers hover states and tooltips). Between `down` and `up`, moving more than 4 pixels starts a drag (such as text selection, scrollbars, or drag handlers). |
| `leave` | Moves the mouse outside the window, clearing hover states. |
| `wheel <target> <deltaX> <deltaY>` | Scrolls the mouse wheel at the target in logical pixels (positive values scroll down or right). Does not change hover state. |
| `scroll <target> row <index>` | Scrolls a virtual row list so row `<index>` (0-based) is at the top, or as far as possible. |

Note: `press` does not move the hover pointer. Add `move <target>` first when testing hover styles or tooltips.

## Keyboard and text

| Command | Description |
| --- | --- |
| `key <name> [shift] [control] [alt] [meta] [down \| up]` | Presses and releases a key, or holds/releases it across frames with `down` or `up`. Uses web key names (`Enter`, `Tab`, `Escape`, `ArrowDown`, `F5`, `Space`) and uppercase characters (`A`, `1`). See [`Key` Javadoc](/api/com/rethinkj/ui/Key.html). |
| `type "<text>"` | Types text into the focused element one character at a time (triggering autocomplete and per-character handlers). Supports `\"`, `\\`, `\n`, `\r`, and `\t`. To insert large text at once, use `clipboard` followed by `key V control`. |
| `compose "<text>"` | Simulates IME text composition (underlined, uncommitted text). `compose ""` clears it; `type` commits it. |
| `focus <target>` | Moves keyboard focus to the target (or its nearest focusable parent), showing the focus ring. |
| `clipboard "<text>"` | Sets the app's in-memory clipboard text. Does not require a `frame`. |

## System dialogs and file drops

Scripts never open OS dialogs. Instead, you pre-program their answers in order:

| Command | Description |
| --- | --- |
| `dialog "<path>" ["<path>" …] [filter <n>]` | Answers the next `App.fileDialog` with these file paths and optional filter index. |
| `dialog cancel`, `dialog button "<text>"`, `dialog error "<text>"` | Cancels the next dialog, clicks a message box button, or simulates a dialog error. |
| `drop <target> "<path>" …`, `drop <target> text "<text>"` | Simulates dropping files or text from another application onto the target. |
| `drop over <target>`, `drop leave` | Simulates hovering an external drag over the target or leaving the window. |

Place `dialog` lines **before** the step that opens the dialog. An unanswered dialog fails the frame, and unused `dialog` answers fail at the end of the script.

## Multiple windows

| Command | Description |
| --- | --- |
| `window <name>` | Directs subsequent commands to this window (`main` for the first window, or the window's title in quotes if it contains spaces). |
| `close` | Requests the active window to close. |

Pointer commands (`press`, `down`, `up`, `move`, `wheel`) and `drop` can also target another window directly with `in <window> <target>` or physical screen coordinates with `screen <x>,<y>`. For `focus` and `scroll`, switch windows first with `window <name>`. A window's `onShown` handler, set before the window first draws, runs at the `frame` step after the one that drew it. See [Several windows](/docs/concepts/windows).

## Error messages

When a step fails, [`Script.Failure`](/api/com/rethinkj/ui/Script.Failure.html) reports the line number and how to fix it:

```text
line 2: press role=switch label="Lamp"
  No frame has run yet, so there is nothing to press. Add `frame` before this line.
```

If a selector matches nothing, the error lists available keys, roles, labels, and states. If it matches multiple elements, it lists each match with its bounds. See [Targets and selectors](/docs/testing/selectors).
