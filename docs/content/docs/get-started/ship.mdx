---
title: Ship your app
description: Package the app with its own Java runtime as a jpackage app image.
---

`jpackage`, which comes with the JDK, builds an app image: a folder with a launcher, a Java runtime and the app's JARs. Users need no Java of their own. The commands below start from [your own project](/docs/get-started) and are shown for Linux.

## Build the image

Collect the app's JAR and its runtime dependencies, which include the fonts, the icons and the natives JAR of the platform that builds:

```sh
mvn -q package dependency:copy-dependencies -DincludeScope=runtime -DoutputDirectory=target/lib
cp target/lights-1.0-SNAPSHOT.jar target/lib/
```

Then build the image:

```sh
jpackage --type app-image --name Lights \
  --input target/lib --main-jar lights-1.0-SNAPSHOT.jar --main-class com.example.Lights \
  --add-modules java.base \
  --java-options --enable-native-access=ALL-UNNAMED \
  --dest target/dist
```

`--add-modules java.base` keeps the runtime small, since `core` and `kit` need nothing else; add the modules your own code uses. Without it, jpackage bundles the whole JDK. `jpackage` builds only for the platform it runs on: build the Windows image on Windows, where the natives profile picks the Windows JAR.

## Run it

```sh
target/dist/Lights/bin/Lights                                            # in a window
target/dist/Lights/bin/Lights --script lights.txt --out target/packaged  # under a script
```

On Windows, the launcher is `target\dist\Lights\Lights.exe`.

## Start faster

The JVM can start an app from an ahead-of-time cache of the classes it loaded and the code it ran in an earlier run ([JEP 514](https://openjdk.org/jeps/514)). For the examples on Linux, that brings the first frame about 150 to 170 ms sooner, from about 700 to about 550 ms. The cache is made by running the app once, so the image needs the runtime's `java` command, which `jpackage` leaves out by default; `--jlink-options` without `--strip-native-commands` keeps it:

```sh
jpackage --type app-image --name Lights \
  --input target/lib --main-jar lights-1.0-SNAPSHOT.jar --main-class com.example.Lights \
  --add-modules java.base \
  --jlink-options '--strip-debug --no-man-pages --no-header-files' \
  --java-options --enable-native-access=ALL-UNNAMED \
  --dest target/dist
```

Then run the app once with the window open as users see it, close it, and point the launcher at the cache:

```sh
JAVA_TOOL_OPTIONS=-XX:AOTCacheOutput=target/dist/Lights/lib/app/lights.aot target/dist/Lights/bin/Lights
echo 'java-options=-XX:AOTCache=$APPDIR/lights.aot' >> target/dist/Lights/lib/app/Lights.cfg
```

Make the cache again whenever the image is built again: the JVM uses it only with the JARs and the runtime it was made with, and otherwise starts without it after printing an error.

`Window.open` makes the GPU device on another thread while it opens the window. An app that does a lot before it opens its first window can start that sooner by calling [`GpuPresenter.prepare()`](/api/com/rethinkj/ui/render/GpuPresenter.html#prepare()) first in `main`.

To measure the start, `WindowLoop` logs at `DEBUG` on the `System.Logger` `com.rethinkj.ui.window` how many milliseconds after the process started each window showed its first frame; with `java.util.logging` (the module `java.logging`, which a packaged image adds with `--add-modules`), set `com.rethinkj.ui.window.level = FINE` and `java.util.logging.ConsoleHandler.level = FINE` to print it.

## Native libraries unpacked at install time

The packaged app unpacks the native libraries into the per-user cache on first start, like any other. An installer can instead place them next to the app and point `rethinkj.ui.natives.dir` at them: then nothing is unpacked, and the natives JAR can be left out. The folder holds the libraries and `manifest.txt`, as they are in the JAR under `META-INF/rethinkj-ui/natives/<platform>/`. `$APPDIR` is the folder of the app's JARs inside the image:

```sh
mkdir target/lib/natives
unzip -j target/lib/rethinkj-ui-natives-linux-x64-0.1.0-SNAPSHOT.jar \
  'META-INF/rethinkj-ui/natives/linux-x64/*' -x '*/licenses/*' -d target/lib/natives
rm target/lib/rethinkj-ui-natives-linux-x64-0.1.0-SNAPSHOT.jar
rm -rf target/dist
jpackage --type app-image --name Lights \
  --input target/lib --main-jar lights-1.0-SNAPSHOT.jar --main-class com.example.Lights \
  --add-modules java.base \
  --java-options --enable-native-access=ALL-UNNAMED \
  --java-options '-Drethinkj.ui.natives.dir=$APPDIR/natives' \
  --dest target/dist
```

The libraries' license texts are in the natives JAR under `META-INF/rethinkj-ui/natives/<platform>/licenses/`; ship them with the app.
