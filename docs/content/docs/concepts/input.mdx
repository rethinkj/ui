Elements take input through handlers. The app finds the element under the pointer, or the one with the keyboard focus, and runs its handler; if the handler changes the state, the view is built again. Kit components set all of this up; this page is for your own elements.

## Pointer

| Call | |
| --- | --- |
| `onPress(Runnable)` | A press: down and up on the element. Enter and Space press a focused element. |
| `onPress((clicks, modifiers) -> …)` | With the click count (2 for a double press) and the modifiers held |
| `onPress((clicks, modifiers, x, y) -> …)` | And where, in the element's content |
| `onSecondaryPress((x, y) -> …)` | The right button, where a context menu opens |
| `onPointerDown(...)` | As the button goes down, before anything moves |
| `onDrag(drag -> …)` | A drag, after the pointer moved more than 4 pixels |
| `cursor(Cursor.POINTER)` | The pointer's shape over the element |

A press goes to the innermost element with a press handler under the pointer, and counts only when the button goes down and up on it.

A `Drag` has its `phase` (`START`, `MOVE`, `END`, `CANCEL`), the step `dx`, `dy`, and where the pointer is in the element's content (`x`, `y`). Escape cancels a drag.

## Keyboard and focus

| Call | |
| --- | --- |
| `focusable()` | Tab reaches the element; a press focuses it |
| `onKey(key -> …)` | A key while the element or something inside it has the focus; return true to take it |
| `onKeyUp(...)`, `onText(text -> …)` | Releases, and typed text |
| `keepFocus()` | A press leaves the focus where it was: for buttons that act on an editor |
| `skipTab()` | Tab passes it by; a press still focuses it |
| `autofocus()` | Takes the focus in the build that adds it |
| `focusRing(argb)`, `focusRingGap(px)` | The ring drawn when the keyboard moved the focus |

Keys go to the focused element's key handler first. Enter and Space without modifiers then press the focused element if it has a press handler; any other key, and those two otherwise, go up through its ancestors until a handler takes one. If none does, Tab and Shift+Tab move the focus through the focusable elements in tree order. A `Key` has the web's key name (`"Enter"`, `"ArrowDown"`, `"A"`) and modifiers (`Key.CONTROL`, `SHIFT`, `ALT`, `META`).

When a rebuild leaves out the focused element, the focus goes to the nearest focusable element along its old place, so closing a tab puts the focus into the next tab's content. `app.focus(el)` moves the focus from a handler.

## Looks

| Call | |
| --- | --- |
| `whenHovered(e -> …)` | While the pointer is over it, or a press would go to it |
| `whenPressed(e -> …)` | While pressed |
| `whenFocused(e -> …)`, `whenFocusWithin(e -> …)` | While it, or something inside it, has the focus |
| `whenHoveredFor(seconds, e -> …)` | After the pointer rested on it: how a tooltip appears |
| `whenFocusVisibleFor(seconds, e -> …)` | After it had the focus with a ring that long: the keyboard's tooltip. It goes when the focus leaves or a key goes down that does not move the focus |
| `onHoverFor(seconds, handler)` | Runs once per stay after the pointer rested on it, or inside it, that long; with 0 in the frame that finds the pointer there. A menu follows the pointer with it |

A look changes the element after it is built; with `motion`, the change springs.

The delays run on the app's clock, so an idle window wakes for them and draws nothing while it waits, and a script moves the clock with `advance`. A press keeps a delayed look and `onHoverFor` away until the pointer has left the element and come back. A delayed look may attach an [overlay](/docs/concepts/overlays), which is how the kit's [Tooltip](/docs/components/tooltip) shows.

## Every press and key

Some components need to know of input that is not theirs: a menu bar tells Alt pressed alone from Alt held while something else happened, and an editor over a grid's cell hands its value on when the user presses elsewhere. These hooks take nothing from the input, which goes on as without them, and run in `frame()`, as handlers do, while the element is in the tree or in a shown overlay:

| Call | |
| --- | --- |
| `onAnyPointerDown(handler)` | Whenever a button of the pointer goes down anywhere in the window, before the press does anything else: in a text field, on a scrollbar, in an overlay or outside it |
| `onAnyKeyDown(key -> …)` | Every key that goes down, before any `onKey` handler or field sees it, also one the focused element takes |
| `onPressOutside(handler)` | A button goes down outside this element and everything inside it; an overlay attached inside it counts as outside |

Presses that the system takes, on the parts of a frameless window's frame, do not reach them.

## Holding the focus

`holdFocus()` makes an element hold the keyboard focus while the view marks it, as an open overlay does without being one: the build that first marks it moves the focus to it, or to its first focusable element, without a ring, and the first build that leaves the mark out gives the focus back to where it was, with the ring it had, if the focus is still inside it or nowhere. A press outside it calls its `onDismiss` handler and goes no further. Overlays that open inside it take the focus from it and give it back. The kit's [MenuBar](/docs/components/menu-bar) holds the focus this way from Alt or F10 until Escape: while its state says the bar has the keys, the view builds the bar with `.focusable().holdFocus().onDismiss(...)`, and without them otherwise.

## The wheel

The wheel scrolls the innermost scroll area under the pointer that can still move that way, then the next one out. Shift turns it sideways. `app.scrollTo(area, x, y)` and `scrollToRow(list, row)` scroll from a handler.
