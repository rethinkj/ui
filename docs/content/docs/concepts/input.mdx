Elements take input through handlers. The app finds the element under the pointer, or the one with the keyboard focus, and runs its handler; the view is then built again. Kit components set this up for you; this page is for your own elements. The calls in the tables below are methods of [`El`](/api/com/rethinkj/ui/El.html).

## Pointer

| Call | |
| --- | --- |
| `onPress(Runnable)` | A press: down and up on the element. Enter and Space press a focused element. |
| `onPress((clicks, modifiers) -> …)` | With the click count (2 for a double press) and the modifiers held |
| `onPress((clicks, modifiers, x, y) -> …)` | And where, in the element's content |
| `onSecondaryPress((x, y) -> …)` | The right button, where a context menu opens |
| `onPointerDown(...)` | As the button goes down, before anything moves |
| `onDrag(drag -> …)` | A drag, after the pointer moved more than 4 pixels |
| `cursor(Cursor.POINTER)` | The pointer's shape over the element |

A press goes to the innermost element under the pointer that has a press handler, and counts only when the button goes down and up on that element.

A [`Drag`](/api/com/rethinkj/ui/Drag.html) has its `phase` (`START`, `MOVE`, `END`, `CANCEL`), how far the pointer is from where it went down (`dx`, `dy`), and the pointer's position in the element's content (`x`, `y`). Escape cancels a drag.

## Keyboard and focus

| Call | |
| --- | --- |
| `focusable()` | Tab reaches the element; a press focuses it |
| `onKey(key -> …)` | A key while the element or something inside it has the focus; return true to take it |
| `onKeyUp(...)`, `onText(text -> …)` | Releases, and typed text |
| `onTypeAhead(text -> …)` | The text typed so far, to go to the item that starts with it, as a tree does; a pause of `App.TYPE_AHEAD` seconds or Escape starts anew |
| `keepFocus()` | A press leaves the focus where it was: for buttons that act on an editor |
| `skipTab()` | Tab passes it by; a press still focuses it |
| `autofocus()` | Takes the focus in the build that adds it |
| `focusRing(argb)`, `focusRingGap(px)` | The ring drawn when the keyboard moved the focus |

A key goes through these steps until one takes it:

1. The focused element's `onKey` handler.
2. Enter or Space without modifiers press the focused element, if it has a press handler.
3. The `onKey` handlers of its ancestors, innermost first.
4. Tab and Shift+Tab move the focus through the focusable elements in tree order. Page Up and Page Down scroll the innermost scroll area around the focus by one page; in a modal overlay such as a dialog, its first scroll area, also while the focus is on a button below it.

A [`Key`](/api/com/rethinkj/ui/Key.html) has the web's key name (`"Enter"`, `"ArrowDown"`, `"A"`) and modifiers (`Key.CONTROL`, `SHIFT`, `ALT`, `META`).

When the focused element leaves the tree, the focus moves to the nearest focusable element near its old place, so closing a tab puts the focus into the next tab's content. `app.focus(el)` moves the focus from a handler.

## Looks

| Call | |
| --- | --- |
| `whenHovered(e -> …)` | While the pointer is over it, or a press would go to it |
| `whenPressed(e -> …)` | While pressed |
| `whenFocused(e -> …)`, `whenFocusWithin(e -> …)` | While it, or something inside it, has the focus |
| `whenHoveredFor(seconds, e -> …)` | After the pointer rested on it: how a tooltip appears |
| `whenFocusVisibleFor(seconds, e -> …)` | After it had keyboard focus (with a ring) that long: a tooltip for keyboard users. Ends when the focus leaves or a key that does not move the focus is pressed |
| `onHoverFor(seconds, handler)` | Runs once each time the pointer has rested on it, or inside it, that long; with 0, as soon as the pointer is there. Menus use it to follow the pointer |

A look changes the element after it is built; with `motion`, the change animates.

Delays run on the app's clock: an idle window wakes for them, and a script moves the clock with `advance`. After a press, delayed looks and `onHoverFor` wait until the pointer has left the element and come back. A delayed look may attach an [overlay](/docs/concepts/overlays); that is how the kit's [Tooltip](/docs/components/tooltip) works.

## Watch all presses and keys

Some components need to see input meant for others: a menu bar tells Alt pressed alone from Alt used in a shortcut, and an editor over a grid cell commits its value when the user presses elsewhere. These hooks observe input without consuming it. They run like handlers, while the element is in the tree or in a shown overlay:

| Call | |
| --- | --- |
| `onAnyPointerDown(handler)` | Any pointer button goes down anywhere in the window, before anything else handles it |
| `onAnyKeyDown(key -> …)` | Any key goes down, before any `onKey` handler or text field sees it |
| `onPressOutside(handler)` | A button goes down outside this element and its descendants; an overlay attached inside it counts as outside |

Presses the system handles, on the title bar parts of a frameless window, do not reach them.

## Hold the focus in a region

`holdFocus()` makes an element take the focus like an overlay, without being one. In the first build that sets it, the focus moves to the element (or its first focusable descendant), without a ring. In the first build without it, the focus returns to where it was before, if it is still inside the element or nowhere. While it is set, a press outside calls the element's `onDismiss` handler and does nothing else. Overlays that open inside it take the focus and give it back.

The kit's [MenuBar](/docs/components/menu-bar) uses it from Alt or F10 until Escape: while the bar has the keyboard, the view builds it with `.focusable().holdFocus().onDismiss(...)`.

## The wheel

The wheel scrolls the innermost scroll area under the pointer that can still move in that direction, then the next one out. Shift scrolls sideways. `app.scrollTo(area, x, y)` and `scrollToRow(list, row)` scroll from a handler.
