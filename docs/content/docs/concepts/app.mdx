Every rethinkj UI app is built from two pieces:
- **State:** A plain Java object holding your application data.
- **View:** A function that takes the state and returns a tree of `El` elements.

`new App<>(state, view)` connects them ([`App`](/api/com/rethinkj/ui/App.html)). Event handlers update the state, and rethinkj UI automatically calls your view function again and renders the new frame. There is no data binding, no observable wrappers, and no manual diffing.

## The update loop

1. Input arrives (mouse click, key press, scroll wheel, typed text, or a callback from a background task).
2. `App` finds the target element (via hit testing or keyboard focus) and runs its handler.
3. The handler updates your state.
4. `App` calls your view function again, calculates layout, and updates animations.
5. The new frame is rendered.

Each input event runs against the view produced by the previous event. For example, pressing `ArrowDown` twice before a frame moves a selection down two rows, and pressing a key right after clicking a menu button sends that key to the newly opened menu.

## Rules for your view function

- **Keep it read-only.** The view should only read state and return elements. Only event handlers should modify state.
- **Rebuild the full tree.** Always build the current UI tree from state. For long lists, use virtual lists so only visible rows are built (see [Lists of many rows](/docs/concepts/rows)).
- **Use keys for identity.** `.key("lamp")` identifies an element among its siblings. Keys preserve animations, focus, scroll positions, and text cursors across rebuilds, and let test scripts find elements.
- **Provide a theme if needed.** Kit components read `Theme.CURRENT`, which defaults to `Theme.DARK`. To switch themes dynamically, call `app.provide(Theme.CURRENT, ...)` (see [Themes](/docs/concepts/themes)).

## What the app keeps for you

`App` automatically manages UI state that does not belong in your domain model: keyboard focus, hover state, scroll positions, running animations, text cursors, text selections, undo history, and the animation clock.

This state is tracked per element key and cleared when the element leaves the tree. To preserve scroll positions or text editor state when switching tabs or views, store a `ScrollState` or `FieldState` in your app state (see [Text fields](/docs/concepts/text-fields)).

## Threading

Your `App`, state, and elements all belong to the single app thread. Run slow operations (network calls, database queries, file I/O) on a worker thread with `App.background`, or deliver updates back from an existing background thread with `App.post` (see [Work off the app's thread](/docs/concepts/background-work)).

## Ways to run an app

- **Desktop window:** `WindowLoop.run(window, app, presenter)` — renders only when something changes and sleeps when idle.
- **Headless script:** `Script.handle(args, app)` or `Script.run(text, app, folder)` — see [Testing and agents](/docs/testing).
- **Single static frame:** `Headless.render(root, width, height, scale)` — returns pixels and the element tree.
- **Custom event loop:** See [Custom runner](/docs/reference/custom-runner).

| `App` method | Description |
| --- | --- |
| `resize(width, height, scale)` | Sets window size in logical pixels and display scale factor |
| `pointerMove(x, y)` | Moves the mouse pointer (logical pixels) |
| `pointerDown(x, y)`, `pointerDown(x, y, clicks, modifiers)`, `pointerUp(x, y)` | Primary mouse button down/up (`clicks = 2` for double-click, `modifiers` from `Key`) |
| `wheel(x, y, deltaX, deltaY)`, `wheel(x, y, deltaX, deltaY, modifiers)` | Mouse wheel scroll at position (positive scrolls down or right), with optional modifiers from `Key` |
| `keyDown(key)`, `keyUp(key)` | Key press/release using web key names and modifiers, e.g., `new Key("S", Key.CONTROL, false)` |
| `textInput(text)` | Sends typed text |
| `frame()` | Dispatches queued input, rebuilds the view, and renders; returns `true` if visuals changed |
| `advance(seconds)`, `time()` | Advances or reads the app clock used by animations, hover delays, and `after` timers |
| `await(timeout)` | Waits for `background` tasks to finish (and for cancelled tasks only if they have an `onEnd` handler), then queues their callbacks for the next frame |
| `tree()` | Returns the root of the last rendered frame (`tree().dump()` produces a [tree dump](/docs/testing/tree-dump)) |
| `render()` | Renders the last frame to pixels and a tree dump |

See the [`App` Javadoc](/api/com/rethinkj/ui/App.html#method-summary) for additional methods (right-click, pointer leave, IME composition, focus/scroll helpers, `awaitProgress`, and inspecting hovered/focused elements).

Without a window, `App` uses an in-memory clipboard (`Clipboard.inMemory()`). Read or replace it with `app.clipboard()` and `app.clipboard(clipboard)`.
