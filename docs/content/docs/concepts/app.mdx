An app is two things you write: a **state**, an ordinary object that holds the app's data, and a **view**, a function from the state to a tree of elements. `new App<>(state, view)` joins them. Handlers in the view change the state; after each input, the app calls the view again and draws the result. There is no data binding, no observer and no diffing to manage. ## The loop

1. Input arrives: a press, a key, a wheel step, text, or a task from another thread.
2. The app finds the element it is for, by hit testing or by the focus, and runs its handler.
3. The handler changes the state.
4. The app calls the view again, lays it out and animates what changed.
5. The frame is drawn.

Each input is handled against the view the previous input produced. Two Down keys before a frame move a selection by two rows; a key right after the press that opened a menu goes to the menu.

## Rules for the view

- **Read, never write.** The view reads the state and returns elements. Only handlers change the state.
- **Build everything.** The view runs after every input, so build the whole tree from the state each time. Long lists build only their visible rows (see [Lists of many rows](/docs/concepts/rows)).
- **Give identity with keys.** `.key("lamp")` identifies an element among its siblings. Animations, focus, scroll offsets and a text field's caret belong to that identity, and scripts find elements by key.
- **Pass the theme.** Kit components take the theme as their first parameter; the view gets it from the state or a constant.

## What the app keeps for you

The `App` tracks the focus, hover, scroll offsets, running animations, the caret, selection and undo history of text fields, and the clock. It keeps them per element identity and drops them when the element leaves the tree. To keep them across that, put a `FieldState` or `ScrollState` in your state ([Text fields](/docs/concepts/text-fields)).

## Threads

An app, its state and its elements belong to the thread that runs the app. Long work runs elsewhere and comes back with `App.post` or `App.background` ([Work off the app's thread](/docs/concepts/background-work)).

## Running it

- In a window: `WindowLoop.run(window, app, presenter)`. It draws only when something changed and waits otherwise.
- Without a window: `Script.handle(args, app)` or `Script.run(text, app, folder)` ([Testing and agents](/docs/testing)).
- One view alone: `Headless.render(root, width, height, scale)` returns the pixels and the tree.
- Inside another toolkit or loop: see [Custom runner](/docs/reference/custom-runner).

## Driving it from Java

A test can drive an app without a script. Input methods queue events, and `frame()` dispatches them in order, calls the view and runs the animations at the app's clock.

| `App` method | |
| --- | --- |
| `resize(width, height, scale)` | The window's size in logical pixels, and physical pixels per logical pixel |
| `pointerMove(x, y)`, `pointerLeave()` | The pointer moved, in logical pixels, or left the window |
| `pointerDown(x, y)`, `pointerDown(x, y, clicks, modifiers)`, `pointerUp(x, y)` | The primary button; `clicks` is 2 for the second press of a double click, `modifiers` the `Key` constants held |
| `secondaryDown(x, y)`, `secondaryUp(x, y)` | The secondary button, for `onSecondaryPress` |
| `wheel(x, y, deltaX, deltaY)` | The wheel at a position; positive scrolls down or right |
| `keyDown(key)`, `keyUp(key)` | A `Key` by its web name and modifiers, `new Key("S", Key.CONTROL, false)` |
| `textInput(text)`, `textComposition(text, cursor)` | Typed text, and an input method's composition |
| `focus(el)`, `scrollTo(area, x, y)`, `scrollToRow(list, row)` | Focus an element of the last frame as Tab would (null for none); scroll an area or a list of rows |
| `frame()` | Dispatches the queue and draws; true when what shows changed |
| `advance(seconds)`, `time()` | The app's clock, which springs, delays and `after` use |
| `await(timeout)` | Waits until `background` work has finished, and queues its results and other posted tasks for the next frame. Cancelled work is waited for only if it has an `onEnd` handler |
| `awaitProgress(timeout)` | Waits until running `background` work reports progress, and queues the reports and other posted tasks for the next frame |
| `tree()`, `focused()`, `hovered()`, `pressed()` | The root of the last frame, whose `dump()` is a [tree dump](/docs/testing/tree-dump), and its elements in those states |
| `render()` | The last frame's pixels and tree, as `Headless` makes them |

Until a window gives it the system clipboard, the app uses an in-memory one (`Clipboard.inMemory()`). `app.clipboard()` returns it; `app.clipboard(clipboard)` replaces it.
