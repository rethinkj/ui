A single `WindowLoop` can manage any number of desktop windows. Each window runs its own `App` (with independent focus, hover, scroll positions, and animations). Windows that share the same state object automatically stay in sync: when a handler updates state in one window, all other windows sharing that state rebuild in the same frame.

The kit's [TabGroups](/docs/components/tab-groups) uses this for tear-off tabs.

It returns a [`Windows.Handle`](/api/com/rethinkj/ui/window/Windows.Handle.html) with `close()`, `raise()`, `hide()`, `show()`, `isHidden()`, `moveTo(x, y)`, `onCloseRequest(handler)`, `onClosed(handler)`, `onShown(handler)`, `isOpen()`, and window position/scale getters. Use `windows.all()` to list all open windows or `windows.of(app)` to find a specific app's handle.

## Handling window close

- **`onCloseRequest(handler)`:** Runs when the user clicks the close button or presses Alt+F4. Your handler can close the window immediately, hide it to the system tray with `window.hide()` (only while a tray icon can show it again; without one, close it), show a confirmation dialog, or ignore the request. A hidden window stays open (keeping its state and tray icon) with no taskbar button and draws no frames until `window.show()` shows it again and brings it to the front. Without a handler, the window closes directly (or ends `WindowLoop` if it is the last open window).
- **`onClosed(handler)`:** Runs on the UI thread after a window closes (as long as at least one other window stays open). Use it to clean up per-window state:

## Knowing a window was shown

`onShown(handler)` runs on the UI thread in the frame after the window shows its first frame on screen. A minimized or hidden window shows no frame, so its handler waits until a frame appears. Use it to tell an updater that a new version started, close a splash screen, or measure time to the first frame. Set the handler right after `open`, before the window shows a frame. A handler set later does not run. For the first window of a `WindowLoop`, its handle is available before `run()`:

## Dragging between windows

Attach `El.dragPayload(object)` to a draggable element (`onDrag`) and `El.onDrop(drop -> …)` to drop targets in any window (`OVER`, `LEAVE`, and `DROP` phases). Each `Drag` event includes screen coordinates, `outside()` (whether the pointer left the origin window), `outsideAll()` (whether it is outside every window of the app, including windows that take no drops), and which window is currently under the cursor — allowing tear-off windows to follow the mouse. When a drag ends, any window opened with `Window.Options.underPointer()` during the drag moves fully inside its display's work area (except on Wayland, or if its minimum size is larger than the work area). This keeps the close button reachable if you drop the window near a screen edge. A window that follows the pointer with its last tab keeps only its title bar on screen, like a system title bar.

While the pointer stays over a drop target, the target receives `OVER` again every `Drop.REPEAT` seconds (0.05) on the app clock. `Drop.time()` returns that clock time. A drop target can use this to open an item the pointer hovers over, or to scroll while the pointer waits near an edge. In scripts, trigger these repeats with `advance` and `frame`.

To accept files or text dragged from external applications, use `El.onFileDrop`.

## Platform notes

Windows and Linux X11 allow apps to position windows freely. Linux Wayland does not allow apps to set window positions, so detached windows cannot follow the mouse cursor — provide menu actions like **Move to new window** and **Move back** as alternatives.

## Testing multiple windows in scripts

Windows opened by handlers are registered in headless scripts under their window title. Use `window <name>` to switch targets, `in <window> <target>` for cross-window pointer actions, and `snap` to save screenshots of every open window. See [Scripts](/docs/testing/scripts).
