---
title: Work off the app's thread
description: Run queries and file reads on another thread, post results back, cancel them, run them one after another, and act later on the app's clock.
---

An app, its state and its elements belong to the thread that runs the app, and only handlers change the state. Long work, such as a query or a file read, runs on another thread; its result comes back as a task that runs on the app's thread like a handler. [`App.background`](/api/com/rethinkj/ui/App.html#background(java.lang.String,java.util.concurrent.Callable,java.util.function.Consumer,java.util.function.Consumer)) does both and can cancel. `App.post` is the one method any thread may call. `App.after` runs an action later on the app's clock.

- `app.background(name, compute, onResult, onFailure)` runs `compute` on a virtual thread, then posts `onResult` with the result or `onFailure` with the exception.
- It returns a [`Work`](/api/com/rethinkj/ui/Work.html). `work.cancel()` interrupts the thread, and neither handler runs, even if the result already arrived.
- Pass the computation only what it needs (a table name, an SQL string, a connection), never the state or elements: nothing guards them against the app's thread.
- Virtual threads do not keep the JVM alive.

## Report progress

Give `background` a computation that takes a `Work.Progress`, and an `onProgress` handler. Each `progress.report(value)` runs `onProgress` on the app's thread.

```java snippet="reporting"
```

- No `onProgress` runs after `work.cancel()`, `onResult` or `onFailure`. In a loop that does not block, check `progress.isCancelled()`; a blocking call sees the interrupt.
- Reports that wait for the same frame may be merged into the newest, so `onProgress` runs about once per frame. Report the total so far (bytes read), not a step to add.
- Type the parameter, as `Work.Progress<Integer>` above, when the handlers do not fix the type.

## Run work one after another

A cancelled computation is interrupted but runs until it returns; a database driver may finish its statement first. For work that must not overlap, such as the calls on one connection, use a lane: `app.lane(name)` returns a [`Lane`](/api/com/rethinkj/ui/Lane.html) with the same `background` methods. Keep it in the state, one per connection. Work on a lane starts only when all work started before it there has ended, including cancelled work.

```java snippet="lane"
```

- Cancelling work that has not started removes it from the lane; it never runs. Cancelling the running work interrupts it, and the next starts when it has returned.
- `work.onEnd(handler)` runs on the app's thread when the computation has really ended: after `onResult` or `onFailure`, or after a cancel. It works on any `Work`, on a lane or not.
- `lane.pending()` lists the running work (also cancelled work that has not returned yet) and the waiting work; `work.isRunning()` tells them apart.
- A lane belongs to the app that made it. The apps of several windows on one state may all start work on it.

## Post a task

`app.post(runnable)` queues a task after the input before it. It runs on the app's thread, and the frame draws. It never blocks, and a waiting window wakes for it at once.

## Act later

```java snippet="after"
```

`app.after(seconds, action)` runs the action in the first frame at or after that time on the app's clock. An idle window wakes for it; a script runs it with `advance`.
