---
title: Work off the app's thread
description: Run slow tasks on background threads, report progress, cancel work, serialize tasks on a lane, and schedule timers.
---

Your `App`, state, and UI elements belong to the app thread. Never run slow work (such as database queries, HTTP requests, or file I/O) on the app thread, because it will freeze the window.

Instead:
- Use [`App.background`](/api/com/rethinkj/ui/App.html#background(java.lang.String,java.util.concurrent.Callable,java.util.function.Consumer,java.util.function.Consumer)) to run work on a virtual thread and receive the result or error back on the app thread.
- Use `App.post` to post a `Runnable` from any thread back to the app thread.
- Use `App.after` to run an action later on the app clock.

- `app.background(name, compute, onResult, onFailure)` runs `compute` on a virtual thread, then delivers the result to `onResult` or any thrown exception to `onFailure` on the app thread.
- It returns a [`Work`](/api/com/rethinkj/ui/Work.html) handle. Calling `work.cancel()` interrupts the worker thread and prevents `onResult` or `onFailure` from running (even if a result was already queued).
- Pass only immutable values or thread-safe resources (like a query string or connection) into `compute` — never touch app state or `El` objects from the background thread.
- Background virtual threads are daemon threads and do not prevent the JVM from exiting.

- `onProgress` stops running after `work.cancel()`, `onResult`, or `onFailure`. In non-blocking loops, check `progress.isCancelled()` periodically (blocking calls receive thread interrupts).
- Multiple progress updates arriving before the next frame may be coalesced into the latest one. Report cumulative totals (like bytes read so far) rather than deltas.
- If Java cannot infer the progress type from your handler, declare it explicitly: `(Work.Progress<Integer> progress) -> …`.

## Run work sequentially with lanes

When you cancel a task, the worker thread is interrupted, but it may take a moment to finish cleaning up (for example, closing a database statement). If tasks must never overlap — such as queries on the same database connection — use a [`Lane`](/api/com/rethinkj/ui/Lane.html).

Create a lane once with `app.lane(name)` and store it in your state. A lane provides the same `background` methods, but guarantees each task starts only after all earlier tasks on that lane have completely finished (including cancelled ones):

- Cancelling a queued task removes it before it starts. Cancelling the currently running task interrupts it, and the next queued task waits until it exits.
- `work.onEnd(handler)` runs on the app thread once the background computation has completely exited (after `onResult`, `onFailure`, or `cancel()`). Works on any `Work`.
- `lane.pending()` lists currently running and queued tasks; `work.isRunning()` distinguishes them.
- In multi-window apps sharing state, any window's `App` can submit work to the same lane.

## Post a task from any thread

`app.post(runnable)` safely queues a task from any thread to run on the app thread and triggers a frame redraw. It never blocks and wakes an idle window immediately.

`app.after(seconds, action)` runs `action` on the first frame at or after the delay on the app clock. In a desktop window it wakes automatically; in a headless script it triggers when `advance` reaches that time.
