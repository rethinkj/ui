---
title: Work off the app's thread
description: Run queries and file reads on another thread, post results back, cancel them, and act later on the app's clock.
---

An app, its state and its elements belong to the thread that runs it, and only handlers change the state. Work that takes long, a query or reading a file, runs on another thread, and its result comes back as a task that runs on the app's thread like a handler. `App.background` does both and lets you cancel; `App.post` is the one method any thread may call; `App.after` acts later on the app's clock.

```java snippet="background"
```

- `app.background(name, compute, onResult, onFailure)` runs `compute` on a virtual thread and posts `onResult` with its result or `onFailure` with its exception.
- It returns a `Work`. `work.cancel()` keeps both handlers from running, even when the answer already waits, and interrupts the thread: the answer of a request the user closed never arrives.
- Give the computation only what it needs (a table name, an SQL string, a connection), never the state or elements: the app's thread reads them while it builds the view, and nothing guards them.
- Virtual threads do not keep the JVM alive.

## Progress

Work that takes a while, a download or an import, can say how far it got. Give `background` a computation that takes a `Work.Progress` and an `onProgress` handler: each `progress.report(value)` from the work's thread runs `onProgress` on the app's thread, as a posted task does.

```java snippet="reporting"
```

- Reports end with the work: after `work.cancel()` no `onProgress` runs any more, also for reports that already wait, and none runs after `onResult` or `onFailure`. A report made after that is dropped. `progress.isCancelled()` tells a loop that does not block; a blocking read sees the interrupt.
- Reports that wait one after the other are coalesced into the newest, as long as nothing else was posted between them and no frame has taken them yet. A download that reports every 8 KB runs its handler about once per frame, and a report never overtakes a task its thread posted after it. So report the whole progress, such as the bytes so far, not a step to add.
- Type the computation's parameter, as `Work.Progress<Integer>` above, where the handlers do not say what a report is.

## Posting

`app.post(runnable)` queues a task after the input that came before it; it runs on the app's thread, against the view the input before it left, and the frame draws. It never blocks. A window wakes for it at once.

## Later, on the app's clock

```java snippet="after"
```

`app.after(seconds, action)` runs the action in the first frame at or after its time. An idle window wakes for it; a script runs it with `advance`.
