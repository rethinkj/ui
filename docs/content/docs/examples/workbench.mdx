The Workbench is the frame of a database manager: servers, databases, schemas, tables and columns in a tree beside a tab per opened table, each a query editor over the table's rows in a data grid. The servers are made up and answer slowly, on other threads, so it shows how an app stays responsive.

<Shot dark="examples/workbench-dark-2x" light="examples/workbench-light-2x" alt="The Workbench: a tree of connections, a query editor and a result grid in cards" />

```sh
mvn -q -pl examples -am compile exec:exec -Dexample=Workbench
```

## What to try

- Open `staging` in the tree: it connects on another thread while the tree shows a spinner; `prod-eu` refuses, and the status line says why.
- Double-press a table, or press Enter on it, to open it in a tab. `localhost/shop/public/orders` has a million rows.
- Type in the query: completions offer the tab's columns, then tables, then keywords. Control+Enter runs it; a table that does not exist is underlined.
- Control+Shift+P opens the command palette; `@` finds tables, `:` goes to a line.
- Drag a tab out of the bar: it gets a window of its own. Drag it back to dock it.

### The tree over the app's own nodes

### Connecting in the background

Opening a server asks for its databases with `App.background`. The work runs on another thread; the two handlers run on the app's thread and change the state, which builds the view again ([Background work](/docs/concepts/background-work)).

Asking a table for its rows works the same way. Closing the tab or running the query again cancels the `Work` that `App.background` returned.

Each tab's query is a [CodeEditor](/docs/components/code-editor) with SQL highlighting. Control+Enter runs the query before the editor's own keys; `Completion.complete` adds the completion list ([Completion](/docs/components/completion)).

The editor's two handlers are methods of the app: an edit keeps the query and takes the message of the last failure away, and Control+Enter runs it.
